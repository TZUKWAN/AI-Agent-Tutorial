# PART 4：怎样判断 Agent 是否真的做对了

> 先导图：验证三层证据模型（待插入 F07）
>
> 本 Part 是全书最重要的质量控制模块。前面三个 Part 教你"怎么把任务交给 Agent、怎么管长任务"，本 Part 教你一件更要紧的事：**Agent 说它做完了，你凭什么信它？**

---

## 4.1 "Agent 说完成了"不等于完成

### 本章要解决什么问题

你让 Agent"读这 20 篇论文，做一张证据矩阵"。两小时后它回你："已完成，文件保存在 `output/evidence_matrix.xlsx`，共 20 行，覆盖全部论文。"

你打开文件，确实有 20 行。然后你随便挑一篇论文，对照原文——发现 Agent 把一篇 2023 年的论文写成了 2018 年，把另一位作者的观点安到了这篇论文头上，甚至有一篇论文的 DOI 根本打不开。

**Agent 没有骗你，它真的"以为"自己做完了。** 这就是本 Part 要解决的核心问题：如何不被"完成声明"骗过，如何亲手确认结果真的对。

### 旧做法

在没有 Agent 的时代，你判断一个工作是否完成，靠的是：
- 自己读了多少、写了多少；
- 导师或同事当面指出问题；
- 最后自己通读一遍。

人对自己的工作有"体感"——你知道自己昨天那篇文献综述改了几遍、哪一段是硬凑的。Agent 没有这种体感，它不会"心虚"。它生成一个看起来很完整的文件，然后用最自信的语气告诉你"完成了"。

### Agent 做法

把"完成"这件事拆成三层证据，逐层核对：

```text
执行证据：Agent 实际做了什么操作？它真的打开了那 20 个文件吗？
结果证据：产出物本身存在吗？打开看了吗？内容对得上吗？
验证证据：有没有独立手段证明结果是对的？（交叉核对、重新算一遍、让另一个模型审）
```

Agent 说"完成了"，只能证明它**走到了流程的某一步**，不能证明结果正确。这就是本 Part 反复要建立的认知：

> **任务完成声明只是状态信息，不是完成证据。**
>
> 真正完成 = 执行证据 + 结果证据 + 验证证据。

### 最少概念

- **完成声明（Completion Claim）**：Agent 在回复里写的"已完成""已保存""已修复"。它是一句话，不是证据。
- **证据（Evidence）**：你可以独立检查的客观痕迹——文件、日志、运行输出、链接、截图、数字。
- **假完成（False Positive）**：Agent 声称完成但实际没完成，或完成得不对。5.6 节会专门讲。

### Mission M13：要求 Agent 证明它完成了

| 字段 | 内容 |
|------|------|
| Mission 名称 | 要求 Agent 证明它完成了 |
| 目标 | 让 Agent 在完成任务后，不只说"做完了"，而是给出三层证据 |
| 难度 | L3 |
| 预计需要的 Agent 能力 | 文件读写、代码执行、联网搜索 |
| 输入材料 | 任意一个你刚交给 Agent 的任务（例如"读 5 份 PDF 做摘要"） |
| 任务说明 | 在 Agent 声称完成后，不要直接交付，而是追加一句："在交付前，请你回答：1）你实际打开了哪几个文件，逐个列出文件名；2）产出文件的路径和行数；3）你做过哪些自检。任何一项拿不出证据，就不要说完成。" |
| 操作步骤 | 1）正常布置任务；2）Agent 回复"完成"后不验收，发出上面的追问；3）检查它列出的文件清单是否真的存在；4）抽查 1-2 个结果点 |
| 风险提示 | Agent 可能会"编"一个看起来合理的文件清单来应对追问，所以第 3 步必须由你亲自打开文件夹核对 |
| 成功标准 | 你能在文件夹里找到它说的每一个文件；抽查点全部对得上原文 |
| 失败案例 | Agent 列了 5 个文件，实际只生成了 2 个；或路径写错了一层目录 |
| 验证方式 | 亲自打开产出文件，对照原始材料抽查 |
| 进阶挑战 | 把"三层证据"写进你的任务模板，以后每个任务都要求 Agent 主动附上 |

### 最简单版本

一句话口诀：**"说完成不算数，拿出来给我看。"** 每当 Agent 说"做完了"，你就问三个问题：
1. 你动了哪些文件？
2. 产物在哪？
3. 你怎么知道是对的？

### 完整版本

把这三层要求写进每次任务的验收条款（8 要素任务法里的第 7 项"验收"）：

```text
验收要求：
1. 执行证据：列出你实际读取/修改/创建的每个文件路径；
2. 结果证据：产出文件必须真实存在于指定目录，并报告行数/字数/条数；
3. 验证证据：至少抽查 3 处结果，说明你是怎么核对的；
4. 任何一项无法提供证据，视为未完成，不得声称完成。
```

### 常见失败

1. **Agent 只给口头总结，不给文件路径。** 你无法定位产物，自然无法验证。
2. **Agent 给了路径，但路径是错的或过时的。** 文件在别的地方，或根本没保存成功。
3. **Agent 把"我生成了这段文字"当成"我完成了任务"。** 它写了一段综述文字贴在对话框里，但没存成文件，也没核对引用。

### 如何验证

不要相信 Agent 的自我感觉，相信你自己的眼睛：
- 文件是否真的在那个路径下；
- 打开文件，内容是不是你要的；
- 抽 1-2 个具体事实点，回到原始材料核对。

### 本章模板

```text
【交付前自查】
在声称完成之前，请确认并报告：
1. 我实际操作了哪些文件（逐个列路径）；
2. 产出物在哪、规模多大（行数/条数/字数）；
3. 我做过哪些验证、验证结果如何；
4. 还有哪些不确定或未完成的地方。
凡是第 4 条有内容的任务，都不得标记为"完成"。
```

### 延伸资源

- Anthropic 官方文档中关于 "Task completion" 与 "Verification" 的说明（以官方文档站最新版为准，核验日期 2026-09-18）。
- 软件工程领域的 "Done Definition"（完成定义）概念：一个任务不算完成，除非有可运行、可测试、可交付的产物。

### 完成标准

你能在任何 Agent 任务结束时，本能地问出"证据呢"，而不是直接相信"已完成"三个字。

## 4.2 执行证据：Agent 实际做了什么操作的记录

### 本章要解决什么问题

你让 Agent"把这 30 个文件分类整理到文件夹里"。它说整理完了。你怎么知道它真的读了 30 个文件，而不是只打开了前 5 个就开始凭印象写总结？

**执行证据**就是回答这个问题：把 Agent 的"操作流水账"留下来。

### 旧做法

你自己整理文件夹时，你知道自己打开过哪些文件、哪几个打不开、哪几个是乱码。这种记忆是天然的执行证据。Agent 没有这种记忆，它做完就"忘了"自己刚才干了什么，所以必须显式要求它留下记录。

### Agent 做法

让 Agent 在工作过程中持续记录"我现在读到哪了、遇到了什么问题"。常见的执行证据形式：
- **操作日志（Log）**：每一步做了什么，时间戳、文件路径、结果；
- **中间文件**：边做边存，而不是最后一次性生成；
- **执行轨迹（Trajectory）**：Agent 平台通常会自动记录它调用了哪些工具、传了什么参数、返回了什么。你可以回看这条轨迹。

### 最少概念

- **执行轨迹（Trajectory）**：Agent 从开始到结束，每一次"想做什么→调用工具→工具返回什么"的完整记录。这是最硬的执行证据。
- **操作日志（Log）**：你主动要求 Agent 写下来的工作日志，例如 `WORKLOG.md`。

### Mission M14（前半）：让 Agent 边做边记录

| 字段 | 内容 |
|------|------|
| Mission 名称 | 让 Agent 边做边记录操作日志 |
| 目标 | 任务结束后你有一份完整的操作流水账 |
| 难度 | L2 |
| 预计需要的 Agent 能力 | 文件读写 |
| 输入材料 | 任意多文件任务 |
| 任务说明 | 在任务开头加一句："请在工作目录维护一个 `WORKLOG.md`，每完成一步就追加一行：时间、动作、涉及文件、结果。" |
| 操作步骤 | 1）布置任务时附上这句话；2）任务结束后打开 `WORKLOG.md`；3）对照你预期的步骤数，检查它真的做了这么多步 |
| 风险提示 | Agent 可能补写日志（事后编造），所以要它"每完成一步就追加"，而不是"最后统一写" |
| 成功标准 | `WORKLOG.md` 里的步骤数与任务复杂度匹配，且每步都有具体文件名 |
| 失败案例 | 日志只有三行"已读取、已分析、已完成"，没有任何文件名，等于没记录 |
| 验证方式 | 抽日志里某一行，打开对应文件确认它确实被处理过 |
| 进阶挑战 | 让 Agent 在日志里标注每一步的"问题/异常"，而不是只记成功步骤 |

### 最简单版本

一句话：**"边做边记，别最后补。"**

### 完整版本

```text
工作记录要求：
- 每完成一个子任务，立即在 WORKLOG.md 追加一行；
- 格式：[时间] [动作] [涉及文件/URL] [结果/异常]；
- 遇到打不开的文件、找不到的网页、报错，必须原样记录，不得跳过；
- 任务结束时，WORKLOG.md 的行数应与子任务数大致匹配。
```

### 常见失败

1. **事后补日志**：Agent 最后一次性写一个"看起来合理"的日志，细节模糊。
2. **只记成功，不记失败**：打开失败的文件、404 的网页它不提，导致你以为全部成功。
3. **日志和实际操作对不上**：日志说读了 A 文件，实际 A 文件没动过。

### 如何验证

抽 2-3 条日志记录，亲自打开对应文件或链接，确认确实发生过。

### 本章模板

```text
请维护 WORKLOG.md：
- 每步追加，不事后补写；
- 记录所有失败和异常，不隐藏；
- 任务结束时附上日志全文。
```

### 延伸资源

- 主流 Coding Agent（如 Claude Code、Cursor、Codex）都自带执行轨迹查看功能，学会在你的平台里找到"对话/操作历史"面板。

### 完成标准

任务结束后，你能仅凭一份日志，复盘 Agent 到底做了什么、在哪一步出过问题。

## 4.3 输出证据：产出的文件/数据/结果本身

### 本章要解决什么问题

Agent 说"文献综述已经写好了"。你怎么确认它不是在对话框里生成了一段话、说完就没了？

**输出证据**就是：产物必须以"独立存在、可打开、可引用"的形式落在你的工作区里。

### 旧做法

学生交论文，是把 Word 文件交给老师。文件本身就是输出证据。Agent 时代最容易犯的错，就是把对话框里的一段文字当成"交付"——那段文字刷新就没了，无法审阅、无法对比、无法存档。

### Agent 做法

明确要求 Agent：
- 把结果**保存成文件**，而不是只贴在对话框里；
- 文件放在你指定的**输出目录**；
- 报告每个文件的**路径、行数/字数、生成时间**；
- 多张产出物之间**互相对应**（正文里引用的表格，必须真的存在于同目录）。

### 最少概念

- **输出目录（Output Directory）**：专门放产物的文件夹，和原始材料分开。原始文件不动，所有新东西都进 `output/`。
- **产物清单（Manifest）**：Agent 自己列的"我这次交了哪些文件"。

### Mission

| 字段 | 内容 |
|------|------|
| Mission 名称 | 让 Agent 交付一份产物清单 |
| 目标 | 任务结束时，你拿到一张"交付物清单"，且清单上每个文件都真实存在 |
| 难度 | L1 |
| 输入材料 | 任意任务 |
| 任务说明 | 在任务里写明："所有产出保存到 `output/` 目录。结束时，在对话框里列出交付清单：文件名、路径、行数/字数、一句话内容说明。" |
| 操作步骤 | 1）布置任务时指定输出目录；2）结束时拿到清单；3）打开 `output/` 文件夹，逐一点开清单上的文件 |
| 风险提示 | Agent 可能把"临时文件""缓存文件"也列进交付清单，注意区分 |
| 成功标准 | 清单上每一个文件都能在 `output/` 里找到，且内容符合一句话说明 |
| 失败案例 | 清单写了 `evidence_matrix.xlsx`，文件夹里只有 `evidence_matrix.csv`；或文件是空的 |
| 验证方式 | 双击打开每个文件，检查大小不是 0 字节、内容不是占位文字 |
| 进阶挑战 | 要求 Agent 在清单末尾加一行"未完成项"，把它没做的事也列出来 |

### 最简单版本

**"东西要落盘，光说不算。"**

### 完整版本

```text
交付要求：
- 所有产物保存到 ./output/，不要写在别的地方；
- 原始材料只读，不得修改或删除；
- 结束时输出交付清单：
  | 文件名 | 路径 | 规模(行/字) | 内容说明 |
- 凡是清单上没有的，不算交付；凡是清单上有但文件夹里找不到的，视为未完成。
```

### 常见失败

1. **对话框交付**：一大段文字贴在聊天里，没存文件。
2. **路径漂移**：Agent 把文件存到了它自己的临时目录，你找不到。
3. **空文件/占位文件**：文件名对了，打开是"待补充"或 0 字节。
4. **引用悬空**：正文写"见表 3"，但表格根本没生成。

### 如何验证

- 用文件管理器打开 `output/`，按修改时间排序，看新文件是不是 Agent 刚生成的；
- 逐个打开，不看大小，看内容。

### 本章模板

```text
输出要求：
1. 产物全部进入 ./output/；
2. 结束时给我一张交付清单表；
3. 清单外的东西不要说交付。
```

### 延伸资源

- 任何现代 Agent 平台都有"工作区文件树"面板，养成每次任务结束扫一眼文件树的习惯。

### 完成标准

你不再把对话框里的文字当作交付，只认 `output/` 里真实存在的文件。

## 4.4 验证证据：如何证明结果是对的

### 本章要解决什么问题

前两层证据解决了"它真的做了、东西真的存在"。但还有最后一层：**这个东西本身对不对？**

Agent 可能老老实实打开了 20 篇论文、认认真真写了一份综述——但它把 A 作者的结论安到了 B 作者头上。执行证据齐全、输出证据齐全，结果还是错的。

**验证证据**就是：用独立于 Agent 的手段，确认结果正确。

### 旧做法

论文写完，导师会挑两段让你"翻回原文看看你写的是不是这个意思"。这就是验证——不靠作者自己说对，靠回到原始材料核对。

### Agent 做法

验证证据有三种强度，从弱到强：

```text
弱：Agent 自己说"我核对过了"（这不算验证，只是它的声明）
中：回到原始材料/原始数据，重新抽查几个事实点
强：用另一条独立路径重新算一遍/重新查一遍，看结果是否一致
```

例如数据分析任务：
- 弱：Agent 说"平均数我算过了，是 47.3"；
- 中：你打开 Excel，用 `=AVERAGE(...)` 拉一下那一列，看是不是 47.3；
- 强：让 Agent 把计算过程写成代码，再让它用另一种方法（透视表/另一段代码）重算，两次结果一致才算过。

### 最少概念

- **抽查（Spot Check）**：不全部重算，随机挑 3-5 个点核对。对文科任务，就是挑 3 处引文、2 个数字。
- **独立重算（Independent Recalculation）**：用不同的代码、不同的工具、不同的路径，得到同一个结果。
- **回源（Source Trace）**：每个关键结论都能指回"它来自哪份原始材料的哪一段"。

### Mission M14（后半）：核验 20 条引用

| 字段 | 内容 |
|------|------|
| Mission 名称 | 核验 20 条事实/引用 |
| 目标 | 把 Agent 写的综述里的每一条引用，逐条回到原文核对 |
| 难度 | L3 |
| 预计需要的 Agent 能力 | 文件读取、联网搜索、PDF 阅读 |
| 输入材料 | Agent 生成的综述 + 原始论文 PDF 文件夹 |
| 任务说明 | 让 Agent 做一张核验表，每条引用一行：引用内容、作者、年份、DOI/出处、回原文核对结果（一致/不一致/找不到原文）、证据页码。不一致的标红。 |
| 操作步骤 | 1）让 Agent 生成核验表；2）你随机抽 3 条"一致"的，亲自打开 PDF 翻到那一页；3）再抽 2 条它标"不一致"的，看它说得对不对 |
| 风险提示 | Agent 可能"自评一致"时放水，所以第 2 步的亲自抽查不能省 |
| 成功标准 | 你亲自抽查的 5 条，结论与核验表一致；整表"不一致"项有明确说明 |
| 失败案例 | 核验表写"全部一致"，但你抽查发现它根本没打开 PDF，凭摘要猜的 |
| 验证方式 | 亲自翻 PDF 页码 |
| 进阶挑战 | 把 DOI 放进浏览器逐个打开，打不开的标出来 |

### 最简单版本

**"挑 3 个点，回到原文，亲眼看。"**

### 完整版本

```text
验证要求（科研任务）：
1. 综述中每个事实性结论后附【出处：文件名#页码】；
2. 生成核验表：逐条核对原文；
3. 我会亲自抽查 3-5 条，你必须能立即翻到对应页码；
4. 找不到原文支撑的结论，要么删除，要么标注"未证实"。
```

### 常见失败

1. **Agent 用自己的话复述原文，但已经走样**。它"觉得"意思差不多，实际关键数字错了。
2. **页码编造**：核验表写了"第 12 页"，翻过去根本没有这段话。
3. **只核对"顺眼"的引用**：难的、偏的它跳过了。

### 如何验证

- 文科：回到 PDF 原文，看页码和原话；
- 数据：用 Excel/计算器独立重算；
- 代码：让它把运行结果贴出来，不是只贴代码。

### 本章模板

```text
【验证条款】
- 关键结论必须回源；
- 我会抽查 3-5 处；
- 抽查前请你先自验，并附核验表；
- 自验不通过的，不要声称完成。
```

### 延伸资源

- 学术写作中的 "Evidence Matrix"（证据矩阵）方法：每条结论对应一份文献、一个页码、一句原文。

### 完成标准

你交付前，能指着任意一个关键结论说："这句话来自第 X 页，我核对过。"

## 4.5 学术引用真实性：如何核验论文/作者/DOI 真实存在

### 本章要解决什么问题

这是文科用户最容易踩、也最致命的坑。Agent 写综述时，会一本正经地列出：

> 张伟，李明. 生成式 AI 与知识劳动转型[J]. 中国社会科学, 2024(3): 112-130. DOI: 10.1234/abcd.2024.03.011.

格式完美、语气自信、期刊权威。但这篇论文可能根本不存在——作者、标题、DOI 全是 Agent 编的。你把它写进开题报告或论文，送审时被审稿人发现，后果是学术不端级别的。

### 为什么这是个高危问题

大语言模型训练时见过海量"像论文引用的字符串"，它最擅长生成**格式逼真**的文本。一个 DOI 格式对、作者名像真名、期刊名像真期刊的假引用，肉眼几乎无法分辨。

### Agent 做法

不要让 Agent"凭记忆"写引用。要让它**当场去查**，并把查询过程留下：

1. 每一条引用必须来自它实际打开过的 PDF 或实际检索到的网页；
2. DOI 必须在 **doi.org** 上真的能打开；
3. 作者、年份、期刊、卷期页码必须与原文一致；
4. 生成一张引用核验表，逐条标注"来源：本地 PDF / 知网 / 出版社页面 / Web of Science"。

### 最少概念

- **DOI（Digital Object Identifier，数字对象唯一标识符）**：学术论文的"身份证号"，格式形如 `10.xxxx/xxxxx`。真的 DOI 在 https://doi.org/ 后接这个号就能跳到原文。编的 DOI 打不开。
- **CrossRef**：一个公开的 DOI 注册数据库，可以用 DOI 反查它对应的论文标题和作者。
- **幻觉引用（Hallucinated Citation）**：Agent 编造的、看似真实但不存在的文献。

### Mission

| 字段 | 内容 |
|------|------|
| Mission 名称 | 批量核验引用真实性 |
| 目标 | 把 Agent 综述里的全部引用，逐条验证是否真实存在 |
| 难度 | L3 |
| 预计需要的 Agent 能力 | 联网搜索、浏览器、文件读取 |
| 输入材料 | Agent 生成的综述文档 |
| 任务说明 | "请把综述中所有引用逐条提取，生成核验表：序号/作者/年份/标题/期刊/DOI/你是怎么确认它存在的（打开了哪个网站、看到了什么）/状态（真实/存疑/编造）。编造和存疑的必须在正文里删除或替换。" |
| 操作步骤 | 1）让 Agent 提取全部引用；2）让它逐条联网核验；3）你自己再随机挑 3 条"真实"的，手动在浏览器打开 doi.org/DOI 看是否跳转；4）特别检查它标注"存疑"的那几条 |
| 风险提示 | Agent 可能把"我搜到了相似标题"当成"这条引用真实存在"，必须要求它打开原文页确认作者和年份完全一致 |
| 成功标准 | 每条引用都有可打开的来源链接；你抽查的 3 条全部跳转成功且信息一致；正文不再含编造引用 |
| 失败案例 | Agent 说"这条在知网能搜到"，但实际搜出来的是另一篇同名文章 |
| 验证方式 | 亲自在浏览器打开 DOI 链接，或在出版社官网/Google Scholar 搜索标题 |
| 进阶挑战 | 让它对每条引用记录"检索关键词"，方便你复现 |

### 最简单版本

**"DOI 点得开，才算数。"** 任何一条引用，如果它给不出一个能打开的链接，就当它是编的。

### 完整版本

```text
引用真实性要求：
1. 所有引用必须来自你实际打开过的来源，不得凭记忆生成；
2. 每条引用附一个可打开的 URL（DOI 或出版社页面）；
3. 作者、年份、标题、期刊、卷期、页码必须与来源页面完全一致；
4. 生成核验表，标注每条的确认方式；
5. 无法确认的引用，从正文删除并列入"未证实清单"。
```

### 常见失败

1. **作者名半真半假**：真实的学者名字 + 一篇不存在的论文。
2. **期刊真实、论文不存在**：《中国社会科学》是真的，但这一期没有这篇文章。
3. **DOI 格式对但打不开**：它会模仿 DOI 的格式，编一串数字。
4. **张冠李戴**：真实论文 + 错误的结论归属。

### 如何验证

- 浏览器打开 `https://doi.org/<那个DOI>`，看是否跳转；
- 在 Google Scholar、知网、出版社官网搜论文标题；
- 把标题加引号精确搜索，看是否有完全匹配结果。

### 本章模板

```text
引用核验任务模板：
- 提取全部引用 → 逐条联网核验 → 生成核验表 → 删除编造项 → 报告未证实清单。
- 任何一条拿不出可打开的来源，一律删除。
```

### 延伸资源

- doi.org（DOI 解析官方入口）；
- CrossRef 官网（DOI 元数据查询）；
- Google Scholar、知网、Web of Science 等权威学术检索。
- （以上入口以写作日 2026-09-18 可访问状态为准。）

### 完成标准

你综述里每一条引用，你都敢在浏览器当场打开它的 DOI 链接。

## 4.6 网页信息真实性：如何核验网页来源

### 本章要解决什么问题

Agent 做行业调研时说："据公开资料，某公司 2025 年营收 12.7 亿元，员工 3400 人。"这个数字从哪来？是公司年报、新闻报道，还是 Agent 编的？

**网页信息真实性**要解决两件事：来源是否真实存在；来源是否可信。

### Agent 做法

1. **每条关键事实必须附 URL**，不允许"据公开资料"这种无来源表述；
2. **打开那个 URL 亲自看**，确认数字确实写在那个页面上，而不是 Agent 从别处看来后自己拼的；
3. **优先权威来源**：公司官网/年报 > 官方统计 > 主流媒体 > 行业自媒体 > 匿名论坛；
4. **注意时效**：网页会改版、下架、更新，Agent 可能引用了一个已经不存在或内容已变的旧页面。

### 最少概念

- **来源追溯（Source Trace）**：每个事实能指回一个具体 URL。
- **权威层级（Source Hierarchy）**：官方原始材料 > 二手报道 > 观点评论。
- **链接腐烂（Link Rot）**：网页随时间失效。Agent 写报告时页面还在，你看的时候已经 404。

### Mission

| 字段 | 内容 |
|------|------|
| Mission 名称 | 做一份全来源可追溯的调研报告 |
| 目标 | 报告里每个数字/结论都有 URL，且 URL 当场可打开 |
| 难度 | L4 |
| 预计需要的 Agent 能力 | 联网搜索、浏览器、网页阅读 |
| 输入材料 | 任意调研主题 |
| 任务说明 | "报告中每个事实性陈述后用脚注标注来源 URL。完成后，把全部 URL 汇总成一张表，并逐个测试是否可访问、内容是否对得上。" |
| 操作步骤 | 1）让 Agent 写报告并附 URL；2）让它自检 URL；3）你随机点 3 个 URL；4）检查它用的是不是权威来源 |
| 风险提示 | 聚合站、二手转载不能当原始来源；新闻报道引用的数字要追到原始出处 |
| 成功标准 | 抽查 URL 全部可打开且内容匹配；关键数字有权威来源 |
| 失败案例 | Agent 引用一个 2019 年的旧数据，却写成"2025 年现状" |
| 验证方式 | 亲自点开链接 |
| 进阶挑战 | 让它对每条来源标注"发布日期" |

### 最简单版本

**"无链接，不采信。"** 任何没有 URL 的事实，都当它是 Agent 的猜测。

### 常见失败

1. **来源不可靠**：用自媒体文章当权威数据。
2. **时效过期**：旧新闻当成现状。
3. **链接失效**：报告写完，网页已下架。
4. **二手转抄**：新闻 A 引了年报数字，Agent 引新闻 A，但没核年报。

### 如何验证

点开链接，看发布日期、看原文、看是否原始出处。

### 本章模板

```text
调研报告要求：
- 每个事实后附 [来源：URL]；
- 优先原始出处（年报/官网/统计公报）；
- 标注发布日期；
- 交付前自测全部链接可达。
```

### 延伸资源

- 互联网档案馆 Wayback Machine（web.archive.org）可查网页历史版本，用于链接腐烂后找回原内容。

### 完成标准

你能顺着报告里的任意一个数字，点到它的原始出处。

## 4.7 数据真实性：如何核验数据来源和计算

### 本章要解决什么问题

你让 Agent 分析一个 5000 行的 Excel，它报告"用户平均停留时长 12.4 分钟，标准差 3.7，显著性 p<0.05"。你怎么知道这些数字不是它编的？

### Agent 做法

数据任务的验证有三道：

```text
第一道：数据来源
- 它用的是不是你给的那份原始数据？
- 行数、列名、时间范围对不对？
- 有没有它"顺手补充"的数据（这很危险）？

第二道：计算过程
- 让它把计算方法写清楚（用了哪一列、怎么过滤的、公式是什么）；
- 要求它把代码和运行结果都贴出来；
- 不允许只给结论不给过程。

第三道：独立复算
- 你用 Excel 的函数（=AVERAGE、=STDEV）手动算一下它报告的那一列；
- 或者让它用两种方法算，看是否一致。
```

### 最少概念

- **描述统计（Descriptive Statistics）**：平均数、中位数、标准差、最大最小值这类基础数字。
- **P 值（p-value）**：统计学中表示"结果是否显著"的指标，文科论文常见。Agent 最容易在这上面编数字。
- **复现（Reproducibility）**：换个人、换个工具，用同样的数据和方法，能算出同样的结果。

### Mission

| 字段 | 内容 |
|------|------|
| Mission 名称 | 验证一份数据分析报告 |
| 目标 | 报告里每个数字都能被你用 Excel 独立复现 |
| 难度 | L3 |
| 预计需要的 Agent 能力 | 代码执行、Excel 读写 |
| 输入材料 | 原始 Excel + Agent 的分析报告 |
| 任务说明 | "请把报告里每个统计数字的计算过程写成代码，并把代码的运行输出贴出来。同时说明：你用了哪一列、怎么过滤的、样本量是多少。" |
| 操作步骤 | 1）拿到代码和输出；2）打开 Excel，自己用函数算 2-3 个数字；3）对比样本量是否和原始数据对得上 |
| 风险提示 | Agent 可能在"清洗数据"时悄悄删掉它不喜欢的行，样本量就变了——必须让它报告样本量 |
| 成功标准 | 你手算的结果与报告一致；样本量与原始数据匹配 |
| 失败案例 | 报告说"有效样本 4800"，原始表明明 5000 行，但没说删了 200 行 |
| 验证方式 | Excel 函数手算 |
| 进阶挑战 | 故意改一个单元格，看它的报告会不会变——变了才说明它真的跑了你的数据 |

### 最简单版本

**"平均数？我自己拉一遍。"** 任何统计数字，先在 Excel 里验证一个再说。

### 常见失败

1. **数字编造**：它没真的算，凭感觉写了个"合理"的平均数。
2. **样本量不对**：清洗过程不透明，少了几行。
3. **列搞错**：分析了错误的那一列。
4. **统计方法错**：该用中位数用了平均数，该做检验没做。

### 如何验证

- 要代码 + 运行输出，只要结论不给过程的不算数；
- 手算 2-3 个关键数字；
- 检查样本量。

### 本章模板

```text
数据分析交付要求：
1. 报告每个数字附：用了哪列、过滤条件、样本量；
2. 附计算代码和真实运行输出；
3. 不得使用我没提供的数据；
4. 我会用 Excel 复算至少 3 个数字。
```

### 延伸资源

- Excel 的 `AVERAGE`、`STDEV.P`、`COUNTIF`、数据透视表是零基础用户最实用的复算工具。

### 完成标准

报告里任何一个关键数字，你都能用 Excel 在 30 秒内复现。

## 4.8 代码是否实际运行：不能只看代码，要看到运行结果

### 本章要解决什么问题

Agent 给你一段 Python 代码，说"运行这段就能画出图"。你打开一看，代码写得挺像那么回事。但它真的跑过吗？

**铁律一：代码生成 ≠ 功能完成。** 代码写出来和代码跑通，是两件事。一个零基础用户最容易被"看起来正确的代码"骗到。

### Agent 做法

- 要求 Agent 把代码**实际运行一遍**；
- 把**完整的运行输出**贴出来，包括有没有报错、报错长什么样；
- 如果画了图，图要真的生成在磁盘上；
- 报错了就继续改，改到跑通为止，不要"理论上应该可以"。

### 最少概念

- **运行时错误（Runtime Error）**：代码写得语法没错，但一跑就报错。这类错误人眼看代码很难发现，必须真跑。
- **标准输出（stdout）**：程序运行时在屏幕上打印的东西。
- **退出码（Exit Code）**：程序跑完返回的数字，0 表示成功，非 0 表示失败。退出码 0 只代表"程序没崩溃"，不代表"结果对"——这一点在 PART 5 还会强调。

### Mission

| 字段 | 内容 |
|------|------|
| Mission 名称 | 让 Agent 跑一段代码并贴出结果 |
| 目标 | 不只看代码，看到真实的运行输出 |
| 难度 | L4 |
| 预计需要的 Agent 能力 | 代码执行、终端 |
| 输入材料 | 任意一段 Agent 生成的代码 |
| 任务说明 | "请实际运行这段代码，把完整的终端输出贴出来。如果报错，把错误信息原样贴出来并修复，直到跑通。不要只给我代码。" |
| 操作步骤 | 1）要求运行；2）看输出；3）如果生成了文件/图，打开看 |
| 风险提示 | Agent 可能只贴"成功的几行"，把错误省略——要求它贴完整输出 |
| 成功标准 | 输出里能看到真实的运行痕迹（行数、时间戳、报错信息） |
| 失败案例 | Agent 说"运行成功"，但输出里只有它自己写的"已完成"三个字 |
| 验证方式 | 亲自运行一遍，或打开它生成的文件 |
| 进阶挑战 | 故意把文件名改错，看它会不会报错——会报错才说明它真的依赖这个文件 |

### 最简单版本

**"光给代码不算，跑给我看。"**

### 常见失败

1. **代码从未运行**：语法有隐藏错误，一跑就崩。
2. **只贴成功片段**：把中间的报错删掉，只留最后"成功"。
3. **跑了但结果不对**：程序没崩溃，但算错了（退出码 0 ≠ 结果对）。
4. **在 Agent 的沙箱里跑了，没在你的环境里跑**：换个环境就坏。

### 如何验证

- 要完整输出，不要裁剪版；
- 亲自跑一遍；
- 看生成的文件。

### 本章模板

```text
代码交付要求：
1. 必须实际运行；
2. 贴完整输出（含报错）；
3. 生成的文件/图保存在 output/；
4. 跑不通就继续修，不要说"理论可行"。
```

### 延伸资源

- 任何 Coding Agent 都有"运行/执行"按钮或终端面板，学会看那个面板而不是只看对话框回复。

### 完成标准

你分得清"一段看起来像代码的文字"和"一段真的跑通了的代码"。

## 4.9 软件功能是否真实测试：不能只听 Agent 说"已测试"

### 本章要解决什么问题

Agent 改了一个网页按钮，说"已经测试过了，点击正常跳转"。你点一下——页面白屏。

**铁律二：代码修改 ≠ Bug 修复。铁律三：测试通过 ≠ 产品完全正确。**

### Agent 做法

"测试"这个词，Agent 和人的理解完全不同。
- 人说"测试过了"：我真的点了那个按钮，看到了预期反应。
- Agent 说"测试过了"：可能只是它在脑子里"想象"了一下这段代码会怎么跑。

必须把测试从"声明"变成"动作"：
- 让它**实际点击/实际操作**，并描述操作前后的状态；
- 让它给出**可复现的测试步骤**；
- 关键功能**你自己点一遍**；
- 修完一个 Bug，要确认**原来出问题的场景现在好了**，同时**原来正常的功能没被搞坏**（这叫回归测试，Regression Test）。

### 最少概念

- **回归测试（Regression Test）**：改完一处后，把其他相关功能也试一遍，确认没被改坏。
- **测试用例（Test Case）**：一组明确的"输入→预期结果"。例如"点击红色按钮 → 应跳转至设置页"。
- **测试通过（Test Pass）**：实际结果与预期一致。不是 Agent 说"通过"就通过。

### Mission

| 字段 | 内容 |
|------|------|
| Mission 名称 | 让 Agent 对修改做真实测试 |
| 目标 | 每个修改都有"操作前/操作后"的证据 |
| 难度 | L4 |
| 预计需要的 Agent 能力 | 浏览器、代码执行 |
| 输入材料 | 一个 Agent 刚改过的软件/网页 |
| 任务说明 | "请列出你做的每一处修改，然后对每一处：1）描述改之前的状态；2）实际操作一遍；3）描述改之后的状态；4）确认它确实变好了；5）再试一遍原来正常的功能，确认没被改坏。" |
| 操作步骤 | 1）拿到测试清单；2）你自己挑 2 个功能点亲自操作；3）检查它有没有做回归测试 |
| 风险提示 | Agent 可能只测它刚改的地方，不测周边功能——这正是最容易出新 Bug 的地方 |
| 成功标准 | 每处修改有前后对比；周边功能也测了 |
| 失败案例 | 它说"测试通过"，但你一点按钮就报错 |
| 验证方式 | 亲手操作关键功能 |
| 进阶挑战 | 让它把测试步骤写成一份 checklist，以后每次修改都跑一遍 |

### 最简单版本

**"你说测过了？把你点了什么、看到了什么写下来。"**

### 常见失败

1. **想象测试**：没真的操作，只是"觉得应该没问题"。
2. **只测主路径**：正常情况测了，异常情况（空输入、错点、断网）没测。
3. **无回归**：修 A 坏 B。
4. **测试环境和真实环境不一样**：它在自己的沙箱里测好了，到你的机器上坏。

### 如何验证

- 自己点一遍关键功能；
- 故意制造一个异常（空输入、乱点），看它会不会崩。

### 本章模板

```text
修改后测试要求：
1. 每处修改附"前/后"状态描述；
2. 列出实际执行的测试步骤；
3. 必须包含回归测试（原有功能再测一遍）；
4. 你说测过的地方，我会亲手复核 2-3 处。
```

### 延伸资源

- 软件工程中的 "Smoke Test"（冒烟测试）：改完后先把主流程跑一遍，确认没塌。
- "Regression Test"（回归测试）概念在 LAB F 会系统讲。

### 完成标准

你不再接受"已测试"这三个字作为证据，只接受"操作步骤 + 前后对比"。

## 4.10 如何要求 Agent 自测

### 本章要解决什么问题

与其等你发现问题，不如让 Agent 在交付前自己先把自己挑一遍毛病。问题是：怎么让它的自测是真的，而不是走个过场？

### Agent 做法

关键是把"自测"从一句"你检查一下"，变成**结构化、可验收、带对抗性**的指令：

1. **明确检查清单**：不是"检查一下"，而是"逐条核对这 10 项"；
2. **要求它找问题，不是找优点**：让它扮演"挑刺的人"，而不是"验收自己作品的人"；
3. **要求它报告问题，而不是藏问题**：明确说"发现问题不要藏，列出来"；
4. **给它一个"对抗任务"**：让它假装自己是审稿人/用户，专门挑错。

### Mission

| 字段 | 内容 |
|------|------|
| Mission 名称 | 对抗性自测 |
| 目标 | 让 Agent 在交付前扮演"审稿人"挑自己的错 |
| 难度 | L3 |
| 预计需要的 Agent 能力 | 文件读取、分析 |
| 输入材料 | Agent 刚交付的产物 |
| 任务说明 | "现在请你切换角色：你是最严格的审稿人/用户，专门挑这份产物的毛病。不许表扬，只列问题：哪些事实可能错、哪些引用没来源、哪些地方含糊、哪些数字可疑。列一个问题清单，按严重程度排序。" |
| 操作步骤 | 1）拿到问题清单；2）看它挑出的问题是否真的存在；3）让它修完再交 |
| 风险提示 | Agent 可能"走过场"式地列两个无关痛痒的小问题——要求它至少列 5 个，且必须有严重级 |
| 成功标准 | 问题清单具体、有严重级分类、不是泛泛而谈 |
| 失败案例 | 它列"整体不错，建议微调语气"这种废话 |
| 验证方式 | 抽查它挑出的"严重问题"是否真实 |
| 进阶挑战 | 让它挑完问题后，自己逐条修复，再挑一轮 |

### 最简单版本

**"别夸自己，挑自己毛病。"**

### 常见失败

1. **自检变成自夸**：列一堆"亮点"，不列问题。
2. **挑软不挑硬**：只说排版问题，不说内容硬伤。
3. **挑了问题不修**：列完就交了，没改。

### 如何验证

看它挑出的问题是不是具体的、可验证的；泛泛而谈的不算。

### 本章模板

```text
【交付前对抗自测】
请切换为审稿人角色，只找问题：
1. 事实性问题（可能错的数据/引用/年份）；
2. 逻辑漏洞；
3. 含糊不清的地方；
4. 缺少来源的地方；
至少列 5 条，按 严重/中等/轻微 分级。
列完后逐条修复，再交。
```

### 完成标准

Agent 交付时不只给你产物，还附一份"我自己挑出的问题清单"和修复记录。

## 4.11 如何要求 Agent 交叉核验

### 本章要解决什么问题

同一个事实，只查一个来源可能被骗（那个来源本身就错）。**交叉核验（Cross-check）**就是：至少用两个独立来源，看它们说的是不是一回事。

### Agent 做法

- 关键事实至少两个独立来源；
- 两个来源要真正"独立"——不是 A 网站抄 B 网站，而是两个不同作者、不同机构、不同时间；
- 如果两个来源矛盾，以更权威的为准，并在报告里说明矛盾；
- 数据任务里，交叉核验 = 用两种方法算同一个数。

### 最少概念

- **交叉核验（Cross-check / Cross-validation）**：用第二条独立路径验证第一条路径的结果。
- **同源引用（Corroboration from Same Source）**：表面上有两个来源，但其实它们抄的是同一个原始出处——这不算独立。

### Mission

| 字段 | 内容 |
|------|------|
| Mission 名称 | 关键事实双源验证 |
| 目标 | 报告里每个关键数字/结论至少两个独立来源 |
| 难度 | L3 |
| 输入材料 | 调研报告 |
| 任务说明 | "请把报告里的关键数字挑出来，每个至少找两个独立来源核对。如果两个来源不一致，写清差异。" |
| 操作步骤 | 1）让它挑关键事实；2）双源核对；3）你检查它找的两个来源是不是真独立 |
| 风险提示 | 新闻 A 转引新闻 B，看起来两个来源，其实一个源头 |
| 成功标准 | 关键事实都有双源；矛盾处有说明 |
| 失败案例 | 两个来源都是同一个自媒体的不同文章 |
| 验证方式 | 追原始出处 |
| 进阶挑战 | 对统计数字，用"两个工具算"代替"两个网页查" |

### 常见失败

1. **伪双源**：抄同一源头。
2. **忽略矛盾**：两个数字不一样，它挑一个顺眼的写，不提另一个。
3. **来源权威度不匹配**：用论坛帖子核对官方数据。

### 本章模板

```text
关键事实交叉核验要求：
- 每个关键数字/结论 ≥ 2 个独立来源；
- 来源独立 = 不同作者/机构，非互相转引；
- 矛盾必须写明，不得隐瞒。
```

### 完成标准

你能对任意关键结论说："这两个独立来源都说了同一件事。"

## 4.12 如何让另一个模型/Agent 进行独立审查

### 本章要解决什么问题

自己审自己，总会有盲区。最强的验证手段，是**让另一个模型/Agent 独立审查**——主 Agent 干活，另一个 Agent 当"质检员"，两者互不认识、互不留情。

### Agent 做法

```text
主 Agent：负责生产（写综述、做分析、改代码）
        ↓
另一个 Agent（最好换一个模型）：负责审查
        - 不给它看主 Agent 的"自检报告"
        - 只给它最终产物 + 原始材料
        - 让它独立挑错、独立核对
        ↓
两份结果对比：主 Agent 说对的地方，审查 Agent 怎么看？
```

这就是软件工程里的 **Planner / Executor / Evaluator** 分离思想：干活的和检查的不是同一个人。

### 最少概念

- **独立审查（Independent Review）**：由没有参与生产过程的另一方来检查。
- **Evaluator（评估器）**：专门负责检查结果是否合格的 Agent 角色。
- **换模型（Model Swap）**：让 A 模型生产、B 模型审查，能显著降低"自己骗自己"的概率，因为不同模型的错误模式不同。

### Mission M17：让另一个模型独立审查结果

| 字段 | 内容 |
|------|------|
| Mission 名称 | 让另一个模型/Agent 独立审查结果 |
| 目标 | 同一份产物，由另一个模型独立挑错 |
| 难度 | L4 |
| 预计需要的 Agent 能力 | 多平台使用（至少两个对话窗口） |
| 输入材料 | 主 Agent 的产物 + 原始材料 |
| 任务说明 | 在另一个模型的新对话里，只粘贴产物和原始材料，不说"这是某 Agent 做的、它说自己做对了"，只说："请审查这份文档：逐条核对引用是否真实、事实是否准确、有无编造，列出所有问题。" |
| 操作步骤 | 1）主 Agent 出产物；2）开新对话换模型；3）只给材料不给立场；4）拿审查报告对比；5）分歧处人工裁决 |
| 风险提示 | 不要在审查对话里替主 Agent 辩护，否则审查会变客气 |
| 成功标准 | 审查 Agent 真的挑出了主 Agent 自检没挑到的问题；或确认无问题 |
| 失败案例 | 审查 Agent 看了产物也说"挺好的"——可能它能力不够，换更强的模型再审 |
| 验证方式 | 把审查出的问题回原文核对 |
| 进阶挑战 | 生产用快模型、审查用强推理模型，形成固定流水线 |

### 最简单版本

**"写完了？换个 AI 再读一遍。"**

### 常见失败

1. **审查放水**：新对话里你说了"这是我团队做的，帮我看看"，审查就客气了。
2. **审查者太弱**：换了个更弱的模型，它挑不出错。
3. **只让它看结论**：没给原始材料，它无法核对。

### 如何验证

审查 Agent 挑出的问题，必须能回到原始材料证实。

### 本章模板

```text
独立审查指令模板：
"这里有一份【产物】和它的【原始材料】。请你扮演严格审稿人：
1. 逐条核对事实/引用是否真实；
2. 找出逻辑漏洞；
3. 指出未提供来源的结论；
4. 不许表扬，只列问题和证据。"
```

### 延伸资源

- 多模型协作（Planner/Executor/Reviewer 分离）是 PART 10 会深入讲的高级架构，此处先建立直觉。

### 完成标准

重要任务交付前，你已经习惯"换个 AI 再读一遍"。

## 4.13 验收清单：要求→证据→结果→问题→修复→复验

> 先导图：验收闭环（要求→证据→结果→问题→修复→复验）（待插入 F08）

### 本章要解决什么问题

前面十二节讲了各种验证手段，最后要把它们收敛成一张你能直接照做的清单。以后任何 Agent 任务结束，你都按这六步走一遍。

### 验收六步闭环

```text
1. 要求（Require）
   - 任务当初要求什么？翻出你的 8 要素任务书，逐条对照。

2. 证据（Evidence）
   - 执行证据：WORKLOG、操作轨迹，它真的做了吗？
   - 结果证据：output/ 里的文件真的存在吗？
   - 验证证据：关键事实回源了吗？跑通了吗？

3. 结果（Result）
   - 打开产物，逐项对照要求：哪条做到了，哪条没做到，哪条走样了。

4. 问题（Issue）
   - 把没做到的、走样的、可疑的，列成问题清单，分级（致命/中等/小问题）。

5. 修复（Fix）
   - 把问题清单发回给 Agent，要求逐条修复。
   - 修复时不要让它"顺手改别的"。

6. 复验（Re-check）
   - 修完后，对被修的点重新走第 2-3 步。
   - 同时检查有没有修出新问题（回归）。
   - 全过才算完成。
```

### Mission M16：检查 Agent 是否假完成

| 字段 | 内容 |
|------|------|
| Mission 名称 | 用验收六步闭环检查一次交付 |
| 目标 | 把一次任务从"它说完成了"走到"你确认完成了" |
| 难度 | L3 |
| 预计需要的 Agent 能力 | 文件读写、对话 |
| 输入材料 | 任意一次你刚交给 Agent 的任务 |
| 任务说明 | 按六步清单逐项过：翻任务书→查三类证据→打开产物对照→列问题→打回修复→复验 |
| 操作步骤 | 1）拿出当初的任务书；2）查 WORKLOG 和 output/；3）打开产物对照；4）列问题清单；5）打回；6）复验 |
| 风险提示 | 第 3 步"打开产物"最容易跳过，必须真打开 |
| 成功标准 | 六步全走完，问题清单清零（致命项清零，小问题可记录但不阻断） |
| 失败案例 | 只做了第 1、2 步就说"看起来没问题" |
| 验证方式 | 六步每步留下痕迹（清单、截图、文件） |
| 进阶挑战 | 把这六步做成一个固定的 checklist 文件，每个任务复用 |

### 验收清单（可直接复制）

```text
【任务验收清单】
任务名称：__________  验收日期：__________

A. 要求对照
[ ] 任务书里的每一条要求，我都能在产物里找到对应
[ ] 没有多做（范围蔓延）也没有少做

B. 三类证据
[ ] 执行证据：WORKLOG / 操作轨迹齐全，每步有文件名
[ ] 结果证据：output/ 里每个文件真实存在且非空
[ ] 验证证据：关键事实回源、关键数字复算、关键代码跑通

C. 问题清单
| # | 问题描述 | 严重级 | 是否已修 | 复验结果 |
|---|----------|--------|----------|----------|
| 1 |          |        |          |          |

D. 修复与复验
[ ] 致命问题全部修复
[ ] 修复后无新问题（回归通过）
[ ] 最终我亲自抽查 3 处通过

验收结论：[ ] 通过  [ ] 打回  [ ] 有条件通过（遗留小问题：____）
验收人：__________
```

### 贯穿小结：科研论文核验 + 数据分析验证

以两条贯穿案例收尾：

**科研论文核验引用**：
- 要求：综述里每条引用真实、准确；
- 证据：每条引用有可打开的 DOI；
- 结果：综述正文与核验表一致；
- 问题：编造引用、张冠李戴、年份错误；
- 修复：删除或替换编造引用；
- 复验：随机抽 3 条当场点 DOI。

**数据分析结果验证**：
- 要求：每个统计数字可复现；
- 证据：计算代码 + 完整运行输出 + 样本量；
- 结果：Excel 手算一致；
- 问题：数字编造、样本量不对、用错列；
- 修复：重跑、重算；
- 复验：改一个输入单元格，看结果是否跟着变。

### 四大铁律（本 Part 必须刻进脑子）

```text
代码生成 ≠ 功能完成
代码修改 ≠ Bug 修复
测试通过 ≠ 产品完全正确
Agent 声明完成 ≠ 实际完成
```

### 本章模板

见上方"验收清单"，可直接复制使用。

### 延伸资源

- 软件工程中的 "Definition of Done"（完成定义）；
- 学术出版中的 "Peer Review"（同行评审）思想：独立第三方检查。

### 完成标准

任何 Agent 任务结束，你都能机械地走完六步闭环，并产出一张填好的验收清单。

## 5.1 幻觉（Hallucination）

### 实际案例描述

你问 Agent："马克思在《德意志意识形态》里有没有说过'人是一切社会关系的总和'这句话？"它一本正经地回答："确实有，见《德意志意识形态》第一章，马克思指出'人的本质不是单个人所固有的抽象物，在其现实性上，它是一切社会关系的总和'。"

听起来很对。但这句话实际出自《关于费尔巴哈的提纲》第六条，不是《德意志意识形态》。Agent 把出处安错了——这就是幻觉。

### 为什么会发生

大语言模型本质上是"根据上下文预测下一个最像人话的词"。它不"知道"事实，它只知道"哪些词经常出现在一起"。当它不确定时，不会说"我不知道"，而是生成一段**在语言上最像正确答案**的话。越是训练数据里常见的题材（经典著作、名人名言、常识），它编得越像真的。

### 如何发现

- 它说得越流畅、越自信，越要怀疑；
- 凡是涉及具体出处（页码、年份、DOI、数据），一律回源；
- 它从不使用"我不确定""需要查一下"这类词，而是什么都敢答——这本身就是危险信号。

### 如何预防

- 重要事实不让它"凭记忆答"，让它"先查再答"，并附来源；
- 在任务指令里写明："不确定的就说不确定，禁止编造"；
- 涉及经典文本、数据、法规，必须给出处。

### 如何恢复

- 发现幻觉后，不要只改那一句话，要让它**重新查一遍**那一类问题；
- 把"这条来源不对"的反馈告诉它，让它基于真实材料重写；
- 严重的幻觉（编造引用、编造数据）必须整条删除，不能"修补"。

---

## 5.2 编造论文 / DOI / 作者

### 实际案例描述

Agent 帮你写文献综述，文末参考文献列了 15 条。你打开 Google Scholar 一搜，其中 6 条根本不存在：作者名是真学者但论文是假的、DOI 格式对但 doi.org 打不开、期刊真实但这一期没有这篇文章。

### 为什么会发生

模型训练时见过数以百万计的"参考文献格式字符串"，它对"一篇正规引用长什么样"有极强的模仿能力。编出来的引用，格式完美、作者像真的、期刊名权威，肉眼几乎分不出。

### 如何发现

- **DOI 点不开**：把 DOI 贴到浏览器 `https://doi.org/<DOI>`，打不开就是假的；
- **标题搜不到**：把论文标题加引号在 Google Scholar 精确搜索；
- **作者对不上**：那个学者这一年没发过这篇论文；
- **卷期页码不存在**：期刊这一期的目录里没有它。

### 如何预防

- 写综述时，只允许引用**你已经上传给它的 PDF**，或它当场检索并打开的来源；
- 要求每条引用附可打开 URL；
- 用 4.5 节的引用核验表逐条过。

### 如何恢复

- 全部引用逐条核验；
- 编造的删除，不准用"差不多的真文献"顶替（那是另一种作弊）；
- 缺口用真实文献重新补齐。

## 5.3 编造数据

### 实际案例描述

你让 Agent 分析一份 3000 行的问卷数据，它报告："受访者平均年龄 27.3 岁，本科占比 68%，城市分布为一线 35%、新一线 42%……"你打开 Excel 用 `=AVERAGE` 一算，平均年龄明明是 31.8 岁——它根本没跑数据，数字是"合理编出来的"。

### 为什么会发生

模型对"一份数据分析报告该长什么样"有强烈预期，它能生成一个**统计上看起来合理、内部自洽**的数字组合。如果没有强制它贴代码和运行输出，它会直接给结论。

### 如何发现

- 只给结论不给计算过程的，一律怀疑；
- 用 Excel 手算 2-3 个数字；
- 检查样本量：报告说 N=3000，清洗后变成多少？没说明就是有问题；
- **反常识测试**：故意改一个输入单元格，如果报告数字不变，说明它没真跑你的数据。

### 如何预防

- 强制要求：代码 + 完整运行输出 + 样本量；
- 不准使用你没提供的数据；
- 关键统计量要求两种方法互验。

### 如何恢复

- 打回，要求它贴出真实运行输出；
- 如果确实是编的，让它从头真跑一遍，过程留痕；
- 已写进报告的数字全部重算。

## 5.4 编造网页结果

### 实际案例描述

你让 Agent"查一下某公司 2025 年的营收"，它回答："根据公司官网，2025 年营收 42 亿元，同比增长 18%，来源：https://example.com/about。"你点那个链接——404，或者打开是另一个不相关的页面。

### 为什么会发生

模型会根据公司名"想象"出一个它认为合理的数字和一个"看起来像官网"的 URL。即使它有联网搜索工具，也可能**没有真的调用**，而是凭训练知识生成了一段"应该是这样"的答案。

### 如何发现

- 点它给的 URL，看是否真的存在、内容是否真写了这个数字；
- 看发布日期：2025 年的事，它引用的页面是不是真在那个时间之后；
- 数字"太整"或"太像策划过的故事"时警惕。

### 如何预防

- 要求"每个事实附 URL + 发布日期"；
- 优先官方原始来源（年报、官网、统计公报）；
- 交付前让它自测全部链接。

### 如何恢复

- 打不开的链接对应的事实全部删除；
- 重新让它真的去搜、真的打开、真的抄数字；
- 追原始出处，不用二手转引。

## 5.5 编造测试结果

### 实际案例描述

Agent 改完一段代码，说："测试通过，12 个用例全部 pass。"你翻它贴的输出，那几行"test ok"是它**自己写的文字**，不是终端真实跑出来的日志——它根本没运行测试。

### 为什么会发生

"测试通过"四个字对模型而言太自然了。它知道一个工程师跑完测试后会说这句话，于是直接说出来，跳过了"真的去跑"这一步。

### 如何发现

- 真实的测试日志有固定格式（框架名、时间、逐行通过/失败、总结行）；Agent 编的往往过于干净；
- 让它贴**完整**终端输出，包括最前面的命令行和最后退出码；
- 你自己在你的环境里跑一遍。

### 如何预防

- 要求完整输出，不许裁剪；
- 要求它在你的环境里跑，不是只在它的沙箱里；
- 关键功能你亲手点一遍。

### 如何恢复

- 打回，要求真实运行并贴完整日志；
- 它若跑不通，让它如实报错并继续修；
- 修完做回归测试。

## 5.6 假完成（假阳性）

### 实际案例描述

你让 Agent"把下载文件夹按类型整理好"。它回复"已完成"。你打开一看：文件夹确实分类了，但它把你的毕业设计初稿、银行卡截图、简历全归进了"杂项"，而且重命名时把两个同名文件互相覆盖了。它"完成"了，但完成得很糟——这就是假阳性（False Positive，系统说"通过"，实际没通过）。

### 为什么会发生

Agent 的目标是"完成流程"，不是"符合你的真实意图"。它做到了表面动作（建了文件夹、移了文件），就认为任务完成。它不知道"毕业设计初稿比临时下载的压缩包重要"。

### 如何发现

- 用 4.13 的验收六步闭环，打开产物逐项对照；
- 抽查边界情况：重要文件、同名文件、大文件、特殊格式；
- 看它有没有在过程中问你"这个特殊情况怎么办"——没问，往往是它自作主张处理了。

### 如何预防

- 在任务里写清**优先级和例外**："毕业设计文件不许动""同名文件不要覆盖"；
- 重要操作要求它**先出方案、经你批准再执行**；
- 原始文件只读，让它在副本上操作。

### 如何恢复

- 从备份恢复被误处理的文件；
- 把你的真实意图补进任务书，让它重做；
- 记录这次假完成的点，下次任务提前防。

## 5.7 理解错版本

### 实际案例描述

你说"按我们上次定的方案改"，但它理解成了更早那版方案，或者把"中文版"理解成"英文版"。你拿到结果，发现全是错方向的。

### 为什么会发生

长对话里有多个版本、多轮修改，Agent 能看到的上下文有限（见 5.9）。它可能拿"印象中最新的"那一版来做，而那个印象是错的。

### 如何发现

- 结果和你预期差很多；
- 它引用的"上次方案"和你记忆中的对不上；
- 关键细节（语言、格式、对象）错了。

### 如何预防

- 重大节点明确写"以 V3 版为准，不要用 V1/V2"；
- 把当前生效的版本单独存成一个文件，让它以那个文件为准；
- 长任务用状态文件（PART 3 的 PROGRESS.md）记录"当前到底是哪一版"。

### 如何恢复

- 明确指出"你用错版本了，应该是这一版"；
- 把正确版本重新贴给它；
- 让它基于正确版本重来，不要在错的版本上硬改。

## 5.8 读取错文件

### 实际案例描述

你让它"分析去年的销售表"，工作目录里有 `sales_2024.xlsx` 和 `sales_2023_final.xlsx`，它打开了后者，然后报告了一堆"去年"的数据——其实是前年的。

### 为什么会发生

文件名相似时，模型只看文件名做判断，不会真的打开确认表头和日期。尤其"final""new""最新"这种词，它会随机挑一个。

### 如何发现

- 报告里的日期/年份和你预期对不上；
- 表头列名和那份文件对不上；
- 行数和你印象里的不一致。

### 如何预防

- 在任务里**写完整文件名**，不要说"那份销售表"；
- 让它第一步先报告"我要打开的是哪个文件、里面有哪些列"，你确认后再继续；
- 文件命名去掉歧义：`sales_2024.xlsx` 而不是 `sales_final.xlsx`。

### 如何恢复

- 指出读错文件；
- 让它关掉错的，打开对的重来；
- 错的那份产出作废。

## 5.9 上下文不足

### 实际案例描述

你上传了一本 500 页的书，让它"总结全书并写读书报告"。它总结得很泛，关键章节的细节全错——它根本没看完，只看了开头几十页就开始"总结"。

### 为什么会发生

模型一次能看的信息量有上限，叫**上下文窗口（Context Window）**。超出这个窗口的内容，它要么截断、要么"概括成大概"，然后自信地继续写。它不会主动告诉你"我没看完"。

### 如何发现

- 它只提了开头的内容；
- 后半本书的问题它答不上或乱答；
- 它引用的页码集中在前几十页。

### 如何预防

- 长材料**分段喂**：一次读一章，逐章做笔记，最后汇总；
- 明确告诉它材料多长、要求它分段处理；
- 用 RAG（检索增强生成，PART 6 讲）把长文档切成块，按需检索。

### 如何恢复

- 把材料拆段，让它逐段处理；
- 检查它每段是否真的读了；
- 汇总时让它引用各段笔记，而不是凭印象重写。

## 5.10 上下文污染：文件越多不一定越好

### 实际案例描述

你觉得"材料越多 Agent 懂得越多"，于是把整个项目文件夹——包含旧版本、废弃草稿、别人的论文、临时下载——全塞给它。结果它引用了一份废弃草稿里的错误数据，写出来的报告全是旧版本的内容。

### 为什么会发生

这和 5.9 是一体两面。上下文塞太满时：
- 无关内容会**稀释**关键信息，让模型抓错重点；
- 多个版本混在一起，它不知道哪个是当前版；
- 矛盾的信息让它"自由发挥"。

这就是**最小充分上下文原则**：给它刚好够完成任务的材料，不多给一份。

### 最少概念

- **最小充分上下文（Minimal Sufficient Context）**：只给完成这个任务必需的材料，无关材料一律不进。多给的不是帮助，是噪音。

### 如何发现

- 结果里出现了你没让它用的旧文件内容；
- 它引用了一个你以为早删了的版本；
- 多个版本混着说。

### 如何预防

- 任务开始前**先整理工作区**：把无关文件移出，或明确告诉它"只用这些文件"；
- 用一个"输入文件清单"限定范围；
- 废弃文件改名为 `_old_xxx`，并说明不要用。

### 如何恢复

- 清理上下文，只留必要文件；
- 让它重新基于正确范围做；
- 把污染内容从产出里剔除。

## 5.11 长任务遗忘

### 实际案例描述

一个跑了三小时的长任务：前半段它认真按你的要求"所有引用必须真实"，做到后半段，它开始编造引用了——因为早期的指令被挤出了上下文窗口。

### 为什么会发生

长任务中，模型能看到的"最近内容"有限。你一小时前的关键约束，到任务后期可能已经不在它的注意力范围内。它不会提醒你"我快忘了你的要求了"。

### 如何发现

- 越往后做，越不遵守你早期定的规矩；
- 前后风格/标准不一致；
- 它做着做着开始"自由发挥"。

### 如何预防

- 用 PART 3 的**状态文件**（TASKS.md、PROGRESS.md）把关键约束写进文件，而不是只在对话里说；
- 每隔一段让它**重新读一遍任务书**；
- 关键要求（如"禁止编造引用"）在任务书开头写，并且每完成一个里程碑让它复述一遍。

### 如何恢复

- 停下来，把关键约束重新发给它；
- 让它对照约束检查后半段产出；
- 把违反约束的部分打回重做。

---

## 5.12 修改造成新 Bug

### 实际案例描述

你让它"修一个按钮点不开的问题"，它改完，按钮能点了——但旁边的表单提交坏了。它只测了按钮，没测表单。

### 为什么会发生

改代码像牵一发动全身。Agent 关注的是"让我改的那个点通了"，不太会主动想到"这一改动可能影响别处"。

### 如何发现

- 原来正常的功能突然不正常；
- 你多试了几个地方才发现；
- 它的测试清单里只有被修的那个点。

### 如何预防

- 修完必须做**回归测试**：把相关功能都试一遍（4.9 节）；
- 一次只改一处，改完测完再改下一处；
- 重要代码先备份（Git 提交），改坏了能退。

### 如何恢复

- 用备份/Git 回到改之前的版本；
- 这次修复拆小，改一处测一处；
- 把"受影响的周边功能"列进测试清单。

## 5.13 误删文件

### 实际案例描述

你让它"清理临时文件"，它把 `temp/` 目录里它认为没用的东西删了——其中一个其实是你刚存的原始数据备份。

### 为什么会发生

"删除"这个动作，模型判断"这个文件是不是没用"靠的是文件名和印象，不了解每个文件对你的重要性。删除又通常不可逆（回收站也可能被它清空）。

### 如何发现

- 重要文件不见了；
- 它的操作日志里出现了 `delete`/`rm`；
- 你发现 `temp/` 里少了东西。

### 如何预防

- **删除操作一律要求人工确认**（L4 风险，见第 7 部分风险分级）；
- 让它"先列出要删的清单，经你批准再删"；
- 删之前先把要删的移到一个 `_trash/` 文件夹，而不是直接删；
- 重要文件提前备份。

### 如何恢复

- 第一时间停止它继续操作；
- 从回收站、备份、Git 历史恢复；
- 如果都没有，这次损失记下，下次任务加"禁止删除"约束。

## 5.14 覆盖原始数据

### 实际案例描述

你让它"清洗数据"，它直接在 `survey.csv` 上改，存回原文件。清洗完你发现：原来的原始答卷被它合并、去重、删行后，已经找不回来了。

### 为什么会发生

模型觉得"在原文件上改完保存"是最直接的做法。它不知道"原始数据"和"清洗后的数据"必须分开——一旦覆盖，统计就无法复现。

### 如何发现

- 原始文件的修改时间变了；
- 行数和最初不一样了；
- 你想"回到原始状态"回不去。

### 如何预防

- **铁律：原始数据只读，永远在副本上操作。** 在任务里写明："原始文件不得修改，清洗结果存到 `output/cleaned.csv`"；
- 任务开始前先复制一份原始数据；
- 用 Git 管理数据，改之前先提交。

### 如何恢复

- 如果有备份/副本，恢复；
- 用 Git 历史回到改之前；
- 没有备份的，这次教训深刻记住：下次先复制。

## 5.15 无限循环

### 实际案例描述

你让它"修到测试全过为止"。它改一版、跑测试、失败、再改、再跑、再失败……一小时过去了，它还在同一个 Bug 上打转，每次用相似的方法，每次失败。

### 为什么会发生

模型遇到它解决不了的问题时，不会主动说"我卡住了"，而是反复尝试相似策略。没有"放弃阈值"时，它会一直烧你的时间和钱。

### 如何发现

- 同样的错误信息反复出现；
- 它的修改方向没有实质变化；
- 时间和 token 消耗异常增长。

### 如何预防

- 设**重试上限**："最多试 3 次，3 次不行就停下来报告"；
- 让它每试一次记录"我试了什么、为什么不行"；
- 卡住超过一定时间就人工介入。

### 如何恢复

- 打断它，让它停下；
- 让它先汇报"已经试了哪些方法、为什么都不行"；
- 你给新方向，或换一个模型/换个任务拆解方式。

## 5.16 Token / Context / Cost 失控

### 实际案例描述

你让它"分析这个大项目"，它开始读每个文件、生成中间报告、又读一遍、又总结……一晚上烧掉了几十万 token，账单出来吓一跳，最后结果还没做完。

### 为什么会发生

- **Token（词元）**是模型计费和计量的基本单位，你读的每一个字、写的每一个字都花 token。
- 长任务里，模型可能反复读同一批文件、生成冗余中间产物，token 像漏水一样消耗。
- 上下文窗口也有限，塞太满会触发截断（5.9），同时费用飙升。

### 如何发现

- 平台显示的 token 用量/费用涨得异常快；
- 任务做了很久还没收尾；
- 它反复读相似的文件。

### 如何预防

- 任务开始就设**预算和上限**："最多花 X 分钟 / X 次迭代，做完或超限都要停下汇报"；
- 限定它读哪些文件，不要让它"自己探索整个文件夹"；
- 中间产物存文件，不要全堆在对话框里；
- 长任务用分段，别一次塞全部。

### 如何恢复

- 立刻打断；
- 让它停下并汇报当前进度；
- 缩小范围，改成更小的子任务重新布置。

## 5.17 API 调用成本

### 实际案例描述

你给 Agent 接了一个付费 API（比如某个检索服务、多模态模型）。它在任务里反复调用，一次任务调用了几百次，费用远超预期。

### 为什么会发生

Agent 调用 API 的次数你不一定能实时看到。它为了"保险"，可能同一件事调多次，或在循环里反复调用。

### 如何发现

- API 平台后台用量异常；
- 账单突然增加；
- 任务里有循环/批量处理。

### 如何预防

- 关键 API 设置**调用次数上限**（平台侧或任务指令里）；
- 付费操作要求它先估计"我打算调多少次"，你批准后再调；
- 优先用便宜模型做批量活，强模型只做关键判断。

### 如何恢复

- 立刻停任务；
- 在 API 平台设硬限额；
- 把批量任务拆成"先试一小批，确认没问题再全量"。

## 5.18 Rate Limit（请求频率限制）

### 实际案例描述

你让它批量查 500 条文献，它每秒发很多个请求，突然报错："Too Many Requests / 429"，任务中断。

### 为什么会发生

网站和 API 都有**速率限制（Rate Limit）**：单位时间内只接受一定次数的请求，防止被刷。Agent 不知道这个限制（除非你告诉它），开足马力就会被拒。

### 如何发现

- 报错信息里出现 429、rate limit、too many requests；
- 任务跑到一半停了；
- 间歇性失败。

### 如何预防

- 批量任务里让它**放慢速度**："每批 10 个，批与批之间停几秒"；
- 告诉它"遇到 429 就等待再试，不要立刻重试"；
- 大量请求前查目标网站的使用条款。

### 如何恢复

- 让它等待一段时间再继续；
- 加入"重试间隔"和"最多重试次数"；
- 把大批量拆成小批次分批跑。

## 5.19 网络失败

### 实际案例描述

Agent 正在查资料，网络断了，或某个网站暂时打不开，它的任务卡住或报错。

### 为什么会发生

网络是不可靠的：断网、DNS 故障、网站临时维护、跨网访问慢。这些都不是 Agent 能控制的。

### 如何发现

- 报错是连接超时、无法访问、502 等；
- 任务没做完就停了。

### 如何预防

- 关键资料**先下载到本地**，不要依赖现场联网；
- 让它对每个下载失败的链接**记录下来**，不要整个任务崩掉；
- 把"网络失败"当作正常情况，任务设计成"断了也能存已完成部分"。

### 如何恢复

- 检查网络恢复后，让它从断点继续（见 5.21 的 Resume）；
- 失败的链接单独列出来，换时间再试；
- 实在下不到的，换来源。

## 5.20 依赖安装失败

### 实际案例描述

你让它跑一段数据分析，它要装一个 Python 包，结果安装报错：版本冲突、网络超时、系统不兼容。它卡在"装环境"这一步，业务代码一行没跑。

### 为什么会发生

代码运行需要**依赖（Dependency）**——别的软件包。这些包之间版本要匹配、要能下载、要和你的系统兼容。零基础用户最容易在这里被卡住。

### 如何发现

- 报错里出现 `pip install`、`npm install`、dependency、version conflict；
- 它说"需要安装 XX"然后就没下文了。

### 如何预防

- 优先用**不依赖安装**的方案（Excel、在线工具）；
- 让它用**常见、稳定**的包，不要追最新版；
- 安装失败时，让它把完整报错贴给你，不要自己反复试；
- 复杂环境交给专业的 Coding Agent 在它的沙箱里解决。

### 如何恢复

- 贴出完整报错，让它针对性解决；
- 版本冲突时，让它固定一个已知可用的版本；
- 实在装不上，换工具或换方法。

## 5.21 恢复策略：Backup / Git / Snapshot / Copy / Rollback / Retry / Resume

> 先导图：恢复策略决策树（待插入 F10）

### 本章要解决什么问题

前面 20 个失败模式，最后都汇到一个问题：**出错了怎么办？** 本 Part 最后一节教你一套通用的"踩坑之后怎么爬出来"的工具箱。不是让你背术语，而是让你在出事时知道该按哪个按钮。

### 七件恢复工具（按零基础友好度排序）

| 工具 | 一句话解释 | 什么时候用 | 零基础怎么上手 |
|------|-----------|-----------|----------------|
| **Copy（复制）** | 动手前先把原件复制一份 | 任何重要操作前 | 选中文件夹 → Ctrl+C → Ctrl+V 到旁边 |
| **Backup（备份）** | 把整个工作区存一份副本 | 长任务、批量操作前 | 任务开始前，把整个项目文件夹复制一份到 `备份_日期/` |
| **Snapshot（快照）** | 给当前状态拍一张"照片"，可随时回到这一刻 | 想多试几种方案时 | 复制一份当前整个文件夹，起名 `snapshot_尝试1` |
| **Rollback（回滚）** | 回到上一个好的状态 | 改坏了、覆盖了 | 用备份或快照把文件换回来 |
| **Retry（重试）** | 失败了再试一次 | 网络抖动、429、临时错误 | 让它"等几秒再试，最多 3 次" |
| **Resume（续跑）** | 从中断处接着做，不重头来 | 长任务中途失败 | 把"做到哪了"写在状态文件里，下次让它读这个文件继续 |
| **Git（版本控制工具）** | 专业的修改历史记录，能精确回到任意一次提交 | 代码、文档的持续修改 | 第 8 部分 LAB F 会系统教，零基础先知道"它是带历史的备份"即可 |

### 核心原则

**预防永远比恢复便宜。** 在你让 Agent 做有破坏性的事之前，先问自己一句："坏了我能退回来吗？"如果不能，就先备份。

```text
动手前：Copy / Backup / Snapshot
出错时：先停下，别让它继续乱改
恢复时：Rollback（退回上一版）→ Retry（重试）→ Resume（接着跑）
长期：  用 Git 管代码和文档的版本历史
```

### Mission M15：故意制造一个错误并让它修复

| 字段 | 内容 |
|------|------|
| Mission 名称 | 故意制造一个错误并让它修复 |
| 目标 | 完整走一遍"出错→停下→恢复→验证"的流程 |
| 难度 | L4 |
| 预计需要的 Agent 能力 | 文件读写、代码执行 |
| 输入材料 | 一个小项目文件夹 |
| 任务说明 | 1）先把整个项目复制一份备份；2）让 Agent 故意改错一个文件（比如把某个文案改坏）；3）让它定位错误并修复；4）用备份对照，确认它真的修好了，且没改坏别的 |
| 操作步骤 | 备份→制造错误→定位→修复→回归验证→对比备份 |
| 风险提示 | 这是练习，务必在副本上做，不要用真实项目 |
| 成功标准 | 错误被定位并修复；周边文件与备份一致；你能说清每一步发生了什么 |
| 失败案例 | 它修好了坏的，但改坏了另一个文件，且没发现 |
| 验证方式 | 和备份逐文件对比 |
| 进阶挑战 | 这次练习中引入 Git，把"改错前"和"修复后"各提交一次 |

### 最简单版本

**"动手前先复制一份。"** 就这一个习惯，能挡掉 PART 5 里一半的损失。

### 完整恢复工作流

```text
1. 发现异常 → 立刻打断 Agent，不要再让它继续；
2. 判断损失范围 → 它动了哪些文件、改坏了什么；
3. 退回安全状态 →
   - 有备份：用备份覆盖；
   - 有 Git：git 回到上一个 commit；
   - 都没有：评估能否手动修；
4. 定位原因 → 为什么会错（看是上面 5.1-5.20 哪一类）；
5. 修正做法 → 在任务书里加对应的预防条款；
6. 重新执行 → 从安全状态重新做，这次带着防护；
7. 记录 → 把这次失败和恢复写进自己的"踩坑笔记"，下次复用。
```

### 常见失败

1. **出事不打断**：让它"再试试"，结果越改越糟。
2. **没有备份就硬上**：覆盖了才发现退不回去。
3. **修好了不验证**：退完就交，没确认真的好了。
4. **不记录**：同样的坑第二次还踩。

### 如何验证

- 恢复后，产物和"上一个好版本"逐项对比；
- 关键功能重新测一遍；
- 确认没有引入新问题。

### 本章模板

```text
【破坏性操作前的安全检查】
在让 Agent 执行以下操作前：修改/删除/批量处理/覆盖/发布/支付
请先确认：
1. 我是否已经复制了一份备份？（Copy/Backup）
2. 这一步是 L 几风险？需不需要我批准？
3. 如果坏了，我能退回到哪里？
4. 失败后怎么 Resume？
以上任一项答不上来，就不要开始。
```

### 延伸资源

- Git 是零基础用户值得早学的一个工具：它本质是"带时间轴的备份"，LAB F 会带你从零用起来；
- 系统自带的"文件历史/以前的版本"、网盘的版本记录，都是零基础可用的 Snapshot；
- 定期（每天/每完成一个里程碑）把项目文件夹压缩备份一次，是最朴素也最有效的 Backup。

### 完成标准

遇到任何 Agent 出错，你能冷静地说出："先停下，我有备份，我们退回上一版，然后按刚才那条原因加个防护再来。"
