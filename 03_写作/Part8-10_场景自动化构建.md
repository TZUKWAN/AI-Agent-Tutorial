# PART 8：场景实验室

先导图：场景实验室导航（待插入 F16）

到这里，你已经学会怎么给 Agent 下任务、怎么管长任务、怎么判断它是不是真做对了、它会怎么失败，以及它由哪些零件组成。从这一部分开始，不再学"通用方法"，而是按专业挑一条路，把真事做一遍。

## 8.0 开工前先对齐三件事

**第一，所有场景都走同一条主线。** 不管你做学习、写综述、跑数据还是改软件，一个任务的生命周期都是：

```text
定义任务 → 准备材料 → 执行 → 观察中间结果 → 验证 → 修复 → 交付 → 沉淀成模板
```

每个 LAB 都是这条主线在一种职业场景里的具体走法。你不用背八个新词，只要在每一步问自己：我现在在哪一步、这一步该由 Agent 干还是我干、怎么算过。

**第二，每次复杂任务套 8 要素。** 目标 / 上下文（喂给它的材料与背景）/ 环境 / 权限 / 约束 / 过程 / 验收 / 交付。前面 Part 讲过，这里只提醒一句：验收必须写成能检查的句子，"做得好"不是验收。

**第三，四条铁律落到本场景。** 通用版是"写出来不等于做对、改了不等于修好、测了不等于全对、它说完成不等于真完成"。到了不同场景，换成各自的及格线：

| 版本 | 四句及格线 |
|------|-----------|
| 科研版 | 文献生成不等于文献真实；综述起草不等于结论成立；检索跑通不等于没有遗漏；它说"已核验引用"不等于真逐条打开过 |
| 数据版 | 代码写了不等于数算对了；动了数据不等于清洗完成；图生成了不等于关系成立；报告写"显著"不等于真显著 |
| 软件版 | 代码生成不等于功能完成；代码修改不等于 Bug 修复；测试通过不等于产品完全正确；Agent 声明完成不等于实际完成 |

后面每个 LAB 出现具体动作时，都可以回到这张表对照：我现在这条动作，对的是哪一句。

## 8.1 LAB 分级：不必做完七个才算学会

七个 LAB 对应七种典型职业场景，但不再平均用力。按三级挑：

| 级别 | LAB | 谁建议做 |
|------|-----|----------|
| 核心（所有人建议做） | A 学习、C Office、D 网络研究、G 日常效率 | 无论什么专业，这四条最高频 |
| 专业（按方向选） | B 科研、E 数据 | 走学术路线选 B，走实证/量化路线选 E，二选一或都做 |
| 进阶 | F 软件开发 | 对软件本身好奇、或想用 Agent 改真实项目的人再上 |

一句话：**做完一到两个 LAB 并沉淀成自己的模板，就算学会了；七个全看一遍而没一个走通，不算。** 难度沿用全书 L0 到 L7 刻度，每个 LAB 开头标出。

## LAB A：学习 Agent（核心）

### 解决什么问题

手里有一门课：大纲、一叠 PPT、四周后考试。把"从材料到会考试"交给 Agent，你做判断人和验收人。难度 L2 到 L5。

### 旧做法为什么不对

让 Agent 把 PPT 总结一遍、画张思维导图，这不叫学习——这叫它替你读了一遍。真正决定考试成绩的，是你能不能在合上材料时把东西**想起来**，而不是你看着材料觉得"懂了"。所以这个 LAB 的闭环围绕"提取"而不是"阅读"设计。

### 学习闭环（核心动作链）

按顺序走，缺一环效果大打折扣：

1. **学习材料**：把大纲、PPT、教材、往年题放进一个文件夹。
2. **先预测，再学**：每章开始前，让 Agent 先考你"你觉得这章会讲什么、你已经会什么"，你先猜。猜错的地方，正是后面要重点盯的缺口——这叫 retrieval practice（提取练习）的前置：先暴露你以为会、其实不会的东西。
3. **Agent 提问，学生回答**：让它一次问一题，你答，它判。不许你先翻书。
4. **诊断错误类型**：把你答错的题归三类——概念记混了、根本没学过、还是理解反了。这一步叫 misconception diagnosis（错误概念诊断），三类错法的补救完全不同。
5. **针对性补充**：记混的做对比表，没学过的回原文重读，理解反的单独讲一遍反例。不要三类错都用"再看一遍"糊弄。
6. **延迟一天再测**：今天答错过的题，第二天换个问法再考一次。当天答对了不算数，隔一天还能答对才是真记住。
7. **间隔复习**：把你答错的知识点排成 1 天、3 天、7 天、14 天的复测表——这就是 spaced repetition（间隔重复），比考前突击省一半时间。

### 逐步实操：拿一门课真做一遍

假设你手上是"机器学习导论"，大纲、12 张 PPT、两周后测验。按上面七步，第一天这么走：

1. 建材料文件夹：`course/` 下分 `outline.md`、`slides/`、`old_exam.pdf`，全部设成只读。
2. 先预测：对 Agent 说"第三章讲监督学习，我先猜它会讲线性回归和分类。你先别纠正，出三道题考我以为会的"。你先答，不许翻 PPT。
3. 它判卷：把答错的题记成 `errors.md`，每条标类型——记混了、没学过、还是理解反了。
4. 针对性补：记混的让它做对比表（线性回归 vs 逻辑回归）；没学过的让它回到 PPT 第几页重讲；理解反的让它单独给一个反例。
5. 延迟一天再测：第二天对它说"用昨天 `errors.md` 里的知识点，换个问法再考我"。
6. 排复测表：让它生成 `review_schedule.md`——错点 A 排第 1/3/7/14 天，错点 B 另排。
7. 每次出题必须带 PPT 出处：你验收时抽五个知识点，能在 PPT 上翻到原文对得上。

这七步跑通一次，就沉淀成你自己的"课程学习 Agent"指令模板，以后每门新课丢新材料进来照走。

### 完整学习闭环：7 天日程表

上面七步是动作链，真到日历上怎么排？以"机器学习导论、两周后测验"为例，把它落到连续 7 天，每天该做什么、产出什么、验收看什么，照表走：

| 天 | 上午（40 分钟） | 下午/晚上（20 分钟） | 当天产出 | 过线标准 |
|----|------------------|------------------------|----------|----------|
| 第 1 天 | 第 3 章：先预测（猜这章讲什么）→ Agent 出题 3 道，合书先答 → 它判卷 → 把错题按"记混/没学过/理解反"三类记入 `errors.md` | 针对性补：记混的做对比表，没学过的回 PPT 第几页，理解反的要一个反例 | `errors.md` 有 ≥3 条带类型的错点 | 抽 5 个知识点，每条都能指出 PPT 出处 |
| 第 2 天 | 延迟再测：把昨天 `errors.md` 的题换个问法重考，不许翻书 | 答对的划掉，答错的升级进下一轮复习表 | 复测记录追加到 `errors.md` | 昨天的错点今天换问法还能答对一半以上 |
| 第 3 天 | 第 4 章走同样闭环（预测→答→判→分类→补） | 第 1 天错点的第 3 天间隔复测 | 第 4 章新错点 + 第 1 天错点复测结果 | 第 1 天错点这次答对率再升 |
| 第 4 天 | 第 5 章闭环 | 第 2 天错点第 3 天复测；把前三章做一次"盲画框架图"（合书画三章逻辑线） | 一张盲画框架图 | 框架图缺的枝丫，就是还没记住的地方 |
| 第 5 天 | 第 6 章闭环 | 整理 `review_schedule.md`：把所有错点排 1/3/7/14 天，打印或置顶 | 间隔复习表成型 | 每个错点都有下一次复测日期 |
| 第 6 天 | 跨章混合考：Agent 从第 1 到 6 章随机抽 10 题，合书做 | 错题再分类，回 PPT 补 | 混合测成绩单 | 10 题对 7 题以上；错的都能定位到章 |
| 第 7 天 | 模拟测验：按往年题型出一套，计时做 | 对答案，把仍错的点单独列进"考前三天重点"清单 | 模拟卷 + 重点清单 | 模拟卷分数能预告真实测验分数 |

这张表的三个纪律：一是**当天答对不算数**，所有错点必须跨天复测，第 2/3/4 天的下午都是在还前几天的账；二是**错题按类型补救**，记混、没学过、理解反三种错法各走各的路，不许都用"再看一遍"；三是**出题必带 PPT 出处**，验收时你随手抽五个点翻原文，对不上就打回重出。

跑满这 7 天，你会得到三个可复用的东西：`errors.md` 的模板（以后每门课换皮用）、`review_schedule.md` 的排表逻辑、以及一份"我这门课到底哪里虚"的诚实清单。两周后的第 8 到 14 天，就只做一件事——按 `review_schedule.md` 到点复测，直到所有错点连续两次答对。

### 出题与验收纪律

- 它出的题重点考你第 2 步暴露的缺口，而不是 PPT 原文填空。
- 每个知识点后面必须标"来自第几张 PPT 第几页"，不许凭空补理论。
- 让它对照大纲列"大纲要求但 PPT 没讲清"的缺口清单，明确禁止它用常识补圆。
- 抽五个知识点翻 PPT 能对上；它出的题你不看答案先做，答案与原文一致。

### 最终沉淀

把上面七步写成你自己的指令模板：以后每门新课丢新材料进来，照走一遍。这就是课程学习 Agent。

### 卡住怎么办：学不进去和记不住

第一种卡点：**学不进去，坐 40 分钟还是在翻第一页。** 这不是 Agent 不够聪明，是节奏错了。把"先预测"那步单独拎出来做——别直接让它讲第三章，先逼自己合书写三句"我猜这章讲什么"，写完再让它对答案。人对"自己猜错的部分"注意力天然集中，比被动听它讲强十倍。还卡就把 40 分钟切成两段：20 分钟只做预测+答题，不看材料；中间起来走 5 分钟；后 20 分钟只回 PPT 补刚才答错的地方。一段段硬啃不如一段段考。

第二种卡点：**当时答对了，第二天换个问法又错。** 这不是你笨，是间隔还没到。当天答对不算数——这本来就是这个 LAB 的设计。翻 `review_schedule.md`，看这个错点排到了第几天复测，没到那天就先不管它；到了那天还错，就把它的间隔从 1/3/7/14 天改成 1/2/4/8 天，加密一轮。还不行就让 Agent 把这个知识点写成一个"反例题"（不是问"是什么"，而是给个错例让你挑哪错了），错例比正面题更能钉住概念。连续两次换问法都答对，才把它从复习表里划掉。

## LAB B：科研 Agent（专业）

先导图：科研 Agent 完整链路（待插入 F17）

这是全书最需要"一边用、一边守底线"的 LAB。科研的生命是真实：真实的文献、真实的数据、真实的方法。Agent 在这些环节的失效不是"做慢了"，而是"做假了"，而它做假时语气和做真时一模一样。

### 先分流：你做的是哪一类研究

不同研究类型，Agent 能帮的程度差很远。开工前先对号入座：

| 研究类型 | 长什么样 | Agent 帮到哪 | 人必须守什么 |
|----------|----------|--------------|--------------|
| 普通课程综述 | 课程要求的小综述 | 读文献、整理、起草 | 选题与结论 |
| Narrative review（叙述性综述） | 围绕一个题目讲故事 | 找文献、列观点、起草 | 脉络判断、立场 |
| Systematic review（系统综述） | 按预设计划全面检索、合并证据 | 执行检索、去重、初筛、填表 | protocol、纳入排除标准、最终判断 |
| Scoping review（范围综述） | 摸清一个领域"研究了什么、没研究什么" | 检索、分类、图谱 | 分类框架 |
| Bibliometric review（文献计量） | 用文献数据做共被引、共现分析 | 跑数据、画图 | 解释、结论 |
| Empirical study（实证研究） | 有数据、有假设、有分析 | 跑统计、画图、改语言 | 研究设计、数据、因果解释 |

多数人是 narrative 或课程综述；想发顶刊、要做 systematic review 的，下面这段单独看。

### 系统综述的五条硬骨架

如果你走 systematic review，这五条一个不能少，缺了就不叫系统综述：

1. **Protocol（预注册方案）**：动笔前先把"研究问题、检索库、检索词、纳入排除标准、提取表"写成一份方案并锁定。后面不许边做边改词——改了就破坏可重复。
2. **Search strategy（检索策略）**：中文词、英文词、同义词、缩写、每个库的检索式，逐条写下来存档。
3. **Inclusion / exclusion criteria（纳入排除标准）**：什么类型的研究算、什么不算，写成可判定的句子，不靠感觉。
4. **Screening（筛选）**：按题录去重 → 按摘要初筛 → 按全文复筛，每一步记录"筛掉多少、为什么"。理想是双人独立筛，至少你自己要复核 Agent 的初筛理由。
5. **PRISMA**：最后画一张文献筛选流程图（识别多少、去重后多少、筛掉多少、最终纳入多少），这是系统综述的标准交付物。

### 任务责任矩阵：谁干，谁必须负责

| 环节 | Agent 可执行 | 人必须负责 |
|------|--------------|------------|
| 选题 | 反问、列举争议 | 研究价值与学术判断 |
| 检索 | 按 strategy 跑、拉题录、去重 | 检索策略与库的选择 |
| 初筛 | 按 criteria 分类并给理由 | 边界案例的最终判定 |
| 精读 | 逐篇填文献卡片 | 理解与批判 |
| 证据矩阵 | 叠表、归纳脉络 | 矩阵是否真的支撑结论 |
| 写作 | 起草、改语言 | 每一句论断的负责 |
| 引用 | 列条目、排格式 | 逐条打开原文核对 |
| 分析 | 跑统计、画图 | 方法选择、因果解释 |

一句话：Agent 负责"读得多、排得齐、写得顺"，人负责"选得对、判得准、担得起"。

### 六条底线（本 LAB 及格线）

1. **学术诚信**：Agent 是助手不是作者。按你所在机构和目标期刊的要求，如实声明它参与了哪些环节。别拿"AI 检测工具抓不抓得到"当判据——那工具误报漏报都被反复讨论过；唯一可靠的底线是如实披露，并对每句结论负责。
2. **引用真实性**：它极擅长造"看起来完全真实"的引用。综述定稿前，逐条打开原文，打不开、查不到、对不上的一律删。
3. **使用边界**：找文献、读文献、整理矩阵、查格式、改语言、写代码可以；替你提核心论点、替你下结论、把没跑过的分析写成自己跑过的，越线。
4. **数据来源**：任何数字回到原始出处（统计局、世行、论文附表、问卷原始记录），不用二手转述，不许它"估"。
5. **方法透明**：用了什么方法、为什么、有什么局限，要能写清楚；你讲不明白的方法，要么真搞懂，要么别用。
6. **可复现**：数据、清洗步骤、分析代码、随机种子都留档，另一个人能跑出你论文里同一组数。

### 怎么查你学校 / 期刊的 AI 政策

不靠猜，去官方页面查。先定两个主体：你在读（或要毕业）的学校，和你要投稿的期刊——前者管学位论文与课程作业，后者管投稿稿件，规定可能不同。用搜索引擎直接搜官方页：学校搜"[学校英文名] generative AI policy / 研究生 生成式人工智能 学术规范"，优先 `.edu` 域名的研究生院或学术诚信办公室页面；期刊搜"[期刊名] author guidelines AI"、"[出版社名] editorial policies AI"，优先出版社作者指南。可查入口示例（政策会更新，用前自行打开确认最新版）：Elsevier 作者指南的 AI 说明页、Springer Nature 的 Editorial policies: AI and AI-assisted technologies 页、各高校研究生院"学术规范 / Use of Generative AI"专栏（如 MIT、Stanford、Oxford、清华、北大）。查到后把链接、访问日期、关键句存进自己的披露清单，投稿前再核对一次。

### 最终沉淀

产物：题录表、证据矩阵、综述初稿、引用核验清单、独立审稿意见（换一个不带写作上下文的对话只当审稿人挑刺）、披露声明草稿。验收：矩阵每行对应一篇你真读过的文献；抽十条论断各有矩阵支撑；抽十条引用逐条打开原文对得上；分析附代码与原始数值可复现。

### 方向性深度：两周跑一个 narrative review 的节奏

如果你是第一次走，别一上来就奔 systematic review。多数人是 narrative 或课程综述，给一个可照抄的两周节奏：

- **第 1-2 天：分流+选题。** 先回到上面分流表对号——你做的是哪一类。narrative review 不需要预注册 protocol，但要先和导师定"围绕哪条脉络讲故事"。
- **第 3-5 天：检索+拉题录。** 让 Agent 按你给的关键词跑检索、导出题录、去重；**但检索库和检索词是你定的**，它只执行。
- **第 6-8 天：精读+填卡片。** 逐篇读，每篇填一张文献卡片（研究问题/方法/结论/局限）。卡片它可以帮你排版，**理解和批判是你的**。
- **第 9-11 天：叠证据矩阵。** 把卡片叠成一张矩阵，归纳脉络。你要判断：这张矩阵真支撑你讲的故事吗？
- **第 12-13 天：起草+核验引用。** 它起草，你逐句负责；**每一条引用逐条打开原文**，打不开的一律删。
- **第 14 天：独立审稿+披露。** 新开一个不带写作上下文的对话，只让它当审稿人挑刺；再写一份披露声明。

每一步该 Agent 干还是你干，回到上面"任务责任矩阵"那一格——Agent 负责"读得多、排得齐、写得顺"，你负责"选得对、判得准、担得起"。

## LAB C：Office 三件套（核心）

### 一条总原则：一个数字只有一个源头

Office 场景最大的事故是"三套数"——Excel 一个数、Word 一个数、PPT 一个数。根治办法只有一条：**Excel 是 source of truth（事实底座），Word 和 PPT 只能引用它，不许各自重算。** 所有 Office 工作都按这条拆成 C1 / C2 / C3。

风险前提：Office 文档格式很脆，Agent 改 Word 会乱样式、改 Excel 会覆盖公式、做 PPT 会标错数。所有操作在副本上做，原始材料锁只读。

### C1 Excel：事实底座

链路：数据 → 质量 → 计算 → 表 → 图。

- 先报表的长相（行列数、每列类型），不许上来就画图。
- 写数据字典：每列什么意思、月还是年、税前还是税后；不确定的列列成问题问你，不替你猜。
- 质量清单：缺失、重复、明显录错（年龄 999、日期在未来）、单位是否统一，先列清单再动手。
- 在副本上清洗，每步说明理由。
- 计算结论每一个都要能点开单元格复核。

把"数据 → 质量 → 计算 → 表 → 图"这条链路落到鼠标和键盘上，以一份原始销售明细 `input_data.csv` 为例，一步一步怎么走：

**第 1 步：打开 Excel，建一个工作簿。** 打开 Excel，新建空白工作簿，按 `Ctrl+S` 立刻命名为 `sales_report.xlsx` 存到自己的项目文件夹。先别碰原始数据文件——原始 CSV 设成只读，后面所有操作都在这个新工作簿里做。

【截图占位：图 C1-1，空白工作簿刚建好，左上角已存为 sales_report.xlsx】

**第 2 步：导入原始数据。** 不要双击 CSV 直接让 Excel 打开（那样会在原文件上改）。正确做法：在新工作簿里点"数据"选项卡 → "自文本/CSV" → 选 `input_data.csv` → 预览确认列名和每列类型 → 点"加载"。这样原始 CSV 只读不动，数据进了工作簿第一张表。把这张表重命名为 `明细`。

【截图占位：图 C1-2，数据导入向导预览，能看到 15 行、各列名】

**第 3 步：让 Agent 先"报长相"，不许上来就算。** 对它说："先告诉我这张表有多少行多少列、每列是什么类型、哪几列可能有缺失"。它应该先返回一份长相清单（行数 15、列数 6、日期列/金额列/文本列各几个），而不是直接出汇总。这一步卡住它，是为了防止它在你都不知道数据长什么样时就替你算完。

【截图占位：图 C1-3，Agent 返回的"表长相"文字说明】

**第 4 步：写数据字典。** 新建第二张表，命名为 `数据字典`，一列写列名、一列写含义。比如"金额：含税销售额，单位元；日期：成交月，YYYY-MM；区域：销售大区"。遇到它拿不准的列（比如某列写着"金额A"），它应该列成问题问你，而不是替你猜。

【截图占位：图 C1-4，数据字典表，列名/含义两列】

**第 5 步：列质量清单，在副本上清洗。** 新建第三张表 `质量检查`，让它逐项报：缺失几行、重复几行、有没有越界（年龄 999、日期在未来）、单位是否统一。报完再动手洗——清洗在 `明细` 表的副本上做，原始导入那一份先留着。每删一行，让它在 `质量检查` 里记一句"删了第几行、为什么"。

【截图占位：图 C1-5，质量检查表：缺失/重复/越界/单位各一行计数】

**第 6 步：计算汇总，每个数都能点开单元格。** 新建 `区域汇总` 和 `产品汇总` 两张表，用数据透视表或 `SUMIF` 算。关键纪律：汇总表里的数必须是公式算出来的（点开单元格能看到 `=SUMIF(...)`），不许手输。算完立刻核一遍：区域汇总的总额、产品汇总的总额、`明细` 表的总额，三个必须相等。本案例三个数都应是 62,818.00 元。

【截图占位：图 C1-6，区域汇总表，点中一个合计单元格，编辑栏露出 SUMIF 公式】

**第 7 步：做表（格式化）。** 给三张汇总表套统一样式：表头加底色、金额列用千分位加两位小数、列宽自动调整、冻结首行。这步交给 Agent 批量做，但你抽查两张确认它只动了格式、没改数字。

【截图占位：图 C1-7，格式化后的区域汇总表】

**第 8 步：画图。** 选中 `产品汇总` 那张表 → 插入柱状图，横轴产品、纵轴金额；再给 `区域汇总` 插一张饼图。每张图下面加一句话标题，写清这张图说明什么、单位是什么。不要让它一张图画三个系列互相打架。

【截图占位：图 C1-8，柱状图"各产品销售额（元）"】

这八步走完，你手里应该有一个 `sales_report.xlsx`，里面至少四张表（明细、数据字典、区域汇总、产品汇总）加两张图。验收就一句话：随便点一个汇总数字，能顺着公式追到明细行；三个总额对得上；原始 CSV 没被改过。

### C2 Word：叙事表达

链路：数据 + 材料 → 结构 → 正文 → 表格 → 引用。

- 先盘点文件夹里有哪些 Word、各多长、大概讲什么，列清单给你确认。
- 先出结构（几章、每章讲什么），你点头再写正文。
- Word 里出现的每个数字，从 Excel 引用，不在 Word 里手输。
- 引用、参考文献按你学校/期刊格式排，排完抽查。

### C3 PPT：演示表达

链路：audience（给谁看）→ message（你要他记住哪一句）→ story（怎么讲）→ slide structure（每页结构）→ visual（怎么可视化）→ review（挑错）。

- 先定"这一页只让观众带走一个结论"，再排版，不堆字。
- 每个数字同样回到 Excel，不现编。
- 页数控制在十页左右，每页一个结论。

### 批量与模板

"一百个 Word 标题统一改宋体小四"这类活交给 Agent 最划算，但必须先拿三个文件试跑、你检查无误再批量——批量出错时错得也很整齐。固定模板给它，要求"只填内容、不动样式"。最后让它当挑错人：错别字、格式不统一、数字前后不一致、引用缺漏。

### 真实案例

见 `examples/labs/lab_c_office/`：输入 `input_data.csv`（15 行销售明细），运行 `python run_lab_c.py` 产出 `sales_report.xlsx`（明细/区域汇总/产品汇总三表）、`sales_report.docx`、`talking_points.md`。复算证据：Excel 区域/产品合计与 Word 总额均为 **62,818.00 元**，三方一致——这就是"一个数字一个源头"的落地。逐项验收见该目录 `CHECKLIST.md`。

### 逐步操作链（照着 lab_c_office 复现一遍）

1. 事实底座：`input_data.csv` 是 15 行销售明细，**全程只读**，脚本不写回它。
2. 跑脚本：`cd examples\labs\lab_c_office`，再 `python run_lab_c.py`。
3. 看产出：它应生成 `sales_report.xlsx`（明细/区域汇总/产品汇总三张表）、`sales_report.docx`、`talking_points.md`，运行日志落在 `lab_c.log`。
4. 验"一个数字一个源头"：打开 Excel，区域汇总与产品汇总都应是 **62,818.00 元**；打开 Word，报告里的总额也必须是 **62,818.00 元**——三方对得上才算过，任何一处手输了别的数都要打回。
5. 批量前先试三个：遇到"一百个 Word 统一改宋体小四"这类活，先拿三个文件试跑，你检查无误再批量——批量出错时错得也很整齐。
6. 让它当挑错人：查错别字、格式不统一、数字前后不一致、引用缺漏。
7. 逐项打勾：`CHECKLIST.md` 共 8 项验收（含"原始输入未被修改"），全过才算完。

### 卡住怎么办：公式报错和数据对不上

第一种卡点：**Excel 公式报错，#DIV/0!、#N/A、#REF! 满屏。** 先别让它"修公式"，先定位是哪一类错。`#DIV/0!` 是分母为零——某行金额被空字符串或 0 除了，让它在公式外套一层 `=IFERROR(原公式,0)` 或者先把空行筛掉；`#N/A` 是 VLOOKUP 没匹配上——多半是两边文本带空格、大小写不一致，让它先跑一遍 `=TRIM()` 清洗再匹配；`#REF!` 是它删了一列但公式还指着那列——这是最危险的，说明它改表结构时没同步改公式，立刻回到上一个备份，让它先把所有公式列出来再动表。修完每改一个公式，点一下编辑栏看它真的是公式而不是手输的数字——手输的数字下次一改源数据就对不上。

第二种卡点：**三个总额对不上，差了几十块。** 这是"一个数字一个源头"原则被破坏了。别让它"凑一凑"，按三步查：先在 `明细` 表最下面用 `=SUM(金额列)` 拿到底表总额；再分别看 `区域汇总` 和 `产品汇总` 的合计行，看哪个和底表不一样；对不上的那个汇总表，点开合计单元格看公式——是不是 `=SUMIF` 的范围没选全（漏了最后两行）、是不是把"退货"行也加进去了、是不是有一行被它手输了个数字而不是公式。差几十块这种小错，十有八九是某一行被手输覆盖了。找到那一行改回公式，三个总额立刻对齐。

## LAB D：网络研究 Agent（核心）

### 解决什么问题

写一份调查报告：一家公司、一项政策、一个行业、一个竞品。靠收藏夹攒链接，既慢又容易只看到愿意看的那几篇。最终项目：每条关键结论后面都挂着真实可打开的来源。难度 L3。

### 搜索策略八步

别上来就搜。按顺序走：

1. **问题拆解**：把"这家公司怎么样"拆成 5 到 8 个可回答的小问题（做什么、谁开的、规模、最近动作、负面/诉讼、行业位置）。
2. **查询式设计**：每个小问题设计多组查询——官方名和俗称、中文名和英文名、同一事实的不同说法。
3. **来源层级**：先排好哪类来源可信——官方原始出处（政府网站、公司公告、法院文书、论文原文）最高；行业报告次之；媒体报道当线索；自媒体和营销稿只当线索不当证据。
4. **时间范围**：政策、价格、数据类信息必须标"这是哪年的数据"，过期信息单独标注。
5. **回到原始来源**：媒体转述的数字，追到公告/原文再用。
6. **主动寻找反证**——这一步最关键，单独说。
7. **交叉验证**：同一事实至少两个独立来源对一遍；互相转载的不算两个来源。
8. **证据表**：从第一天建一张来源表（标题 / 网址 / 发布日期 / 访问日期 / 支撑了哪个结论），报告里每个关键结论都能在表里找到行。

八步是骨架，每步具体怎么动手？拿"调查某竞品公司 X"为例，逐步落到键盘上：

**第 1 步 问题拆解——怎么拆。** 别用"X 公司怎么样"这种大问题搜。拿一张纸，先逼自己写出"我要给老板交一份报告，他会问哪几件事"。一般拆成这几格：主营业务是什么、创始人与股权背景、营收/规模量级、最近一年的重大动作（融资/新品/裁员）、负面与诉讼、在行业里排第几。写到 `questions.md` 里，每条后面留空待填。拆不好的标志：搜出来全是广告稿、或者怎么都搜不到——说明你问的是个没法回答的模糊问题，回去重拆。

**第 2 步 查询式设计——怎么写查询式。** 每个小问题准备 2 到 3 组查询式，覆盖四种说法：官方全称（"X 科技股份有限公司"）、俗称/简称（"X 科技"）、英文名（"X Tech"）、同一事实的不同问法（"X 营收"和"X 年收入"、"X 融资"和"X 投资方"）。查询式里善用引号锁短语、用减号排除垃圾（`X 公司 -招聘 -博客`）。设计完先自己搜一遍试试，第一页全是招聘网站和软文的，说明这组词太泛，加限定词或换角度。

**第 3 步 排来源层级——哪类来源先信。** 建 `sources.md` 时就给每条来源打个等级标：一手（政府/监管网站、公司自己的公告与招股书、法院文书、论文原文）= 直接采信；二手（知名行业咨询机构报告、主流财经媒体）= 可作线索但要追一手；三手（自媒体、公众号、营销稿）= 只当"别人在说什么"，永远不当证据。写报告时，关键结论只挂一手和二手，三手内容最多写"坊间传闻"。

**第 4 步 标时间——怎么判断过没过期。** 每条数字后面必须手写它的年份和发布日期。营收数据超过两年、政策文件已被新文件取代、价格/市占率这类快变量，一律标注"截至 YYYY-MM"。发现一条"X 公司有 500 人"的说法，先看它哪年发的，三年前的数今天可能翻倍也可能裁完了。

**第 5 步 追原始来源——怎么追。** 媒体稿里写"据公告，X 去年营收 10 亿"，你别直接用这 10 亿。点它引的链接，找不到链接就自己去公司官网"投资者关系/公告"栏或证监会披露平台，搜"X 公司 年度报告"，翻到财报那一页，对一遍数字对不对。媒体漏小数点、把季度当全年的事天天发生，只有原始出处能救你。

**第 6 步 主动找反证——怎么搜相反的话。** 这一步是强制动作，不是可选项。专门另起一组查询，把你想问的每个正面结论配一个反面词：`X 公司 风险`、`X 公司 诉讼`、`X公司 裁员`、`X公司 处罚`、`X 差评`、`X 倒闭`、`X 欠债`。在裁判文书网、信用中国、企业信用信息公示系统这些官方负面库里单独搜一遍公司名。搜到反证就如实写进报告"风险"一节；一条都没搜到，也必须白纸黑字写一句"已按上述反面查询式检索，未发现公开负面记录"——这一句话本身就是证据，证明你真的找过。

**第 7 步 交叉验证——什么才算两个来源。** 同一条事实，找两个**独立**来源对一遍。判断独立的方法：这两个来源是不是都转自同一个公告？A 媒体写"据 B 报道"，B 又写"据 C 公告"——那其实只有 C 公告一个来源。真正两个来源是：公司年报写的数 + 第三方行业报告独立测出来的数，这种才算互证。互相转载、洗稿、矩阵号通发的，全算一个来源。

**第 8 步 建证据表——怎么记。** 从第一天就建 `sources.md`，列五栏：标题 / 网址 / 发布日期 / 访问日期 / 支撑了哪条结论。每读完一条来源立刻登记，别攒到最后回忆。写到报告正文时，每个关键结论后面挂一个证据表行号；写完倒查一遍：随机抽五条结论，五条都能在表里点开对应行，才算合格。表里查不到行的结论，一律删或改写。

### 主动找反证

人和 Agent 都有同一个毛病：搜"这个公司好不好"，会顺手只收集说好的。所以流程里**强制**加一步：每下一个重要结论之前，让 Agent 专门搜一组相反的查询——"公司名 + 风险 / 诉讼 / 争议 / 倒闭 / 差评 / 被处罚"，看有没有打脸的证据。找到反证就写进报告，找不到也要写一句"已检索反面来源，未发现"。报告里必须有一节"本报告未能核实的部分"，查不到就老实写"未找到可靠来源"，不许用流畅的话把空白填满。

### 验收

随机抽五条结论，每条都能点开来源且来源确实支持这句话；至少三条标注访问日期并能看出数据年份；有专门一节写未核实部分。

### 逐步实操：拿一家竞品公司真做一遍

目标是写一份"某竞品公司"的调查报告。把上面八步落成动作：

1. 拆问题：把"这家公司怎么样"拆成 6 个小问题（做什么/谁开的/规模/最近动作/负面诉讼/行业位置），先写进 `questions.md`。
2. 设计查询：每个小问题配 2 到 3 组查询——官方名+俗称、中文名+英文名、同一事实的不同说法。
3. 排来源层级：先定好哪类可信——官方原始出处最高，行业报告次之，媒体当线索，自媒体只当线索不当证据。
4. 标时间：每条数字都标"这是哪年的数据"，过期信息单独标注。
5. 追原始：媒体转述的数字，追到公告/原文再用，二手转述不落结论。
6. 找反证：专门搜一组"公司名+风险/诉讼/争议/差评/被处罚"，找到写进报告，找不到也写一句"已检索反面来源，未发现"。
7. 交叉验证：同一事实至少两个独立来源对一遍；互相转载的不算两个来源。
8. 建证据表：从第一天就建 `sources.md`（标题/网址/发布日期/访问日期/支撑了哪条结论），报告里每条关键结论都能在表里找到一行。

### 卡住怎么办：找不到来源和搜出来全是软文

第一种卡点：**关键问题怎么都搜不到一手来源。** 比如你要查"这家公司去年的研发投入"，官网只写"持续加大研发投入"，没有具体数字。这时候别让它"根据公开信息估算"——估出来的数就是编的。换三条路：一是去证监会/股转系统/交易所的披露平台，搜这家公司的年报、招股书、融资说明书，研发投入在财报附注里一定有；二是找第三方行业报告（券商研报、咨询机构），哪怕是二手的，至少它引用了原始出处，你顺着它的引用再追一手；三是直接在报告里写"截至 YYYY-MM，公开渠道未披露具体研发投入数字，仅知其为 X 行业头部公司"——查不到就老实写查不到，这比编一个数强一百倍。

第二种卡点：**搜出来全是软文和招聘稿，没有真东西。** 说明你的查询式太泛。三个动作：一是加排除词，`公司名 -招聘 -博客 -软文 -推广 -加盟`，把营销内容先滤掉；二是换角度搜，别搜"公司名 怎么样"，改搜"公司名 年报""公司名 处罚""公司名 融资""公司名 专利"——这些词出来的是硬材料；三是直接去官方负面库（信用中国、裁判文书网、企业信用信息公示系统）搜公司全称，那里出来的东西不会是软文。如果按上面三招搜完还是只有营销稿，说明这家公司要么太小、要么太新、要么太低调——这本身就是结论，写进报告"公开信息有限，多为品牌稿，未发现独立第三方深度报道"。

## LAB E：数据分析 Agent（专业）

先导图：数据分析流程（待插入 F18）

你有一份数据表，想知道里面说明什么。这个 LAB 分两层：E1 适合普通文科生做描述性分析，E2 适合硕博做研究型分析。先看自己落在哪层，别硬上 E2。

### E1 基础数据分析（普通文科生）

链路：读数据 → 数据字典 → 质量 → 清洗 → 描述统计 → 可视化 → 报告。

- 先报表的长相，不分析。
- 数据字典：每列什么意思，不确定的问你，不猜。
- 质量清单：缺失、重复、越界、单位，先列后洗，在副本上做，原始数据不动。
- 描述统计 + 可视化：每张图配一句"这张图想说明什么、坐标轴是什么、范围多少"。
- 报告：每个结论后面跟"用了哪些数据、在什么范围内成立"，范围外不说满。

### E2 研究型分析（硕博）

在 E1 基础上加一段真正的推断与建模：

- **先写假设**：你要检验什么？同一个数据集，回答不同问题用不同方法。
- **方法选择**：为什么用这个方法、它的假设是什么，讲清楚。
- **推断统计与模型**：凡是报"显著"，必须同时给代码和原始数值、p 值、样本量，不许只给一张图说显著。
- **Diagnostics（诊断）**：模型在样本上表现如何，残差、假设是否满足。
- **Robustness（稳健性）**：换一种做法、换一个样本，结论变不变。一变就变的"规律"不能当发现写。
- **Sensitivity（敏感性）**：关键参数/阈值动一动，结论稳不稳。
- **Reproducibility（可复现）**：清洗与分析代码、随机种子、数据说明一并留档，别人能跑出同一组数。

### 四条铁规矩（本 LAB 及格线）

一，不看图"猜数据"——差多少、p 值、样本量，必须有数。二，不编造统计结果——每个均值、比例、相关系数都要贴出可复算代码。三，代码可复现——今天跑和三个月后跑结果一样。四，指标定义明确——"活跃用户""高收入"第一次出现就写清怎么算、阈值多少，全文不变含义。

### 完成标准：E1 交什么，E2 交什么

- **E1 基础版（普通文科生）交六样**：数据字典、质量清单（缺失/重复/越界/单位各多少）、清洗后的数据、描述统计、每张图配一句"这图说明什么/坐标轴/范围"、一段"结论在什么范围内成立"的话。以 `lab_e_data/` 为证：`dirty_data.csv` 22 行里剔成 `cleaned_data.csv` **10 行**，收入均值恒为 **10,180.05 元**，年龄均值 31.1——这组数你今天跑和三个月后跑必须一样。
- **E2 研究版（硕博）在 E1 之上多交三样**：一段写清的假设、一段"为什么用这个方法+它的假设是什么"、以及**凡是报"显著"就必须同时给代码、原始数值、p 值、样本量**。再加三样留档：模型诊断（残差、假设是否满足）、稳健性（换个做法结论变不变）、可复现包（清洗与分析代码+随机种子+数据说明）。一变就变的"规律"不能当发现写。

### 真实案例

见 `examples/labs/lab_e_data/`：自建脏数据 `dirty_data.csv`（22 行，含缺失/越界/格式不一致三类），运行 `python run_lab_e.py` 产出 `cleaned_data.csv`、`quality_report.md`（数据字典+质量检查+剔除留痕）、`analysis_report.md`、`income_by_city.png`。复算证据：清洗后恒为 **10 行**，月收入均值恒为 **10,180.05 元**。逐项验收见 `CHECKLIST.md`。

## LAB F：不会编程也能开发软件（进阶）

先导图：软件开发 Agent 全流程（待插入 F19）

这是进阶 LAB，只建议对软件本身好奇、或真要拿 Agent 改一个真实项目的人做。教学目标说死：**借助 Agent 完成开发，不是从零教你编程。** 你练的是"甲方加验收员"那套动作——找项目、读说明、跑起来、提需求、验收、存版本；代码由 Agent 写，你负责看结果、判对错。某行代码你看不懂很正常，本 LAB 不要求你看懂，只要求你确认它跑出来的效果对不对。

### 主线：跟着一个真实项目走，做的时候再解释术语

不再一个名词一个名词地讲课。教程已经把一个真实开源项目 vendor 进了 `examples/labs/labf_project/repo/`——就是 [tartley/colorama](https://github.com/tartley/colorama)（BSD-3，纯标准库零依赖）。你跟着下面这条动作链走，术语在你真正遇到它时我才解释。先记住这一屏字，每一步都可能回头看：

```text
代码生成 ≠ 功能完成
代码修改 ≠ Bug 修复
测试通过 ≠ 产品完全正确
Agent 声明完成 ≠ 实际完成
```

**动作链（边做边懂词）：**

1. **Clone（克隆）到本地**：把 GitHub 上的项目完整下到你电脑，连版本历史一起拿下来（后面要靠它回退）。这一步你只要让 Agent 执行、自己不用敲命令。
2. **打开 README**：项目根目录那个说明文件，是它的使用说明书。让 Agent 读给你听：解决什么问题、要什么前提、怎么启动。README 写得烂、根本跑不起来的项目趁早换。
3. **跑一次，看它报错还是跑通**：在自己屏幕上亲眼看到窗口、网页或"运行成功"。Agent 说"应该能跑了"不算，你看到才算。跑不起来时，最常见的麻烦是 Dependency（依赖）——这个软件需要的"其他零件"没装好；把报错原样贴给 Agent 让它解决。
4. **找到 demo01 跑起来**：进入 `demos/`，先跑最简单的 `demo01.py`。这一步在本机已验证：`run_demo.log` 里颜色网格已正常输出。
5. **让 Agent 画一张"文件地图"**：你看不懂代码没关系，让它当翻译——主流程在哪、哪个文件控制那个按钮、哪几个文件以后最常改。这张图存下来，后面所有修改靠它定位。
6. **挑一个最小改动**：改文字、换颜色、加一句欢迎语都行，越小越好。别直接说"帮我改一下"，先让它把需求列成 Task List（碰哪个文件、改哪行、怎么验证），你觉得靠谱再动手。
7. **立刻在你自己的窗口看效果**：改一个东西就跑一次看一眼，不对就改回去。不要一口气改十处再跑——坏了你不知道是哪处弄坏的。
8. **亲手 Test（测试）**：你像真实用户一样点一点、试几种情况。它自己说"我测过了"不算，你点过了才算。本机这个改动对应 `test_smoke.py`，运行输出 `SMOKE OK`。
9. **回归测旧功能（Regression Test）**：改了新地方，把以前能用的老地方再试一遍——修好了水龙头，顺便看看马桶还冲不冲。Agent 很容易"修一个坏三个"。
10. **Git 存档（Commit）**：Git 是游戏存档系统，每完成一个能正常工作的小改动就存一次，写一句"这次改了什么"（"把 demo01 末尾加一行 banner"才是合格说明，"改了点东西"不是）。本机这次改动已本地 commit 为 `2874e5f`。

走到这里你就完整经历了"找到 → 跑起来 → 改一点 → 测一测 → 存版本"的本地闭环。再往后的词——Branch（平行修改线，放心折腾的安全区）、Push（上传到 GitHub，对外动作，先确认且不含密钥）、Pull Request（改完别人项目后礼貌申请合并）、Deployment（部署到别人能访问的地方）、Release（正式宣布版本发布）——等你真的要对外发时再查，现在不必背。

### 十步操作链的真实证据（每步对应一个文件）

这十步不是嘴上说说，`examples/labs/labf_project/` 里每一步都留下了实物证据，你照表核对：

## LAB G：个人工作台（核心）

### 收缩为一件事：统一 Inbox

前面几个 LAB 围着"一个具体任务"，这个 LAB 只围着你每天的杂事转，但只做一件事——**把 Email / Calendar / Tasks / Files / Notes 五个入口整理成一个统一 Inbox**。具体自动化（定时扫、自动发、自动归档）留给 PART 9，这里只解决"乱"。

### 怎么做

- **Email**：让它读收件箱，按"今天要回 / 这周处理 / 只是通知 / 垃圾"分四类，给需要回的起草草稿。起草可以，**发出去不行**（对外动作，必须你点）。
- **Calendar / Tasks**：把散落在备忘录、聊天、邮件里的事抽成一张待办清单，按时间和紧急度排好，每周一早上给你一份"这周做什么"。
- **Files**：让它把下载文件夹、桌面、截图文件夹按规则归一次档——这是 PART 1 那个 Mission 的长期版。
- **Notes**：把平时攒的笔记、读过的东西先堆进同一个 Inbox，定期让它去重、补标签。

### 成功标准

你能说出三件它每周替你省下的、具体发生的事；它起草的邮件和纪要你改两笔就能用，而不是重写；凡"发出去、存进去、公开"的动作，永远停在你这里等确认。

### 逐步实操：第一天就这么干

1. Email：让它读收件箱，按"今天要回/这周处理/只是通知/垃圾"分四类，给需要回的起草草稿。**起草可以，发出去不行**——对外动作必须你点。
2. Calendar/Tasks：把散在备忘录、聊天、邮件里的事抽成一张待办清单，按时间和紧急度排好，每周一早上给你一份"这周做什么"。
3. Files：让它把下载文件夹、桌面、截图文件夹按规则归一次档——这是 PART 1 那个 Mission 的长期版。
4. Notes：把平时攒的笔记、读过的东西先堆进同一个 Inbox，定期让它去重、补标签。
5. 跑一周后验收：对照成功标准——能说出三件它替你省下的事；草稿改两笔就能用；没有任何一封邮件是它替你发出去的。

### Inbox 整理第一周：每日操作清单

第一天那五步只是开头，真正把乱账理顺要一周。下面是第一周每天的具体动作，每天 15 到 20 分钟，按表走：

| 天 | 当日动作（15-20 分钟） | 当日必做 | 验收 |
|----|------------------------|----------|------|
| 第 1 天 | 建统一 Inbox：新建一个文件夹叫 `Inbox/`，下面分 `邮件/` `日程/` `文件/` `笔记/` 四个子目录。先不整理旧物，只建架子 | 架子建好，五个入口各归一位 | 五个乱入口都能在 `Inbox/` 下找到对应子目录 |
| 第 2 天 | Email 第一轮分类：让它读收件箱未处理邮件，按"今天要回/这周处理/只是通知/垃圾"分四类列给你看。你点头后，给"今天要回"的起草草稿 | 草稿起草好，但一封都不发 | 有一份分类清单；待发草稿都躺在草稿箱，没一封发出去 |
| 第 3 天 | Files 第一轮归档：让它把下载文件夹和桌面按"按类型+年月"归一次档（图片/文档/安装包/其他，再按月份分） | 桌面和下载清空，移到 `Inbox/文件/` | 桌面只剩回收站和此电脑；下载文件夹没有散文件 |
| 第 4 天 | Calendar/Tasks 抽清单：让它把散在聊天、备忘录、邮件里的事抽成一张待办清单，按"本周必做/本周可做/以后再说"分三档 | 抽出一份清单，不超过 15 条 | 每一条都能说出"谁、什么时候、要我做什么" |
| 第 5 天 | Notes 归集：把散落的笔记、微信收藏、读书划线全丢进 `Inbox/笔记/`，让它去重、补标签 | 一次性归集，不要求当天读 | 笔记不再散在五个 App 里，都在一个地方 |
| 第 6 天 | 邮件第二轮：处理第 2 天起草的草稿——你逐封看，"发"的点发送，"重写"的打回，"不回"的归档。顺便把这五天新到的邮件跑一遍分类 | 草稿清零 | 草稿箱空；没有它替你发出的信 |
| 第 7 天 | 周复盘：让它生成本周小结——你这五天收了多少邮件、回了多少、归了多少文件、清了多少待办；哪些动作你希望它下周自动做 | 写一份下周的自动化候选清单 | 你能说出三件它这周替你省下的具体事 |

第一周的纪律有三条：一是**只收不删**——归档是移动到 `Inbox/` 下，不是删掉旧物，理乱账第一周不许下删除键；二是**对外动作一律停手**——起草邮件、整理日程可以自动，"发送、删除、对外提交"这些动作第一周全由你亲手点，先把自动段和手动段的边界看清了，下周才好谈自动化；三是**每天只做当天那一格**——不要第一天就想把半年的文件全理完，那是第二周以后的事。第一周的唯一目标，是让"东西都有地方放"这件事先成立。

### 卡住怎么办：整理完又乱了和邮件处理不完

第一种卡点：**刚整理完一周，第二周桌面又堆满了。** 这不是失败，是你没给新东西设入口。乱的根源永远是"新进来的东西没有固定去处"。两个动作：一是在桌面和下载文件夹各建一个 `今日收件/` 文件夹，所有新下载、新截图、新存的文件一律先丢这里，不许直接散在桌面；二是每周五下班前花 10 分钟，把 `今日收件/` 里的东西归到 `Inbox/文件/` 对应的年月子目录——只做这一件事，不要顺手"顺便再整理一遍旧文件"。乱了就回到这个最小动作，别试图一次性把半年的账重理一遍，那只会让你更挫败。

第二种卡点：**邮件每天几十封，分类都分不完。** 别让它"把所有未读邮件都分类"——那是无底洞。改成三条规则：一是让它只处理"未读且发件人不在通讯录"的邮件，通讯录里的人你自己看；二是分类只分三档——"今天要回 / 这周处理 / 不用回"，别搞四档五档，档越多越分不完；三是"不用回"那档直接归档不进队列，"这周处理"那档攒到周五下午批量处理，"今天要回"才起草草稿等你批。每天真要你拍板的邮件不会超过 5 封——超过 5 封说明你的分类阈值太松，把"这周处理"那档再砍一半。

### PART 8 小结：怎么选路

按分级表挑，不必全做：本科生从 A 加 G 起步；要发论文走 B 主线，E 配数据分析、D 配查资料；做项目/创业/找实习选 C 加 D；对软件本身好奇再上 F。做完一个 LAB 别急着开下一个——先把跑通的流程存成自己的模板，这就是 PART 7 讲的 Reuse，也是 PART 9 要讲的"把它变成自动跑"的前提。

# PART 9：自动化与长期运行

先导图：自动化触发-条件-执行闭环（待插入 F21）

前八讲你做的每件事都是"你喊一声，Agent 动一次"。这一 Part 解决：有些事你不想每天喊。

## 从一个真实愿望拆开

不从术语讲起，从你每天真会想要的一件事开始：

> "每天早上自动检查 5 个网站，有重要变化才告诉我。"

这个愿望听起来是一句话，拆开来其实是六个问题。我们一个一个问，术语就在你需要它的时候出现：

**第一个问题：谁来启动它？** —— 到点了自己开始，这是 Trigger（触发）。它是闹钟：不响，一切静止；响了，后面才动。设计自动化第一句永远是"它凭什么开始"，写不清楚就会该动不动、不该乱动。

**第二个问题：什么时间启动？** —— 每天早上八点，这是 Schedule（定时）。定时任务最简单、最可预期，最大的坑是"雷打不动"：周末放假它也跑，节假日你不在它也跑，堆出一堆没人看的结果。所以定时必须和下一个条件配合。

（另一种启动不是到点，而是 Event（事件）：来新邮件、网页更新了、仓库收到新 PR，"有事才动"。技术上常用 Webhook——那个系统在事发生时自动往你指定地址推一条消息，不用你每五分钟去问一遍。重要事件流还要配一个定时兜底，防 Webhook 漏。）

**第三个问题：什么叫"重要变化"？** —— 抓了一批新信息，不能直接 whole batch 发给你。先过一道 Condition（条件）：和昨天存的版本比，有没有真变化？所谓重要是你事先定好的规则——出现我关注的关键词、数字变动超过某幅度、来了新的官方公告。有，才往下走；没有，这一轮静默结束，连通知都不发。条件越具体，你被打扰越少；最忌讳的条件是"有新内容就通知"——新内容天天有，等于没条件。

**第四个问题：它到底做什么？** —— 抓网页、读邮件、写摘要、更新表，这是 Action（动作）。每个动作都要有明确输入输出，跑一轮留一轮产物，不能"跑了但什么都没留下"。动作要分级：只读、搜索、在副本上分析可以全自动；要往外发、要改线上、要花钱的，不能放进全自动段。

**第五个问题：怎么告诉你？** —— Notification（通知）。三条原则：有价值才通知（"一切正常"发一次是礼貌，发十次你就会关掉整个通知）；通知短、带结论、告诉你下一步干什么；通道要对（要决策的推到你随时看的地方，纯摘要攒成每日一封，错误异常立刻推）。

**第六个问题：什么必须停下来等你批准？** —— Human Approval（人工审批），这是本 Part 最重要的一个问题。

## 人工审批：为什么不可省

自动化的可怕之处不在于它做错，而在于它"错得很有规律、而且停不下来"。它可以在你睡觉时，按错误判断把措辞不当的邮件发给客户、把没核完的数据贴到公开文档。一次错是事故，自动重复一百次错是灾难。

铁律：**凡是对外的、不可逆的、影响别人的动作，都必须经过人工审批。** 发邮件发帖——草稿自动生成，发送你点；覆盖文件、删数据、Git Push、改云端正式文档——自动生成改动，执行你确认；花钱、下单、改权限、对外提交——绝不自动化。只读、在副本上分析、写草稿、做摘要——可以自动跑。

审批不是"每一步都问你"，那样你比手动还累。把流水线分两段：全自动段负责读、想、起草、准备好；到"最后一脚"——发送、发布、提交——才停。你审的是成品不是过程。审批消息里必须写清：它打算干什么、依据是什么、点哪个按钮同意、点哪个拒绝。糊里糊涂的"请确认是否继续"等于没审。

## 两个真实流程怎么装

**流程一：每日信息监控（只读，全自动安全跑）**

```text
每天 08:00（Schedule）
   ↓
抓取关心的几个来源的新信息（Action）
   ↓
和昨天存的版本对比（Condition：有无真正重要变化）
   ↓
   ├─ 有变化 → 写摘要+变化点+来源 → 推给你（Notification）
   └─ 无变化 → 静默退出，不打扰
```

全程只读、不对外，所以不需要审批节点——这是全自动安全跑的典型。

**流程二：邮件分类与回复（有对外动作，必须停在审批）**

```text
收到新邮件（Event：Webhook 敲门）
   ↓
分类：需回复 / 仅通知 / 待办 / 垃圾
   ↓
提取待办归入清单；对"需回复"的起草草稿（Action，只起草不发送）
   ↓
停下来等你（Human Approval）
   ↓
   ├─ 你说"发" → 才发出去
   └─ 你说"重写/不回" → 重来或结束
```

读、分类、起草都是只读和本地动作，可自动跑；"发送"对外且收不回，必须停在审批。

### 逐零件拆解：把两个流程填到六个格子里

上面是流程图，真要装，得把每个零件具体填什么写死。以本教程两个可运行脚本为例，逐格填：

**流程一：每日信息监控（`examples/automation/daily_monitor.py`）——全程只读，全自动安全跑**

| 零件 | 这个流程里具体填什么 | 对应脚本里的实物 |
|---|---|---|
| Trigger | 到点自己开始，不靠人喊 | Windows 任务计划程序 `schtasks` |
| Schedule | 每天早上 8:00 | `/SC DAILY /ST 08:00` |
| Condition | 和昨日快照按 tag 对比，只有"今天有、昨天没有"的 Release 才算变化；首次运行只建基准不通知；没变化就静默退出 | `diff_new_releases()`、`is_first_run` 分支 |
| Action | 抓目标仓库的 Releases，只读 | `fetch_github_releases()` |
| Notification | 有变化才写一份变更摘要，没变化连通知都不发 | `write_report()` → `reports/change_*.md` |
| Human Approval | **不需要** | 全程不对外发任何消息，所以没有这一格 |

它的三分支写得很清楚：第一次跑，建基准、不通知；第二次没新 Release，静默退出；第三次检出新 Release，才写摘要。**这就是"宁可不推，不要刷屏"的代码化。**

**流程二：邮件分类与回复（`examples/automation/email_triage.py`）——有对外动作，必须停在审批**

| 零件 | 这个流程里具体填什么 | 对应脚本里的实物 |
|---|---|---|
| Trigger | 收到新邮件才动（事件驱动）；教学版先手动 `run` | `emails/` 目录里的新邮件文件 |
| Schedule | 不固定，随邮件来 | 无 |
| Condition | 按关键词分工作/个人/通知三类 | `classify()` |
| Action | 起草回复草稿、写进待办队列 | `draft_reply()` + 入 `pending.json` |
| Notification | 你随时 `list` 看队列 | `cmd_list()` |
| Human Approval | **停在这一格**：`approve` 才发，`reject` 就不发 | `cmd_approve()` / `cmd_reject()` |

安全设计是重点：`_try_send()` 里先查 `SMTP_HOST`/`SMTP_USER`/`SMTP_PASS` 三个环境变量——**没配齐凭据，它只把待发内容落进 `outbox.log`，永远不真发**。也就是说，哪怕你忘了设审批，缺凭据这道兜底也不会让它把邮件真发出去。真接你自己的收件箱，再把"读 `emails/` 目录"换成 IMAP 真实拉取，审批和"无凭据不真发"的设计原样保留。

## Agent 自动化和传统 RPA 的区别

新手最容易混这两个。把旧说法纠正一下：传统 RPA（机器人流程自动化）强调**预定义的确定性流程**——把操作一步步预先录好或编排好，机械重复；现代 RPA 其实也早已用上 selector（界面元素定位）、OCR（识别文字）、API 和规则引擎，不是只会"录鼠标"。但 RPA 的判断仍由人预先写死。

Agent 工作流的主要区别是：**把语言模型引入判断、规划和非结构化信息处理**。它看懂的是任务的意思（"我要找那个提交按钮、把这单办完"），不是屏幕上的像素；页面布局变了，它能自己再找路。代价是灵活性更高、输出更不可预测——所以对 Agent 自动化，人工审批节点比 RPA 时代更重要，不是更不重要。

自动化平台是把这些零件拼起来的现成工具，挑的时候看三点：支持哪些触发源、能不能中间插一个"等人批准"的节点、失败了有没有日志可查。

**把 daily_monitor.py 拆开看：每段代码在做什么**

这个脚本不长，但它把 PART 9 讲的 Trigger / Action / Condition / Notification 四个零件全落进了代码。从上到下分段看：

**第一段：开头文档字符串与导入。** 最顶上那个大段三引号注释，写明了两种模式（live 真联网、offline 教学自测）、各自的证据文件落在哪、怎么用。这就是前面说的"一份规则说明"——脚本自己把触发条件、动作、产物路径都写在头上，三个月后回来一看就懂。下面只 import 标准库（argparse 解析命令行、json 读写快照、logging 记日志、Path 处理路径），所以不需要 pip 装任何东西。

**第二段：路径与日志 `BASE_DIR` / `MODE_PATHS` / `_build_logger`。** `BASE_DIR` 用 `Path(__file__).resolve().parent` 取脚本自己所在目录——这很关键，意味着你把脚本挪到哪、任务计划从哪启动，它的产物永远落在脚本旁边，不会因为"当前工作目录不同"而把日志写到 C 盘根目录。`MODE_PATHS` 把 live 和 offline 两种模式的日志、快照、报告目录分开列，避免自测时把真监控的快照冲掉。`_build_logger` 同时往文件和屏幕写日志，时间戳加级别——这就是"运行记录"，失败了翻 `monitor.log` 就能看到哪一步出的事。

**第三段：抓数据 `fetch_github_releases`。** 这是 Action 零件。它拼出 GitHub API 地址 `https://api.github.com/repos/<repo>/releases?per_page=10`，带上 User-Agent 发 GET 请求，把返回的 JSON 里每一条 Release 抽成 `{tag, name, published_at, url}` 四个字段。注意它的错误处理：HTTP 403（限流）、网络超时这些异常都被接住，而且在抛出前先把"这次请求长什么样、返回了什么"存成 evidence——出了事不是一句"请求失败"，而是有现场。它还特意只返回结构干净的字段，不把整个 GitHub 原始 JSON 塞进状态里，这就是"动作要有明确输入输出"。

**第四段：离线样例 `_OFFLINE_SNAPSHOT_A` / `_OFFLINE_SNAPSHOT_B`。** A 是"昨天已有的两个版本"，B 比 A 多一条 v2.32.0。设计这两份假数据是为了不联网也能跑通全流程：拿 A 跑一轮是"没变化"，拿 B 跑一轮是"有变化"，两条分支都能在自己电脑上验证。教学脚本不能只有 happy path。

**第五段：快照读写与对比 `load_previous` / `save_current` / `diff_new_releases`。** 这是 Condition 零件的核心。`load_previous` 读昨天存的快照文件，文件不存在就返回空列表（这就是"第一次运行"的判断来源）。`save_current` 把今天抓到的结果写回去，作为明天的"昨天"。`diff_new_releases` 最关键：它把昨天所有 tag 放进一个集合，再扫今天的列表，只保留"今天有、昨天集合里没有"的——按 tag 判重，不是按发布时间，所以同一个版本号反复出现不会被当成新变化。这三行就是"和昨天比，有没有真变化"。

**第六段：写摘要 `write_report` / `save_http_evidence`。** 这是 Notification 零件。`write_report` 建 `reports/` 目录，用当前时间戳做文件名，把新增的每个 Release 写成"版本号/发布时间/链接"三行。注意文件名带时间戳——每次跑出来的报告不覆盖前一次，历史可追溯。`save_http_evidence` 只在 live 模式调用，把真实请求和返回存档，方便你以后核对"它当时到底抓到了什么"。

**第七段：主流程 `run`。** 这是把四个零件串起来的地方，三分支结构是整个脚本的灵魂：

1. 先抓数据（offline 用样例、live 调 API，抓失败直接记日志返回退出码 2，不让定时任务崩）。
2. 读昨天快照。`is_first_run = len(previous) == 0`——如果是第一次，**只存基准、不通知**，直接返回。这一行就是"宁可不推，不要刷屏"的代码化：第一天没有"昨天"可比，不能把今天抓到的一堆全当新东西推给你。
3. 算 `new_items`：空列表就静默退出（只在日志写一行"无新 Release"），非空才调 `write_report` 写摘要。
4. 无论有没有变化，最后都 `save_current` 刷新快照——这是个容易漏的细节：哪怕今天没新东西，也要把今天的状态存成新基准，否则明天一对比，今天这一轮等于白跑。

**第八段：命令行 `main`。** 用 argparse 定义 `--repo` `--mode` `--offline` `--update` 四个参数，把"监控哪个仓库、真跑还是自测、要不要模拟新版本"做成可调旋钮，不靠改代码换配置。最后 `raise SystemExit(main())` 把退出码交回系统——任务计划程序靠这个码判断这轮成功还是失败。

看懂这八段，你就看懂了一条真实自动化流水线的全部零件：日志负责可观测、抓取负责只读动作、快照负责记住昨天、diff 负责当条件、写报告负责通知、退出码负责让调度器知道成败。把 GitHub Releases 换成你关心的任何只读数据源（政府公告、竞品官网、论文库），骨架原样不动。

**案例二：邮件分类审批** —— `examples/automation/email_triage.py`，读 `emails/` 样例邮件分三类，给"工作/个人"起草回复，进 pending 队列停下等人批准：

```powershell
python email_triage.py run      # 分类+起草+入队
python email_triage.py list     # 看队列
python email_triage.py approve <id>   # 批准
python email_triage.py reject <id>     # 拒绝
```

安全设计是重点：默认不真发，待发内容只写进 `outbox.log`；只有你在环境变量里配齐 `SMTP_HOST` / `SMTP_USER` / `SMTP_PASS` 时 approve 才真的通过 SMTP 发信——没填凭据就永远不会真发。真接你自己的收件箱，需要按邮箱 IMAP 文档把"读 emails/ 目录"换成真实拉取，审批与"无凭据不真发"的设计原样保留。

**把邮件审批工作流的每一步走实：流程图对应的真实命令和状态**

上面那张流程图是骨架，落到 `email_triage.py` 上，每一步到底在敲什么命令、系统内部发生了什么、你应该看到什么，一步步说清：

```text
[1] run        扫描 emails/ 目录，对每封邮件：
                 parse_mail_file 抽出发件人/主题/正文
                 classify 按关键词打分，分出 工作/个人/通知
                 draft_reply 按类别写一段回复草稿
                 生成 id，写入 pending.json，状态=draft
        ↓
[2] list       你随时看 pending 队列：哪几封待审、分别是谁、什么类别
        ↓
[3] 你逐条做二选一：
     ├─ approve <id>  → _try_send 先查 SMTP 凭据：
     │                    没配齐 → 只写进 outbox.log，状态记为 approved，不真发
     │                    已配齐 → 真的用 SMTP 发出去，状态记为 sent
     └─ reject  <id>  → 状态直接记为 rejected，永远不再碰
```

逐格拆：

**第 1 格 Trigger 与 run。** 教学版的触发是手动跑 `python email_triage.py run`。它做的第一件事是确认 `emails/` 目录在不在、里面有没有 `.txt` 或 `.eml` 文件；空目录就直接退出不报错。然后它读 `pending.json`，把已经处理过的邮件文件名存进 `seen_files`——同一个文件不会被重复分类入队，这就是"幂等"：你跑十遍 run，已经审过的邮件不会再冒出来。

**第 2 格 classify 分类。** 它把主题和正文拼成一串，分别数 `WORK_KEYWORDS`（会议/报告/客户/合同/deadline……）、`PERSONAL_KEYWORDS`（生日/聚会/周末……）、`NOTICE_KEYWORDS`（noreply/发票/验证码/物流……）三组词各命中几次，命中最多的那类胜出；一个都没命中就归"通知"。这是确定性规则，不依赖大模型，所以你今天跑和三个月后跑，同一封邮件的分类不变——这就是可复现。

**第 3 格 draft_reply 起草。** 按类别套模板：工作类写"今天内梳理并回复进展"，个人类写"约个时间细聊"，通知类写"已归档无需回复"。真实项目里把这段换成大模型生成更自然，但教学版先用模板，是为了让你先看清"起草"和"发送"之间隔着一道闸。

**第 4 格 入队 pending.json。** 每封待回复的邮件生成一个 8 位 id，连同发件人、主题、类别、草稿、状态（`draft`）、时间一起写进 `pending.json`。这个文件就是"停在审批点"的实物——自动化到这里就停了，没有任何一封邮件被发出去。

**第 5 格 list 查看队列。** 跑 `python email_triage.py list`，它把队列按"ID / 状态 / 类别 / 发件人 | 主题"打印成一张表。你每天扫一眼这张表，就知道今天有几封要拍板。

**第 6 格 approve 批准。** 跑 `python email_triage.py approve <id>`。它先查这条 id 还在不在、当前状态是不是 `draft`——已经发过或拒绝过的不许重复审批，这是防"同一封邮件发两遍"。然后调 `_try_send`：这是整个工作流安全设计的命门，它先读 `SMTP_HOST` / `SMTP_USER` / `SMTP_PASS` 三个环境变量，**只要有一个没配，它就把"本应发出的邮件"完整写进 `outbox.log`，然后返回，绝不真发**。也就是说，哪怕你手滑点了 approve，只要你没设过邮箱密码，这封信就永远躺在日志里当证据，不会真飞出去。只有你真配齐了三个凭据，它才用 SMTP_SSL 465 端口登录并发送，状态记为 `sent`。

**第 7 格 reject 拒绝。** 跑 `python email_triage.py reject <id>`，状态直接改 `rejected`，记上拒绝时间。被拒绝的邮件不会被删，只是标记为"这封不回"，以后还能翻出来看——不删数据是这条流水线的纪律。

这条工作流和每日监控那条的根本区别就在第 6 格：每日监控全程只读，所以连审批点都不需要；邮件审批因为"发送"对外、收不回，所以必须把流水线切成"自动起草 + 手动放行"两段，而且放行那一段还藏着第二道保险（无凭据不真发）。你以后给自己装任何自动化，照这两段对照：只读的随便自动，对外的一律停在这一格。

## 两个工作流出错时怎么办：失败、重试、审批拒绝

上面讲的都是 happy path——数据源正常、分类正确、你点了 approve。真实跑起来一定会遇到三种意外，下面把两条流水线各自的失败分支写死。

### 每日监控：API 失败、重试逻辑、快照损坏

**API 失败怎么办。** 抓取那一步不是每次都成功——GitHub 限流、政府网站改版、网络抖动，都会让 `fetch_github_releases()` 抛异常。正确的处理是三档：第一档，网络超时或 5xx 错误，等 30 秒重试一次，再失败等 2 分钟再试一次，最多三次——这就是指数退避；第二档，403/429 限流，不要立刻重试，直接记日志"今日被限流，跳过本轮"，明天再跑，硬撞只会把你账号封更久；第三档，404 或返回结构变了（网站改版），这不是临时错，立刻推一条告警给你"目标页面结构变了，需要人工检查"，不要静默跳过——静默跳过你会以为"今天没新内容"，其实是它根本没抓到。

**重试逻辑写死在哪。** 别让它"遇到错误再想办法"。在 `fetch_github_releases()` 外面包一层重试装饰器，参数写死：最多 3 次、间隔 30s→120s→300s、只对网络错和 5xx 重试、对 4xx 不重试。每一次重试都写日志，包含第几次、等了多久、下一次为什么还试。这样三个月后你翻 `monitor.log`，能清楚看到"第几次失败后放弃的"。

**快照损坏怎么办。** 快照文件 `state.json` 是它"记着昨天"的唯一依据。两种损坏：一是写一半崩了，文件变成半截 JSON，下次读直接报错；二是快照被误删了。第一种，写文件时先写 `state.tmp`，写完再 `rename` 成 `state.json`——这叫原子写，写一半崩了最坏情况是 tmp 是坏的，正式文件还是上一次好的；第二种，启动时读不到快照就当成"第一次运行"，只建基准不通知，不要把今天抓到的全部当成新变化推给你。每周日自动把 `state.json` 复制一份到 `backups/state_YYYYMMDD.json`，坏了能从最近一周的备份恢复。

### 邮件审批：审批拒绝、重复邮件、错误分类

**审批拒绝后怎么办。** 你点了 reject，这条邮件的状态从 `draft` 变成 `rejected`，流程结束——但"结束"不是"丢掉"。正确做法：一是把你拒绝的理由写回 `pending.json`（比如"这封不用回，是广告"），下次它遇到类似邮件能自动归到"不用回"那档，不用你再拒一次；二是被拒绝的邮件不要从队列里删，标记成 rejected 留在记录里，你翻 list 时还能看到；三是同一发件人连续被你拒三次以上，下次他来邮件直接归"不用回"，不进审批队列——拒绝是教学，不是一次性动作。

**重复邮件怎么去重。** 同一个发件人十分钟内发了三封内容几乎一样的邮件，run 一次就会进三条待审，你批不过来。去重放在 classify 那一步：对同一发件人+同一主题+正文前 200 字做一个简单哈希，哈希相同的只留最早一条进队列，后面的标为"同线程重复，已合并"。线程内的回复也一样——你已经回过一封"收到，周五前给你"，对方又回了"好的谢谢"，这封不该再起草新草稿。去重记录写进 `seen_files`，重启后不重复处理。

**错误分类怎么纠正。** 它把一封"发票通知"错归成了"工作"，还起草了一封"今天内梳理回复进展"的草稿——这封根本不用回。纠正流程：你点 reject 时顺手补一句"这是通知类，不用回"；它下次 classify 时把这条反馈记进关键词表，`发票/账单/收据` 这类词下次直接归"通知"。每周日让它跑一次"本周分类回顾"：把本周被你 reject 的邮件按类别统计，看哪类错得最多——如果"通知"类老被错分成"工作"，说明关键词表里 `NOTICE_KEYWORDS` 漏了词，补进去。分类不是一次写死，是靠你每周的 reject 反馈慢慢调准的。

## 长期跑要维护的三样东西

重复工作流（Recurring Workflow）会记着上一轮干到哪、昨天抓的是什么。你要维护：一份规则说明（触发/条件/动作/审批点写清）、一份运行记录（每轮何时跑、结果、报错）、一份定期复核（每周或每月看一眼：通知还有价值吗、条件该调了吗、有没有哪轮悄悄失败）。自动化最大的隐患不在第一天，在第三个月——规则没人维护，它还按三个月前的标准天天跑。

## Mission

搭一条每周至少跑五天的流水线，跑满两周再评价。成功标准：连续两周你能说出它帮你抓住了哪几条本来会漏看的变化；同时这两周它没在没问你的情况下发出过任何对外消息。常见失败是条件太松、天天刷屏，修法是把"重要变化"门槛定更严，宁可不推，不要刷屏。

# PART 10：构建自己的 Agent（Build-along）

先导图：构建自己的 Agent 蓝图（待插入 F24）

这一部分只面向一类读者：你已经用 Agent 帮自己干了几个月真活，现在想"我能不能造一个专门服务我专业的 Agent"。没到这一步可以先跳过——它不影响你成为熟练用户。

先纠正一个最大的误解：**自己构建 Agent，不等于自己写 Agent 框架。** 从零写一个 Runtime 是几十人团队几年的活，不是你毕业项目的目标。你的目标是用现成零件，拼出一个真替你干活的东西。下面我们就从一个已经能跑的最小 Agent 开始，一步一步往里加东西。

## 从一个能运行的最小 Agent 开始

教程在 `examples/my-agent/` 放了一个最小但真实可运行的 Agent：纯 Python 标准库，不需要 API Key、不联网、不 pip 装任何东西。没有 Key 时它用确定性规则引擎跑——这正好让你先把零件结构看懂，以后接大模型只换大脑、不换骨架。

跟着下面 13 步走，每一步先做事，遇到的概念当场解释。

**Step 1：先跑起来。** 在该目录下依次跑：

```powershell
python test_agent.py    # 冒烟测试，应全部 PASS
python eval.py          # 评测，输出 X/X 通过
python agent.py         # 交互式和它对话
```

本机实测（2026-09-18，Python 3.14）：`test_agent.py` **14 项断言全 PASS**；`eval.py` 七个用例 7/7 通过；交互下查时间、做计算、读文件、危险动作请求人工批准均按预期。第一步什么都不用懂，先让它在你屏幕上活起来。

**Step 2：看 System Prompt。** 打开 `system_prompt.txt`。这是你给这个 Agent 的"岗位说明书"：它是谁、服务谁、不能做什么、按什么流程干活。前面 8 要素里的目标、约束、过程、验收，长期化之后就是 System Prompt。改这个文件，下次启动它就用新岗位说明。

**Step 3：看 Tool。** 打开 `tools.py`。它现在有四个工具：读文件、安全计算器、查时间、关键词检索笔记。你要让 Agent 能用一个工具，光说"你可以搜索"不够，得写清楚这个工具叫什么、要什么参数、什么时候用——这份填表式说明叫 Tool Schema；模型看到它才知道"这情况该调搜索"。模型不直接回答、而是输出"我调哪个工具、传什么参数"，再由程序去执行，这个机制叫 Function Calling。注意它的安全设计：计算器用 AST 白名单，`__import__('os')...` 这类注入被直接拒；读文件被限制在项目目录内，越界路径被拒。

**Step 4：看 State。** 看 `state.json` 和 `agent.py` 里的读写。State 是"这个任务现在干到哪了"——做到第几步、上一步结果是什么。它和 Memory 的区别：State 是这一件事的进度，任务结束就没用了；Memory 是跨任务长期攒的。对话历史就是 Context（上下文），模型一次能看的信息有上限，所以要做 Context Management：每轮只塞正好够用的，别一股脑全倒。

**Step 5：加一个 Skill。** 打开 `skills/summarize.md`。当你发现自己反复给 Agent 写同一套指令、同一套模板，就该沉淀成 Skill——一份说明文件加配套资产。这是最适合零基础起步的"自己开发"：你写的主要是文字和流程，不是代码。

**Step 6：加 Knowledge / RAG。** 看 `docs/note_*.md` 和 `tools.py` 里的 `search_notes`。材料太多塞不进上下文时，做法是先把材料存成库，每轮先检索出最相关的几段再让模型回答——这就是 RAG（检索增强生成）。诚实地说：本项目的检索是词频打分，不是向量/嵌入检索，这是教学简化。

**Step 7：加 Planner。** 打开 `pipeline.py`。Planner 负责把大任务拆成一步步小任务，强推理模型适合干这个。本项目的 Planner 是模板生成，不是 LLM 规划——这也是以后要换的地方。

**Step 8：加 Executor。** 同一个 `pipeline.py` 里，Planner 拆完的每一小步由 Executor 真正去干：搜、读、写、算。执行可以用快一点、便宜一点的模型，因为它干的是执行不是思考。

**Step 9：加 Evaluator。** 还是 `pipeline.py`：每干完一步，Evaluator 检查结果合不合格、要不要重来。用一个独立的"挑刺角色"，往往比让干活的人自己评价自己可靠——这正是 PART 4 讲的独立审查。本项目用确定性断言做判断。

**Step 10：加 Approval。** 在 `agent.py` 里找 `_ask_approval`。遇到"删除 / 发送 / 覆盖"类危险动作，它会停下来问你 y/N。这就是 Human-in-the-loop：关键节点等人确认。设计自己的 Agent 时，第一件事就是标好哪些节点必须等人。

**Step 11：看 Logs。** 打开 `agent.log`。你的 Agent 跑起来之后，你得能看见它每一轮干了什么：调了哪个工具、给了什么参数、拿到什么结果、为什么这步这么决定——这叫 Observability（可观测性）。没有日志，它出错你只能瞎猜。

**Step 12：跑 Tests。** 回到 `test_agent.py`。它替你用一用、看它是不是按你想的工作。你是零基础，但你正好是最好的真实用户测试员。它自己说"我测过了"不算，你跑过了才算。

**Step 13：跑 Eval。** 跑 `eval.py`。怎么知道它做得好不好？不能靠感觉。准备一组固定测试用例（十到二十个典型任务），每次改完它都跑一遍，看哪些过了、哪些退化——这就是 Evaluation，也是 LAB F 的回归测试，对象换成了你自己的 Agent。

### 十三步再补一层：每步在做什么、为什么、做完该看到什么、常踩什么坑

上面十三步讲了"是什么"和代码片段，这一层讲"为什么要这一步、做完眼睛该看到什么、新手最常在哪摔"。按步看：

**Step 1 先跑起来。** 在做什么：不读代码，直接把三个脚本跑一遍，让 Agent 在你屏幕上活过来。为什么需要：后面十二步都在这个能跑的系统上改，你连它现在长什么样都没见过，改就是盲改。做完应看到什么：`test_agent.py` 全 PASS、`eval.py` 出 X/X、`agent.py` 能和你对话。常见坑：跑 `python` 提示"不是内部或外部命令"——说明 Python 没装或没进 PATH，去装 Python 并在安装界面勾"Add to PATH"，别先怀疑代码；报"ModuleNotFoundError"——纯标准库项目不该缺包，先确认你是不是在 `examples/my-agent/` 目录里跑的，路径不对会找不到文件。

**Step 2 看 System Prompt。** 在做什么：打开 `system_prompt.txt` 看这份"岗位说明书"。为什么需要：Agent 的一切行为边界都从这五句话来，你以后调它，九成改动是改这里，不是改代码。做完应看到什么：它清楚写着这个 Agent 是谁、能干哪三件事、什么必须先问你。常见坑：改完 Prompt 不重启就试——脚本是启动时读文件的，改完要重新跑 `agent.py` 才生效；或者改得太长把岗位说明写成一整本手册，模型抓不住重点，保持五行以内。

**Step 3 看 Tool。** 在做什么：打开 `tools.py`，看四个工具各自的 Schema 怎么写、白名单怎么拦注入。为什么需要：你以后加任何能力，都是照着这个 Schema 再写一个工具函数，再注册进 TOOLS 字典。做完应看到什么：计算器拒绝 `__import__`、读文件不许跳出项目目录。常见坑：新工具加进 TOOLS 字典却忘了写 Schema 描述——模型看到了工具名但不知道什么时候用，结果永远不调；或者计算器忘了 AST 白名单，直接 `eval` 字符串，那就是给自己留了个后门。

**Step 4 看 State。** 在做什么：看 `state.json` 和 `agent.py` 怎么读写它。为什么需要：这是"崩了能从第 8 轮接着来"的关键，也是你调试时看"它到底记到哪了"的入口。做完应看到什么：`state.json` 里有 task_status、turns、last_message 三个字段。常见坑：把 State 和 Memory 搞混——State 是这一件事的进度，任务结束就该清空；你把跨任务的长期记忆也塞进 State，文件会越长越乱；或者写 State 时忘了原子写，中途崩了把 `state.json` 写坏，下次启动读不出来。

**Step 5 加 Skill。** 在做什么：看 `skills/summarize.md` 怎么写成一份带 frontmatter 的说明文件。为什么需要：这是最适合零基础的"自己开发"——你写的是文字和流程，不是代码。做完应看到什么：`agent.py` 启动时把 `skills/*.md` 都扫进了上下文。常见坑：Skill 写得像散文没有操作步骤——模型照着做时抓不到动作；或者 frontmatter 格式写错（name/description 冒号后缺空格），`_load_skills` 解析不出来，这个 Skill 就静默失效了。

**Step 6 加 Knowledge/RAG。** 在做什么：看 `docs/note_*.md` 怎么被 `search_notes` 检索出来喂给模型。为什么需要：材料一多，全文塞进上下文既超长度又费钱，先检索再回答是必经之路。做完应看到什么：问"工具和安全"，它返回命中最相关的两三篇笔记。常见坑：以为检索出来的就是准确答案——词频打分只是教学简化，同义词、近义词它不认识；或者把没整理的原始材料全丢进 docs 让它检索，结果检索到一堆噪声，相关性反而更差。

**Step 7 加 Planner。** 在做什么：看 `pipeline.py` 怎么把"计算 1+2*3"拆成一步调 calculator。为什么需要：大任务必须先拆成小步再执行，一步一步来才好检查。做完应看到什么：plan 返回一个 step 列表，每步写明调哪个工具、传什么参。常见坑：模板匹配太死——本项目是正则匹配"计算…"，换个问法它就拆不出来，这是教学简化的已知边界，以后换 LLM 规划；或者拆得太粗，一步里塞了五件事，出错时不知道是哪件错的。

**Step 8 加 Executor。** 在做什么：看 `pipeline.py` 怎么把 Planner 拆的每一步真的调工具跑掉。为什么需要：拆完不执行等于没拆；执行和思考分开，是为了思考用贵模型、执行用便宜模型。做完应看到什么：step 列表里每一步都有真实输出。常见坑：某一步工具报错，Executor 不中断继续往下跑，结果后面所有步骤都基于错的输入——执行时每步必须接住错误，失败就停。

**Step 9 加 Evaluator。** 在做什么：看 `_assert_one` 怎么用确定性断言挑 Executor 的错。为什么需要：干活的人不能自己给自己打分，独立挑刺这一步，是 PART 4 独立审查的落地。做完应看到什么：断言不通过就返回 False，触发重来。常见坑：断言写得太宽（"包含数字"就算过），错结果也能蒙混；或者让干活的同一个模型既执行又评价——自己夸自己，等于没评。

**Step 10 加 Approval。** 在做什么：看 `_ask_approval` 怎么在危险动作前停下问 y/N。为什么需要：删除、发送、覆盖这些不可逆动作，必须有人点一下，这是 Human-in-the-loop 的底线。做完应看到什么：你说"删除 config.bak"，它停下来问，你输 n 它就不删。常见坑：把审批列表写漏——DANGEROUS_PATTERNS 里没列"清空"，它碰到"清空回收站"就直接动手了；或者审批提示只写"是否继续"，你根本不知道它要干什么，那这道审批等于没设。

**Step 11 看 Logs。** 在做什么：打开 `agent.log` 看它每一轮干了什么。为什么需要：没有日志，它出错你只能瞎猜；有日志，你能指着某一行说"它这一步调错工具了"。做完应看到什么：每轮调了哪个工具、传了什么参、拿到什么结果、审批是通过还是拒绝。常见坑：只记"发生了什么"不记"为什么这么决定"——日志缺了决策理由，事后还是查不明白；或者日志里明文写了密钥，这是安全事故，日志文件要扫敏感字段。

**Step 12 跑 Tests。** 在做什么：跑 `test_agent.py`，看 14 条断言有没有全过。为什么需要：你是最好的真实用户测试员，它自己说"我测过了"不算。做完应看到什么：全 PASS；改坏了立刻 FAIL 并退出。常见坑：改完代码不跑测试就往下走——这就是回归 bug 溜进来的方式；或者测试只测 happy path，不测"它该不该拒绝危险动作"这种反例。

**Step 13 跑 Eval。** 在做什么：跑 `eval.py`，用固定十到二十个用例看哪些过了、哪些退化。为什么需要：测试是"这一处对不对"，评测是"整体水平掉没掉"，每次改完都跑一遍才能放心。做完应看到什么：一个 X/X 的分数，并且比上次没退步。常见坑：评测集半年不更新——Agent 升级了、任务变了，老用例不再代表真实场景；或者只看总分不看哪条退化——总分没变但某条关键用例挂了，那就是真退步。

这十三步的常见坑归结成一句话：每一步做完都要"亲眼看到对的东西"，而不是"它说做完了"。Step 1 看 PASS、Step 3 看拒绝注入、Step 10 看它真停下来问、Step 11 看日志真记了——你亲眼核对的那一眼，就是 Agent 时代你和"它说完成"之间唯一的护城河。

### 十三步读者自检：每步亲手做一次，常见报错对照

上面讲的是"为什么"，这一节给你一张可以照着敲的自检表。每步都有一个"你亲手做一次"的动作和一个"看到什么才算过"的判据，外加新手最常遇到的报错和处理办法。

**Step 1 先跑起来。** 你亲手做：在 `examples/my-agent/` 目录下依次敲 `python test_agent.py`、`python eval.py`、`python agent.py`，三个窗口都看一眼。看到什么才算过：测试全 PASS、评测出 X/X、交互能回话。常见报错对照：敲 `python` 提示"不是内部或外部命令"——Python 没装或没进 PATH，去 python.org 下载安装包，安装时勾"Add Python to PATH"；提示"can't open file 'test_agent.py'"——你不在 `examples/my-agent/` 目录里，先 `cd` 进去；报 `SyntaxError`——你的 Python 版本太老，本项目要 3.10 以上。

**Step 2 看 System Prompt。** 你亲手做：打开 `system_prompt.txt`，把"回答要短、要直接"改成"回答要带例子"，存盘，重新跑 `agent.py`，问它一个问题，看它是不是真的开始带例子了。看到什么才算过：改完重启后行为真的变了。常见报错对照：改完不重启就试——脚本启动时读一次文件，运行中改不生效；改完重启后行为没变——检查你是不是改对了文件，`system_prompt.txt` 要在 `examples/my-agent/` 根目录，不是在别的子目录；改完启动报错——多半是引号或括号没配对，把你刚加的那句删掉再试。

**Step 3 看 Tool。** 你亲手做：在交互里输入"计算 `__import__('os').system('dir')`"，看它是不是拒绝；再输入"读文件 `../../etc/passwd`"，看它是不是也拒绝。看到什么才算过：两个危险输入都被拒，正常计算和读项目内文件能用。常见报错对照：计算器报"表达式只允许数字和运算符"——你输了字母或函数，这是白名单在拦，不是 bug；读文件报"越界"——你让它读项目外的文件，这是安全设计；新写的工具加进去后它永远不调——你忘了在 TOOLS 字典里写 Schema 描述，模型不知道什么时候用。

**Step 4 看 State。** 你亲手做：跑两轮对话后打开 `state.json`，看 `turns` 是不是从 0 涨到了 2、`last_message` 是不是你最后那句；然后手动把 `state.json` 删掉，重启 `agent.py`，看它是不是从 0 开始。看到什么才算过：对话真的被记下来、删掉后真的重置。常见报错对照：启动报"JSONDecodeError"——`state.json` 写坏了，删掉它重启就重建；`state.json` 越来越大——你把跨任务的长期记忆也塞进去了，State 只存当前任务进度；改完 `state.json` 没重启——运行中改不生效。

**Step 5 加 Skill。** 你亲手做：在 `skills/` 下新建一个 `my_skill.md`，照 `summarize.md` 的 frontmatter 格式写一份，重启 `agent.py`，问它"你现在有哪些 Skill"，看它是不是把你的新 Skill 列出来了。看到什么才算过：新 Skill 被 `_load_skills()` 扫到、列在它的可用清单里。常见报错对照：新 Skill 没被加载——frontmatter 里 `name:` 和 `description:` 冒号后必须有空格，格式不对解析器跳过；写了 Skill 但它不用——`description` 没写清"什么情况下用"，模型看不到调用时机；Skill 写得像散文——它照着做时抓不到动作，要写成一步一步的动词句。

**Step 6 加 Knowledge/RAG。** 你亲手做：在 `docs/` 下新建一篇 `note_test.md`，写一句话"这是一个关于咖啡机的测试笔记"，重启后问它"咖啡机怎么用"，看 `search_notes` 是不是把这篇笔记返回了。看到什么才算过：你的新笔记真的被检索到、出现在上下文里。常见报错对照：新笔记搜不到——词频打分靠关键词匹配，你问"咖啡机"但笔记里写的是"滴滤壶"，同义词对不上；搜出来一堆无关笔记——你往 docs 里丢了没整理的原始材料，检索噪声太大；检索结果 relevance 很差——这是教学简化的已知边界，本项目不用向量检索。

**Step 7 加 Planner。** 你亲手做：在交互里说"计算 1+2*3"，看它是不是先把这句话拆成一步"调 calculator、传 1+2*3"再执行；再说"帮我查一下今天天气"，看它拆不出来（本项目 Planner 只认计算）。看到什么才算过：能拆的真拆了、不能拆的老实说不行。常见报错对照：换个问法它就拆不出来——"帮我算一下一加二乘三"这种中文写法模板匹配漏了，这是教学简化；拆出来的步太多——一步里塞了五件事，出错时不知道是哪件；拆完不执行——Planner 和 Executor 没接上，检查 `pipeline.py` 里 `plan()` 的返回值有没有传给 `execute()`。

**Step 8 加 Executor。** 你亲手做：故意把 Planner 拆出的某一步工具名写错（比如把 `calculator` 写成 `calc`），看 Executor 是不是报错停下，而不是硬着头皮往下跑。看到什么才算过：某步工具不存在时立刻报错、不继续。常见报错对照：工具报错后它继续往下跑——Executor 没接住异常，后面所有步骤都基于错的输入；某步返回空——工具函数没 return，检查 `tools.py`；Executor 调工具时参数传错——Planner 拆出来的 arg 格式和工具函数要的参数对不上。

**Step 9 加 Evaluator。** 你亲手做：在 `pipeline.py` 的评测用例里，把 calculator 那条的期望值从 14 改成 99，跑 `eval.py`，看它是不是真的 FAIL 并报"expected 99, got 14"。看到什么才算过：故意改错后评测真的变红、不是永远绿。常见报错对照：评测永远 PASS 不管你怎么改——断言写得太宽（"包含数字"就算过），错结果也能蒙混；改完不跑 eval 就往下走——回归 bug 就是这么溜进来的；让干活的同一个模型既执行又评价——自己夸自己，等于没评。

**Step 10 加 Approval。** 你亲手做：在交互里说"删除文件 config.bak"，看它是不是真的停下来问"批准？(y/N):"；输 n，看它是不是真的没删；再试一次输 y，看它是不是真的执行了。看到什么才算过：危险动作真的停下、按 y/N 分别走两条路。常见报错对照：它直接删了不问——`DANGEROUS_PATTERNS` 里没列你刚才那句话的关键词，比如漏了"清空"；审批提示只写"是否继续"——你根本不知道它要干什么，那这道审批等于没设；输了 y 它也不动——`_ask_approval` 的返回值没接到执行函数上。

**Step 11 看 Logs。** 你亲手做：跑三轮对话（一轮正常计算、一轮危险动作被拒、一轮危险动作被批），然后打开 `agent.log`，看这三件事是不是都各记了一行、时间戳和动作对不对得上。看到什么才算过：每轮的工具调用、参数、结果、审批决定都在日志里。常见报错对照：日志是空的——`_build_logger` 的文件路径没建目录，先 `mkdir logs`；日志里明文写了密码——这是安全事故，把敏感字段从日志里剔出去；日志只记"发生了什么"不记"为什么"——事后还是查不明白决策理由，补一句"为什么这么决定"。

**Step 12 跑 Tests。** 你亲手做：故意把 `tools.py` 里 calculator 函数的加法改成减法（把 `ast.Add` 对应的 `operator.add` 改成 `operator.sub`），跑 `test_agent.py`，看它是不是立刻 FAIL。看到什么才算过：你改坏一处，测试立刻红——这就是回归保护。常见报错对照：改完代码没跑测试就往下走——bug 就是这么溜进来的；测试全过但你手点发现不对——测试只测了 happy path，没测"它该不该拒绝危险动作"这种反例；测试跑得越来越久——你往 `test_agent.py` 里塞了太多用例，拆成单元测试和冒烟测试两层。

**Step 13 跑 Eval。** 你亲手做：把 `eval.py` 里某条用例的期望值改成错的，跑 `eval.py`，看总分是不是真的掉下来；改回来再跑，看分数是不是恢复。看到什么才算过：总分真的会随你改的用例上下浮动、不是永远 X/X。常见报错对照：总分三个月不变——评测集没更新，Agent 都换代了还在测老问题；总分没变但你知道某条功能坏了——你只看总分没看哪条退化，逐用例看明细；eval 跑出来 X/X 但真实用着不对——评测集太简单，加几个贴近你真实任务的用例。

## 回头一看：你已经用过哪些 Agent 概念

走完这 13 步，回头点一点你刚用过的概念。全书后面列过 23 个 Agent 零件，你在这个能跑的小 Agent 里其实已经亲手摸过其中一多半：System Prompt、Runtime、Tool Schema、Function Calling、Skill、Context Management、State、Memory、RAG、Planner、Executor、Evaluator、Sub-agent（派子任务）、Human-in-the-loop、Hooks（自动检查）、Sandbox（计算器沙箱/读文件限制）、Security（不写密钥、最小权限）、Observability（agent.log）、Evaluation（eval.py）、Deployment（怎么从"你电脑能跑"变成"日常能用"）……

剩下没在本项目里展开的——Plugin（比 Skill 更平台绑定）、MCP Server（把你自己的系统按标准暴露给任何支持 MCP 的 Agent，写一次到处能用）、API 设计——知道它们解决什么问题、什么时候需要，就够了，不必每个都自己实现。

## 零基础怎么迈第一步

正确顺序是反过来的：先挑一个现成平台或开源框架，把别人做好的 Runtime、工具调用、记忆管理直接拿来用；你真正要花心思的只有三样——写清楚 System Prompt（这个 Agent 到底服务什么、怎么干）、接好它要读的资料和要调的工具、设计好"怎么算干得好"的测试。框架会换、模型会升级，这三样不会变。

判断你有没有学会，标准很朴素：一个不懂技术的同学，拿着你写的说明书，能不能照着装好、跑起来、出一次合格结果；出了错，你能不能靠日志说出它错在哪一步。

## 毕业项目

走到这里，毕业项目是一件事：**设计、实现、测试并交付一个面向你自己专业的 Agent。** 交付物不是"能跑"四个字，而是六件套：

1. **真实任务**：一个你本专业每周都做、做得烦的活（文献研究、案例梳理、史料整理、宏观数据跟踪、调研、财务分析、课程学习……），别选"听起来酷但你自己不会用"的题。
2. **可运行 Agent**：按 8 要素把岗位书写清，配好它要读的资料和要调的工具，按 Planner–Executor–Evaluator 串起来。
3. **测试集**：十到二十个测试用例。
4. **Eval 报告**：每次改完用同一套用例跑，记录哪些过、哪些漏、哪些胡说，附回归对比。
5. **风险说明**：一份"它做不到什么、什么情况必须你来"的诚实清单——哪些动作必须人工批、它的边界在哪。
6. **真实用户试用**：找一个真实的人（同学、同事）真用一次，拿回反馈。

最后记全书的结论：Agent 的价值不在于它会说多少，而在于它在明确的目标、合适的工具、可控的权限和可靠的验证下，持续完成真实工作。你造出的这个 Agent，能不能让你下周还愿意用它、敢把真事交给它，就是毕业与否的唯一标准。
