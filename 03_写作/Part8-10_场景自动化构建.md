# PART 8：场景实验室

先导图：场景实验室导航（待插入 F16）

到这里，你已经学会了怎么给 Agent 下任务、怎么管长任务、怎么判断它是不是真做对了、它会怎么失败，以及它由哪些零件组成。从这一部分开始，我们不再学"通用方法"，而是进入"按专业挑一条路，把真事做一遍"。

先把三件事说清楚。

第一，本 Part 不要求你把 LAB A 到 LAB G 全部做完。七个实验室对应七种典型职业场景：学生做功课、研究生做科研、文职做 Office 报表、做调查写报告、跑数据、学软件开发、打理日常事务。你只需挑与自己专业和近期目标最相关的一到两个，做到"最终项目"那一步。贪多嚼不烂，把一条路走通，比每条路都看一遍教程有用得多。

第二，每个 LAB 都是同一个结构：一段 Mission 说明（做什么、多难、分几步、怎么算成），然后是操作要点，最后是"最终项目"。Mission 里的难度沿用全书 L0 到 L7 的刻度：L0 纯聊天，L1 单文件，L2 多文件，L3 联网加文件，L4 用工具或浏览器，L5 长任务，L6 自动化，L7 自己开发 Agent。

第三，也是最重要的——前面反复强调的四大铁律，到了场景里不是口号，而是每一步的检查动作：

- 代码生成不等于功能完成：Agent 写了一行代码、一段报告、一张表，都只是"写出来了"，不是"做对了"。
- 代码修改不等于 Bug 修复：Agent 说"我改好了"，要你自己跑一遍、看一遍才算数。
- 测试通过不等于产品完全正确：它跑通了你给的那个例子，不代表所有情况都对。
- Agent 声明完成不等于实际完成：它说"已完成"，你要拿出证据。

下面逐一来。

## LAB A：学习 Agent

### 这个 LAB 解决什么问题

你手里有一门课：一份课程大纲、一叠 PPT、一本教材，还有四周后的考试。以前的做法是自己逐页翻 PPT、画思维导图、考前突击背题。这个 LAB 要把"从材料到会考试"这条链路交给 Agent，你做判断人和验收人。

最终项目：搭一个"课程学习 Agent"，以后每门新课都能复用这套流程。

### Mission：课程学习全流程

- 名称：课程学习 Agent
- 目标：给定一门课的大纲和 PPT，产出知识结构、学习计划、自测题、错题分析和复习资料，形成可重复使用的工作流。
- 难度：L2 到 L5（前几步 L2 多文件，口试和错题分析属于 L5 长任务）。
- 需要的能力：读取 PDF/PPT 文件、长任务管理、要求它自我验证；不需要联网。
- 输入材料：课程大纲（一两页）、全部课件 PPT 或 PDF、教材电子版（可选）、往年题（可选）。
- 风险提示：Agent 会把它"以为你该知道"的常识当成课程内容，也会把 PPT 上一句话扩写成一段你老师根本没讲过的理论。所有知识点都必须回到课件原文核对。

### 分步骤怎么做

第一步，让 Agent 先读课程大纲，输出它对这门课的理解：这门课讲哪几大板块、每个板块多少学时、老师强调什么。这一步的目的不是要它总结，而是先看它有没有读错、读漏。读错了，后面全错。

第二步，让它逐份读 PPT，为每一章生成知识结构：一级概念、二级概念、概念之间的关系。要求它在每个知识点后面标注"来自第几张 PPT 第几页"。这个标注就是它的证据，不允许凭空补充。

第三步，找知识缺口。让它对照大纲和 PPT，列出"大纲里要求但 PPT 里没讲清楚"的条目。这一步很关键：Agent 读材料时倾向于"圆上"，把没讲到的地方用常识补全。你要明确禁止它补，只允许它列成"缺口清单"。

第四步，制定学习计划。让它按考试倒推日期，把缺口清单和知识点清单排成四周的计划，每天学什么、花多久、学完用什么方式自测。计划是给你执行的，不是给你欣赏的，所以要具体到天。

第五步，生成问题。让它从 PPT 原文出题：选择题、简答题、论述题都要，并附标准答案和"答案出处"。重点考那些它第三步标出的知识缺口。

第六步，口试。这是最像真学习的一步。你让 Agent 一次问你一个问题，你回答，它判断你答得对不对、漏了什么、有没有理解偏。它问完一轮，给你一份"你答错/答偏的点"清单。

第七步，分析错误。让它把你答错的点归成三类：是概念记混了、是根本没学过、还是理解反了。每一类给两到三个再练的题。

第八步，生成复习资料。基于错题清单，让它生成一页 A4 的考前速查表和十道压轴题。

第九步，把上面这套流程固定下来。你已经做过一遍，把每一步"你给它的指令、它该遵守的约束、每步产出什么文件"写成一份自己的模板。下一门课，把新材料丢进来，按模板走。这就是最终项目：课程学习 Agent。

### 成功标准

- 知识结构图里的每个一级概念都能在 PPT 里找到出处；随机抽五个知识点，翻 PPT 能对应上。
- 它出的题，你自己不看答案先做一遍，答案和 PPT 对得上。
- 口试一轮后，它给你的错题清单你逐条认可：确实是你不会的，而不是它挑刺挑出来的。
- 四周计划落到了天，而不是"第一周学前两章"这种空话。

### 常见失败

- 它把 PPT 里一页的标题扩写成一大段理论，你以为课上教了，其实没有。识别方法：抽查出处页码。
- 它出题太简单，全是 PPT 原文填空，测不出你懂没懂。改进：要求它出"用自己的话解释""两个概念区别是什么"这类题。
- 学习计划排得太满，两周后你就放弃了。改进：让它按你每天实际能学的时间排，并且预留一天机动。

### 旗舰项目模板：课程学习 Agent

把上面九步固化成一个可复用项目，以后每门新课照走一遍。

- 输入材料：一门课的课程大纲（一两页）、全部课件 PPT 或 PDF、教材电子版（可选）、往年题（可选）。
- 步骤：读大纲建立理解 → 逐章生成带页码标注的知识结构 → 列知识缺口清单 → 按考试倒推排学习计划 → 从原文出题 → 口试一轮 → 错题归类并出再练题 → 生成速查表与压轴题 → 把全流程写成自己的指令模板。
- 产物：知识结构图、缺口清单、按天学习计划、带答案出处的题库、错题分析、考前速查表一页、可复用的流程模板。
- 验收标准：随机抽五个知识点都能在 PPT 找到出处；它出的题你先做一遍、答案与原文对得上；错题清单你逐条认可；计划落到天而非"第一周学前两章"。

## LAB B：科研 Agent

先导图：科研 Agent 完整链路（待插入 F17）

这是全书最需要"一边用 Agent、一边守住底线"的 LAB。科研的生命是真实：真实的文献、真实的数据、真实的方法。Agent 在这些环节上的失效不是"做慢了"，而是"做假了"，而它做假的时候语气和做真的时候一模一样。所以这个 LAB 把完整科研链路拆开，同时把学术诚信单独拎出来讲。

最终项目：搭一条自己的科研工作流 Agent——以后任何一个选题，都能按这条流水线走一遍。

### 完整链路

```text
研究问题
→ 检索策略
→ 文献搜索
→ 去重
→ 筛选
→ 文献阅读
→ Evidence Matrix（证据矩阵）
→ 研究脉络
→ 文献综述
→ 理论框架
→ 研究设计
→ 数据
→ 分析
→ 可视化
→ 写作
→ 引用核验
→ 独立审计
→ 投稿准备
```

逐段说明它在干什么、你要盯什么。

研究问题阶段：让 Agent 帮你把"我想研究点什么"这个模糊念头收敛成一个可检验的问题。它擅长的是反问你：你到底关心哪个群体、哪个机制、什么时间范围。它不擅长替你决定研究价值——选题的学术判断必须是你和导师的。

检索策略阶段：先别搜。让它把检索词拆出来——中文关键词、英文关键词、同义词、缩写、要用的数据库名（知网、Web of Science、Google Scholar、PubMed 等按学科选）。检索策略写下来，后面每一步都按它执行，避免"边搜边改词"导致你都不知道自己到底搜了什么。

文献搜索与去重：它按策略去搜，把每一篇的题录（标题、作者、年份、出处、DOI）先拉成一张表。去重不是删重复条目那么简单，要它说明按什么字段判重、判掉了多少篇、剩下多少篇。

筛选：让它按"摘要里是否真的谈了这个问题"初筛，分成"必读/可略/不相关"三类，每篇给一句理由。理由必须能在摘要里找到依据。

文献阅读：不要让它一口气读完五十篇然后给你一个笼统综述。让它一篇一篇读，每篇填一张卡片：研究问题、方法、数据、核心发现、局限、与你的选题关系。这就是证据矩阵的雏形。

Evidence Matrix：把所有卡片叠成一张表，行是文献，列是"研究问题/理论视角/方法/样本/核心结论/与我研究的关系/可质疑之处"。这张表是你后面写综述和设计研究的底盘，也是你判断"这个领域到底干了什么、没干什么"的依据。

研究脉络：让它在证据矩阵上回答三个问题——这个领域是怎么一步步发展到今天的、有哪几条互相争论的线索、最近三年的新转向是什么。它说的每一条"脉络"，背后都要能在矩阵里找到两三篇文献支撑。

文献综述与理论框架：让它基于矩阵写综述初稿。这一步它写出来的东西"像论文"，但也最容易混入它自己的发挥。写作阶段的铁律是：每一个论断后面跟着它来自矩阵哪几行；找不到出处的论断，标成"待核实"，不许直接留在正文里。

研究设计、数据、分析、可视化：到了这里，Agent 能帮你想设计、帮你跑统计、帮你画图，但"用什么数据、数据怎么来的、样本怎么选的"必须由你定义清楚并能对人讲明白。统计结果一律要求它同时给出代码和原始数值，不许只给一张图说"显著"。

写作、引用核验、独立审计、投稿准备：写完之后，把引用核验单独成一步——它列的每一条文献，你打开原文核对作者、年份、出处、页码、DOI，凡是打不开、查不到、对不上的，一律删掉或换成真实存在的。再让一个与写稿时不同的模型（或同模型新对话，不带写作上下文）只当审稿人，挑问题。最后才是格式、期刊要求、cover letter。

### 必须单独守住的六条底线

这六条不是"注意事项"，是这个 LAB 的及格线，单独说。

第一，学术诚信。Agent 是助手不是作者。它帮你读、帮你整理、帮你起草，但研究问题、判断、结论由你负责。绝大多数期刊和学术机构对"AI 生成式工具"都有披露要求，你必须按你所在机构和目标期刊的规定如实声明它参与了哪些环节。这里要澄清一个常见误解：不要把"会不会被 AI 检测工具抓出来"当作是否越线的判据——AI 检测工具的误报和漏报都在文献里被反复讨论，它既不能证明你清白，也不能判定你违规；真正可靠的底线只有一条，就是按机构和期刊要求如实披露，并对自己写下的每一句结论负责。

第二，引用真实性。这是 Agent 最容易翻车的地方。它非常擅长造出"看起来完全真实"的引用：真实的作者、相近的年份、格式标准的 DOI、甚至通顺到像真论文的标题。你没有义务怀疑每一句话，但你有义务打开每一个引用。流程上强制自己：综述定稿前，逐条打开原文，打不开的一律删。

第三，AI 使用边界。让它做什么、不做什么，自己心里要有一条线。一般来说，帮你找文献、读文献、整理矩阵、查格式、改语言、做代码，是合理的；让它替你提出核心论点、替你下结论、替你伪造"我做过这个分析"，越线了。尤其要警惕：它没跑过的分析，不要在论文里写成自己跑过。

第四，数据来源。它给你的任何数字、任何"某国某年某指标"，都要能回到原始出处——国家统计局、世界银行、论文附表、问卷原始记录。不许用二手转述当一手数据，更不许它"估"一个数。

第五，方法透明性。你用了什么方法、为什么用这个方法、有什么局限，要能写清楚。Agent 很容易把方法写得"很高级但你自己讲不明白"——凡是你讲不明白的方法，要么真搞懂，要么别用。

第六，可复现性。把你的数据、清洗步骤、分析代码、随机种子都留好。理想状态下，另一个人拿到你的数据和代码，能跑出你论文里的同一组数。这既是学术规范，也是你防止自己"被 Agent 绕进去"的最好办法：结果能不能复现，一跑便知。

### 如何查找你目标学校 / 期刊的 AI 使用政策

"要披露"这件事不能靠猜，必须落到你自己所在机构和目标期刊的具体规定上。方法很简单，就是去官方页面搜，不要转述别人的二手说法。

第一步，确定两个主体：一是你在读（或要毕业）的学校，二是你准备投稿的期刊。学校管的是学位论文和课程作业，期刊管的是投稿稿件，两者规定可能不同，要分别查。

第二步，用搜索引擎直接搜官方页面。推荐关键词组合：

- 学校："[学校英文名] generative AI policy"、"[学校中文名] 研究生 生成式人工智能 学术规范"、"[学校英文名] graduate school AI use policy"。优先点开域名以 `.edu` 结尾的研究生院（graduate school）或学术诚信办公室（office of academic integrity）页面。
- 期刊："[期刊名] author guidelines AI"、"[出版社名] generative AI policy"。优先点开出版社作者指南（author instructions / guide for authors）页面。

第三步，几个可查的官方入口示例（核验日期：2026-09-18。政策会更新，使用前请自行打开确认最新版本）：

- Elsevier（爱思唯尔）作者指南中的"AI 与 AI-assisted technologies in scientific writing"说明页，搜"Elsevier author hub AI policy"。
- Springer Nature 的"Editorial policies: AI and AI-assisted technologies"说明页，搜"Springer Nature editorial policies AI"。
- 各高校研究生院官网的"学术规范 / Academic Integrity / Use of Generative AI"专栏，如 MIT、Stanford、Oxford、清华、北大的研究生院或教学发展中心页面。
- 国内可同时查学校研究生院官网发布的"研究生学位论文写作规范"及其中关于人工智能工具使用的说明。

第四步，把查到的规定存证。把官方页面链接、访问日期、原文关键句截图或另存一份，写进你自己的"披露清单"。投稿前再核对一次目标期刊的当前版本——政策可能在你改稿的几个月里更新。

### 四条真实性硬要求（本 LAB 的及格线）

在动用任何 Agent 之前，先把这四条写死在你的工作流里：

- 真实文献：综述里每一篇文献都必须是你亲自打开、读过的原文，不接受 Agent 报出但你没核实的条目。
- 真实数据：任何数字都要回到原始出处（统计局、世行、论文附表、问卷原始记录），不用二手转述，不许它"估"。
- 可追踪证据：证据矩阵里每一行文献、每一个论断，都能指出它来自哪篇的哪一页或哪张表。
- 可复现代码：清洗与分析代码、随机种子、数据说明一并留档，另一个人能跑出你论文里的同一组数。

### 成功标准

- 证据矩阵里每一行都对应一篇真实存在、你真的读过的文献。
- 综述里抽十条论断，每一条都能在矩阵里找到支撑文献；抽十条引用，逐条打开原文能对上。
- 你能向导师用十分钟讲清楚研究问题、方法、数据来源和局限。
- 你清楚地知道本稿里 Agent 参与了哪些环节，并已按要求准备披露。

### 旗舰项目模板：个人科研工作流 Agent

- 输入材料：一个具体研究问题、拟用数据库清单（知网 / Web of Science / Google Scholar / PubMed 等按学科选）、初版检索词表。
- 步骤：写检索策略 → 拉题录表并去重 → 摘要初筛分三类 → 逐篇填文献卡片 → 叠成 Evidence Matrix → 归纳研究脉络 → 基于矩阵写综述初稿 → 逐条核验引用 → 换对话当独立审稿人挑刺 → 按目标期刊和学校政策准备披露声明。
- 产物：题录表、证据矩阵、综述初稿、引用核验清单、独立审稿意见、披露声明草稿。
- 验收标准：矩阵每行对应真实读过的文献；抽十条论断各有矩阵支撑；抽十条引用逐条打开原文对得上；分析结果附代码与原始数值可复现；已按查到的官方政策写好披露声明。

## LAB C：Office Agent

### 这个 LAB 解决什么问题

学生和职场人大量的时间花在三件事上：整理 Word、分析 Excel、做 PPT。这个 LAB 把这三件事连同 PDF 处理、批量文件处理、模板套用串成一条流水线。

最终项目：从一批原始材料（比如一份调研问卷导出的 Excel、几份访谈记录 Word、若干 PDF）自动形成"Excel 分析加 Word 报告加 PPT 汇报"三件套。

### Mission：三件套流水线

- 名称：从原始材料到汇报三件套
- 难度：L3（联网加文件）到 L5（长任务）。
- 需要的能力：读写 Excel/Word/PPT/PDF，必要时用代码做批量处理。
- 输入材料：一个装着原始材料的文件夹，结构乱一点没关系。
- 风险提示：Office 文档的格式很脆。Agent 改 Word 时可能改乱样式、改 Excel 时可能覆盖你的公式、做 PPT 时可能把你的数据标错。所有操作都要求它在副本上做，原始材料锁起来只读。

### 分项要点

Word 整理：让它先盘点这个文件夹里有哪些 Word、各自多长、大概讲什么，列一张清单给你确认。再让它把同类文档合并、统一标题层级、补目录。不要一上来就让它"把这些文档整理好"——它不知道"整理"对你意味着什么。

Excel 分析：这是最需要数据纪律的一步。让它先读懂表——有多少行多少列、每一列是什么含义、有没有缺失、有没有明显异常值（比如年龄写成 999、收入写成空字符串）。它先把"数据字典"（每列叫什么、代表什么、取值范围）写出来给你确认，再开始分析。绝不允许它不看表就画图。

PPT：先定结构再做页。让它给你一个汇报大纲（几页、每页讲什么、结论是什么），你点头了再让它排版。PPT 上每个数字都要能在 Excel 分析结果里找到，不许它现编。

PDF：PDF 是最麻烦的格式——扫描件、图片版、表格跨页、乱码都常见。让它先判断这个 PDF 是文字版还是扫描版，扫描版先做识别再谈内容；提取表格时，要求它把提取出来的表再贴回来和原 PDF 对一遍。

批量处理："把这一百个 Word 的标题都改成宋体小四""把这五十个 Excel 都加一列"这类活，交给 Agent 最划算，但必须先拿三个文件试跑，你检查无误，再让它批量做全部。批量出错时，错得也很整齐——一百个文件一起错。

表格格式与模板套用：固定你常用的报告模板（公司模板、学校模板都行），把模板给它，让它"只填内容、不动模板样式"。

文档检查：最后让它当挑错人——查错别字、查格式不统一、查数字前后不一致、查引用缺漏。这一步用它比用你自己更冷静。

### 成功标准

- Excel 分析的每一个结论，你点开对应单元格能复核。
- Word 报告里的数字和 Excel、PPT 完全一致，没有三套数。
- PPT 十页左右，每页一个结论，不堆字。
- 原始文件夹原封未动，所有产物在新的输出文件夹里。

### 旗舰项目模板：从原始材料到汇报三件套

- 输入材料：一个装着原始材料的文件夹（调研问卷导出的 Excel、若干访谈记录 Word、若干 PDF），外加你常用的报告模板。
- 步骤：盘点文件夹并列清单 → Word 合并统一格式 → Excel 先写数据字典再分析 → PPT 先出大纲你点头再排版 → PDF 先判断文字版还是扫描版 → 三个文件拿三个试跑再批量 → 套用模板 → 当挑错人做最终检查。
- 产物：整理后的 Word 报告、带数据字典和复算说明的 Excel、十页左右的 PPT 汇报、输出文件夹（原始材料只读不动）。
- 验收标准：Excel 每个结论点开单元格可复核；Word 数字与 Excel、PPT 完全一致；PPT 每页一个结论不堆字；原始文件夹原封未动。

## LAB D：网络研究 Agent

### 这个 LAB 解决什么问题

你要写一份调查报告：调查一家公司、一项政策、一个行业、一个产品、一个竞品、或者一类学术资源。靠搜索引擎一页一页翻、靠收藏夹攒链接，既慢又容易只看到愿意看的那几篇。这个 LAB 教你把"找资料、读网页、比来源、核事实"做成一条可追溯的流水线。

最终项目：一份调查报告，里面每一条关键结论后面都挂着真实可打开的来源。

### 必须覆盖的能力

Search（搜索）：基础联网检索。要教会它换着关键词搜——同一事实的不同说法、中英文、官方名和俗称。

Deep Research（深度研究）：让 Agent 自己规划检索路径、读很多网页、交叉比对后给你一份带来源的长报告。用它之前，你仍然要先把"要回答什么问题、可接受的来源类型、多少篇起步"说清楚，否则它会给你一份什么都提到、什么都不深的东西。

Browser（浏览器）：有些内容搜索抓不到，但打开网页能看到。让它像人一样点进去读页面、翻分页、点下一页。网页阅读要区分：正文、评论区、广告、相关推荐——别让它把推荐链接当事实来源。

多来源比较：同一个事实，至少找两个独立来源对一遍。来源之间互相抄的不算两个来源。

信息提取：把网页里的关键数字、时间、人名、机构名抽成一张表，每条带来源链接和访问日期。

事实核验：凡是重要结论，单独核一遍——优先找官方原始出处（政府网站、公司公告、法院文书、论文原文），媒体转述、自媒体文章只能当线索，不能当证据。

来源记录：从第一天就建一张来源表：标题、网址、发布日期、你访问的日期、这篇资料支撑了哪个结论。报告里的每个关键结论都能在这张表里找到行。

网页变化与时效性：网页会改、会删、会过期。对关键页面，让它存档一份（截图或保存网页），并记下访问日期。政策类、价格类、数据类信息尤其要看"这是什么时候的数据"。

### Mission：企业调查

拿一家真实但你不太了解的公司练手。让 Agent 回答：这家公司做什么、谁开的、规模多大、最近有什么大动作、有没有负面新闻或诉讼、行业里排什么位置。

要求它把每个答案都写成"结论加来源加访问日期"的格式，并且明确区分：哪些是公司自己说的（官网、招股书）、哪些是第三方报道、哪些是查不到只能存疑。查不到的，老实写"未找到可靠来源"，不许它补。

### 成功标准

- 报告里随机抽五条结论，每条都能点开来源、且来源确实支持这句话。
- 至少三条结论标注了访问日期，且你能看出数据是哪一年的。
- 有一节专门写"本报告未能核实的部分"，而不是把空白用流畅的话填满。

### 旗舰项目模板：企业 / 行业调查报告

- 输入材料：一家真实但你不太了解的公司（或一项政策、一个行业、一个竞品），你关心的 5 到 8 个具体问题。
- 步骤：换关键词多轮搜索 → 深读官方原始出处优先 → 同事实至少两个独立来源互证 → 抽关键数字建来源表 → 重要结论单独核验 → 每个结论按"结论+来源+访问日期"写 → 单列"未能核实"一节。
- 产物：带来源表的调查报告、来源清单（标题/网址/发布日期/访问日期）、未能核实事项清单。
- 验收标准：随机抽五条结论都能点开来源且来源确实支持；至少三条标注访问日期并能看出数据年份；有专门一节写未核实部分而非用流畅话填满。

## LAB E：数据分析 Agent

先导图：数据分析 Agent 完整流程（待插入 F18）

### 这个 LAB 解决什么问题

你有一份数据表（问卷导出、公开统计、实验记录都行），想知道里面到底说明了什么。这个 LAB 把数据分析拆成标准工序。它和前面几个 LAB 的区别在于：这里"看图说话"的诱惑最大，所以纪律最硬。

### 完整流程

```text
读取数据
→ 数据字典
→ 数据质量
→ 清洗
→ EDA（探索性分析）
→ 可视化
→ 分析
→ 建模
→ 诊断
→ 稳健性
→ 解释
→ 报告
```

逐段说。

读取数据：让它先报告这个表的"长相"——多少行、多少列、每列名字、每列大概是什么类型（数字、文字、日期）。先别分析。

数据字典：每一列到底什么意思？问卷里这道题问的是什么？"收入"这一列是月还是年、税前还是税后？这些含义你不说清楚，后面所有结论都是悬空的。让它把不确定的列列成问题问你，而不是替你猜。

数据质量：缺失多少、有没有重复行、有没有明显录错的值（年龄负数、日期在未来）、单位是不是统一。这些问题先列清单，再动手。

清洗：删哪些、补哪些、改哪些，每一步都要它说明理由，并且在副本上做。原始数据永远不动。

EDA（Exploratory Data Analysis，探索性分析）：先不加任何判断，把分布、极值、相关性画出来给你看，回答"数据长什么样"，不回答"为什么"。

可视化：画图的目的是让你看懂，不是好看。要求它每张图配一句"这张图想说明什么、坐标轴是什么、数据范围是多少"。

分析、建模：到了要算关系、要建模型的时候，先问你一句"你的研究问题是什么"——同一个数据集，回答不同问题要用不同方法。让它把用了什么方法、为什么用、假设是什么讲清楚。

诊断、稳健性：模型跑出来之后，让它做两件事——这个模型在样本上表现好不好（诊断），换一种做法结论会不会变（稳健性）。结论一变就变的"规律"，不能当发现写。

解释、报告：最后落到结论。每个结论后面跟：这是用哪些数据、什么方法、在什么范围内成立的。范围外的话不要说满。

### 四条铁规矩

一，不允许看图"猜数据"。它画了一张图说"两组人差异很大"，你就问它：具体差多少、p 值多少、样本量多少。没有数字的图，等于没分析。

二，不允许编造统计结果。凡是报告里出现的平均数、比例、相关系数，要求它把计算用的代码贴出来，你能在你的数据上重跑一遍得到同一个数。

三，代码应可复现。把清洗和分析的代码存成文件，连同数据说明一起放项目里。今天跑和三个月后跑，结果应该一样。

四，指标定义必须明确。"活跃用户""高收入人群""年轻消费者"这类词，在报告里第一次出现时必须写清楚：怎么算出来的、阈值是多少。同一个词在不同段落里不能变含义。

### 成功标准

- 你能对着数据字典，用自己的话讲清每一列是什么。
- 报告里每个关键数字都能复算。
- 有一节写清"这个结论在什么条件下成立、什么情况下可能不成立"。

### 旗舰项目模板：一份可复现的数据分析报告

- 输入材料：一份真实数据表（问卷导出、公开统计、实验记录均可），以及你要用它回答的一两个具体问题。
- 步骤：先报表的长相（行/列/类型）→ 写数据字典给你确认 → 列数据质量清单 → 在副本上清洗 → EDA 出图带图注 → 按研究问题选方法 → 模型诊断与稳健性检验 → 每个结论标注数据/方法/适用范围。
- 产物：数据字典、清洗与分析代码、带图注的 EDA 图、结论报告（含适用范围与局限一节）。
- 验收标准：每个关键数字都能在你的数据上用附的代码复算；每个图表都有图注说明坐标轴和范围；报告有一节写清结论在什么条件下成立、什么情况下不成立。

## LAB F：不会编程也能开发软件

先导图：软件开发 Agent 全流程（待插入 F19）

这是本教程最有特色的一个 LAB，也是最需要你耐住性子的一个。它要教的不是"写代码"，而是"一个完全不会编程的人，怎么借助 Agent 把一个软件项目从找到、跑起来、改一点、测一测，到真正发出去"。

先把教学路径说死：本 LAB 的目标是"借助 Agent 完成开发"，不是"教你从零学会编程"。你不需要背语法、不需要默写函数，你需要练的是找项目、读说明、跑起来、提需求、验收、存版本这一套"甲方加验收员"的动作。代码本身由 Agent 写，你负责看结果、判对错、做决定。如果某一步它写的代码你完全看不懂，这是正常的，本 LAB 不要求你看懂，只要求你能确认它跑出来的效果对不对。

再讲怎么挑一个适合练手的开源项目。别一上来挑一个几十人团队、几十万行代码的大项目——你会被依赖装半天、文档三版不一致直接劝退。挑项目按四条标准：

第一，简单。优先选单语言、单仓库、README 里明明白白写了"三步跑起来"的小工具类项目。一个 CLI 小工具、一个静态网页、一个单文件脚本，都比一个前后端分离的大系统适合第一次练手。

第二，活跃。看两个指标：最近三个月有没有人提交代码、Issue 区有没有人在回答。超过一年没动静、一堆打开的 issue 没人管的项目，你踩了坑都没人问。

第三，文档好。README 必须写清楚怎么装、怎么跑、怎么贡献。README 一上来就是架构图、不提运行方法的项目，新手绕不出来。

第四，许可友好。选 MIT、Apache-2.0、BSD 这类宽松许可的项目，便于你学习和二次修改；GPL 类项目用于个人学习没问题，但如果你想把它拿来做商业发布，要先看懂许可。具体怎么找：在 GitHub 搜索框里按 "topic 加语言" 搜（如 "python cli"、"markdown notes"），按 stars 排序，再点进几个候选的 README 对照上面四条筛。

最后把权限边界讲清楚，哪些动作你自己在本地就能做、哪些需要账号和权限：

- 你在本地就能独立完成的：Clone / Download 下载项目、配依赖、本地跑起来、改一点代码、本地测试、用 Git 在本地提交（Commit）和开分支。这些全程不需要任何外部账号。
- 需要你自己注册账号、并具备对应权限才能做的：GitHub Push（需要 GitHub 账号和该仓库的写权限，别人的项目你只能先 Fork）、Pull Request（需要你自己的 GitHub 账号）、Deployment（需要部署平台账号，如 Vercel / Netlify / GitHub Pages）、Release（需要该仓库发布权限）。

所以零基础第一遍，完全可以只走"本地闭环"：Clone → 跑起来 → 改 → 本地测 → 本地 Commit。把这一圈走顺了，再花十分钟注册账号，去碰 Push / PR / Deploy / Release 这些对外动作。涉及对外的动作，照例按全书风险分级先确认再按。

先记住这一屏字，后面二十一步每一步都可能回头看它：

```text
代码生成 ≠ 功能完成
代码修改 ≠ Bug 修复
测试通过 ≠ 产品完全正确
Agent 声明完成 ≠ 实际完成
```

先导图：四大铁律警示图（待插入 F20）

下面严格按 F1 到 F21 的顺序走。每一步都用大白话解释它在干什么、你要做什么、怎么判断这步过了。

### F1. 软件开发到底在做什么

别被"软件"两个字吓住。所谓软件开发，本质上就是：把一堆事先写好的文本文件（代码），放到一个能读懂它的环境里运行，让它按你想要的方式工作。你要做的不是手写这些文件，而是指挥 Agent 找到、读懂、改动这些文件，并亲眼确认改动真的生效。你的角色是"甲方加验收员"，不是"程序员"。

这一步你要建立的认知：软件不是一个黑盒子，它是一堆放在文件夹里的文件，有办法看、有办法改、有办法退回去。

### F2. GitHub 是什么

GitHub（代码托管平台）是一个网站，全世界的人把自己写的软件项目放在上面，公开分享。你可以把它理解成"软件界的公开网盘加作品展示架"。绝大多数你想用的开源软件，都能在 GitHub 上找到。你不需要会用它的全部功能，只需要会找项目、看说明、下载项目。

### F3. Repository 是什么

Repository（代码仓库，简称 Repo）就是 GitHub 上的一个项目文件夹。点进一个项目，你看到的那个页面就是一个 Repository：里面有代码文件、有说明、有别人提的问题、有版本记录。你可以把它想成一个项目的"主页加文件柜"。

### F4. Clone / Download

Clone（克隆）就是把 GitHub 上那个项目完整下载到你自己电脑上，下载完你就有了这个项目的全部文件。Download 是另一种更简单的方式：直接下载一个压缩包解压。区别是 Clone 会把"这个项目的版本历史"也一起拿下来，后面我们要用这个历史来回退。第一次练手，用 Agent 帮你执行 Clone 就行，你不用自己敲命令。

### F5. README

README 是项目根目录里那个说明文件。任何人想知道这个项目是干什么的、怎么装、怎么跑，都先读它。对零基础的你，README 是这个项目的"使用说明书"。让 Agent 把 README 读给你听：这项目解决什么问题、需要什么前提、怎么启动。如果 README 写得很烂、根本跑不起来，这个项目趁早换——别在它身上耗。

### F6. 找到如何运行项目

读懂 README 之后，下一个问题是"我怎么在自己电脑上把它跑起来"。让 Agent 帮你找：启动命令是什么、需要点哪个按钮、跑起来以后访问哪个地址。跑起来的标志是：你自己亲眼看到一个窗口、一个网页、或者一句"运行成功"出现在你屏幕上。Agent 说"应该能跑了"不算，你看到才算。

### F7. Dependency

Dependency（依赖）是这个软件正常运行所需要的"其他零件"。就像做饭需要菜和调料，一个软件常常需要别人写好的一堆基础包。你不用认识这些零件是谁，你只要知道：Agent 会帮你把它们装好；装不上、报错、版本对不上，是这一步最常见的麻烦，把报错原样贴给 Agent 让它解决。

### F8. Local Development

Local Development（本地开发）指的是：在你自己的电脑上，把这个项目跑起来、改一改、再看效果的状态。你要建立的工作姿势是：改一个东西，立刻跑起来看一眼；不对，就改回去。不要一口气改十处再跑——那样一旦坏了，你根本不知道是哪一处弄坏的。

### F9. 让 Agent 阅读代码

现在你有了一个能跑的项目，但你看不懂里面的代码。没关系。让 Agent 当你的翻译："这个项目的主流程是什么？哪个文件控制页面上那个按钮？这个按钮点下去会发生什么？"它读完会给你一张"地图"：哪几个文件是核心、哪个文件你以后最常改。这张地图你存下来，后面所有修改都靠它定位。

### F10. 需求 → Task List

你想加一个小功能（比如把首页那个按钮的颜色改了，或者加一句欢迎语）。不要直接说"帮我改一下"。先把需求写成一句话目标，再让它列成 Task List（任务清单）：第一步碰哪个文件、第二步改哪一行、第三步怎么验证。清单你看过、觉得靠谱，再让它动手。这就是前面学过的长任务管理，只是搬到了代码上。

### F11. 修改一个小功能

挑一个最小的功能动手——改个文字、换个颜色、动个位置都可以。越小越好。让它按 Task List 改，改完立刻在你自己的浏览器或窗口里看效果。这一步的目的不是改出多酷的东西，是让你完整走一遍"提需求—改—看效果"。

### F12. Test

Test（测试）就是：你亲自用一用，看它是不是按你想的那样工作。你是零基础，但你正好是最好的测试员——你就像一个真实用户一样点一点、试一下。它自己说"我测过了"不算数（回想铁律），你点过了才算。把你试的几种情况都记录下来。

### F13. Debug

Debug（调试）就是东西没按预期工作时，找出哪里出了问题。发生了别慌：先把现象描述清楚——你做了什么、它显示了什么、你期望它怎样。把这三句话连同报错截图一起给 Agent。它给的修复方案，仍然要你跑一遍确认。它说"应该好了"，你再点一次，好了才算好。

### F14. Regression Test

Regression Test（回归测试）是个听着吓人、其实很朴素的概念：你改了新地方之后，把以前能正常工作的老地方也再试一遍，确认新改动没有把旧功能弄坏。就像修好了水龙头，顺便看看马桶还冲不冲。Agent 很容易"修一个坏三个"，这一步就是防这个的。

### F15. Git

Git（版本控制工具）是一个帮你记录"文件每一次改动"的工具。你可以把它理解成游戏的存档系统：改坏了，随时读档回到上一个正常的地方。零基础的你不需要懂它的全部原理，只要养成习惯：每完成一个小的、正常工作的改动，就存一个档。后面所有"改坏了"的恐慌，都会被这个习惯消掉。

### F16. Commit

Commit（提交）就是上面说的"存档"。每存一次，你要写一句话：这次改了什么。这句话写给三个月后的你看。让 Agent 帮你执行，但那句话你要自己想清楚——"改了点东西"不是 commit 说明，"把首页按钮改成蓝色"才是。

### F17. Branch

Branch（分支）是一条平行的修改线。主分支是"现在能正常用的版本"。你要试一个比较大的改动时，开一条新分支去折腾；折腾成了再并回主分支，折腾砸了直接扔掉这条分支，主分支不受影响。新手最容易犯的错是直接在主分支上乱改——开分支就是给你一个"放心折腾"的安全区。

### F18. GitHub Push

Push（推送）就是把你电脑上存的这些改动，上传到 GitHub 那个仓库上。到这一步要特别小心：上传是对外的动作。上传之前确认：这是你的项目或你有权改的项目、里面没有密码密钥、你确实想让它公开可见。涉及上传的动作，按全书的风险分级属于 L3，先确认再按。

### F19. Pull Request

Pull Request（合并请求，简称 PR）是 GitHub 上一种礼貌的"申请"：你改完了一条分支，发个请求说"我觉得这些改动不错，要不要合进去"。如果你改的是别人的项目，PR 就是你贡献代码的方式——别人会看到你的改动、提意见、决定要不要合并。如果你改的是自己的项目，你也可以自己合并，但保留 PR 这个环节，能让你养成"改完先看一眼再合"的习惯。

### F20. Deployment

Deployment（部署）就是把你做好的软件，放到一个能让别人访问的地方，而不只是在你自己电脑上跑。比如把一个小网页挂到网上。对零基础的你，不用一上来就学复杂的服务器——先用现成的托管平台，让 Agent 帮你把项目传上去、生成一个链接。这一步开始涉及对外可见的东西，上传前照例确认一遍内容。

### F21. Release

Release（发布）就是你正式宣布"这个版本做好了"，给它起个版本号、写个说明：这版加了什么、修了什么、怎么下载。它不是技术动作，是"对外打招呼"。做完这一步，你就完整经历了一个软件从找到、跑起来、改一点、测一测、存版本、上传、到发布的全过程。你依然一行代码都没自己写过，但你已经知道一个软件项目是怎么运转的了。

### 旗舰项目模板：借助 Agent 完整走一个开源项目闭环

- 输入材料：一个你按上面四条标准挑好的、简单且活跃的开源小项目（自己 Fork 或只在本地 Clone 均可）。
- 步骤：Clone 到本地 → 读 README 跑起来 → 让 Agent 画一张"文件地图" → 选一个最小改动（改文字/换颜色/加一句欢迎语）→ 写成 Task List → 按清单改 → 本地看效果 → 测几种情况 → 回归测旧功能 → 本地 Commit 存档。有余力再注册账号，走 Push → 开 PR → 部署 → Release。
- 产物：跑起来的本地项目、一份"文件地图"、一次最小功能改动、测试记录、本地 Git 提交历史。
- 验收标准：你亲眼在自己屏幕上看到它跑起来；改动后效果符合预期；以前能用的功能回归正常；每完成一个小步都有 Git Commit 存档；对外动作（Push/PR/Deploy/Release）发生前你已确认内容且没有密钥外泄。

### 走完 F1–F21 你该有的心态

会用 Agent 改一个按钮，不等于你会做软件；但它比绝大多数"看了十本编程教程却从没跑通过一个项目"的人，离真实开发更近。真正的门槛从来不是写代码，而是：找得到、跑得起来、改得动、测得出来、坏了能退、做好了敢发。这套本事，你已经有了。

## LAB G：日常工作 / 个人效率 Agent

### 这个 LAB 解决什么问题

前面几个 LAB 都围着"一个具体任务"转。这个 LAB 围着"你这个人每天的杂事"转：邮件、日程、文件、待办、会议、信息跟踪、知识库、周报、工作总结、自动提醒。这些事的共同点是碎、重复、但又不能全撒手。

### 可以让 Agent 接管什么

邮件：让它读收件箱，按"需要我今天回/这周处理/只是通知/垃圾"分类，并给需要回的邮件起草回复草稿。注意——起草可以，发出去不行（这是全书反复讲的 L3 动作，必须你点）。

日程和待办：让它把你散落在备忘录、聊天记录、邮件里的事抽成一张待办清单，按时间和紧急程度排好，每周一早上给你一份"这周要做什么"。

会议：会前帮你把相关背景材料读一遍列成两页要点；会后把录音或你的笔记整理成纪要，分出"决定了什么、谁负责、什么时候交"。

文件：定期让它把下载文件夹、桌面、截图文件夹按规则归一次档（这是 PART 1 那个 Mission 的长期版）。

信息跟踪：你关心的几个主题（某个政策、某家公司、某个领域的新论文），让它每周帮你扫一遍有没有新东西，有就摘要，没有就不打扰——这个我们在 PART 9 会把它做成自动化。

知识库：把你平时攒的笔记、读过的论文、写过的报告，定期让它整理成一个可检索的个人知识库。

周报和工作总结：到周五，让它从你这周的待办完成情况、会议纪要、改的文件里，拼一份周报初稿，你改改就发。

自动提醒：把"该交什么、该回谁、该续费了"这类时间敏感的事，让它提前提醒你。

### 成功标准

- 你能说出三件它替你省下来的、具体的、每周都发生的事。
- 它起草的邮件和纪要，你改两笔就能用，而不是重写。
- 涉及"发出去、存进去、公开"的动作，永远停在你这里等确认。

### 旗舰项目模板：个人事务管家 Agent

- 输入材料：你真实的一周邮件、日程、待办、下载文件夹，以及你常用的周报模板。
- 步骤：让它读邮件分四类并起草需回邮件 → 把散落各处的事抽成待办清单 → 会前列两页背景要点、会后整理成纪要（决定/负责人/截止）→ 定期把下载和桌面按规则归档 → 关心的主题每周扫一遍新东西 → 周五拼一份周报初稿。
- 产物：邮件分类与回复草稿、待办清单、会议纪要、归档后的文件夹、周报初稿。
- 验收标准：说出三件它每周替你省下的具体事；它起草的邮件和纪要你改两笔就能用；凡"发出去/存进去/公开"的动作都停在你这里等确认。

# PART 9：自动化与长期运行

先导图：自动化触发-条件-执行闭环（待插入 F21）

前八讲，你做的每一件事都是"你喊一声，Agent 动一次"。这一部分要解决一个新问题：有些事你不想每天喊。

你不想每天早上八点自己去搜一遍关心的新闻，也不想每来一封邮件就手动让 Agent 分类。你想要的是：定好规则，它自己跑；没事别烦你，有事再叫你。这就是自动化（Automation）——从"我让它做一次"进入"数字工作流"（Autonomous Workflow）。

但自动化的第一课不是"怎么让它跑起来"，而是"哪些动作绝不能让它自己跑"。所以这一 Part 会把一条流水线拆成八个零件，然后用两个真实例子把它们装起来。

## 9.1 Trigger（触发）

Trigger（触发）是"什么情况发生了，这个工作流才开始动"。它就像一个闹钟：闹钟响了，后面的动作才发生；不响，一切静止。

在给 Agent 派活时，触发就是你说的那句"开始吧"。一旦你想让它长期运行，你就得把"开始吧"这件事也交给某个客观条件来做，而不是靠你记得。触发有两大来源：一种是到点了（时间），一种是出事了（事件）。这两种分别对应下面的 9.2 和 9.3。

设计自动化时，第一个要问的问题永远是："它凭什么开始？"触发条件写不清楚，整条流水线要么不该动的时候乱动，该动的时候不动。

## 9.2 Schedule（定时）

Schedule（定时）就是"按时间触发"。每天早上八点、每周一九点、每月一号、每两小时一次——这都是定时。定时任务是最简单、最容易预测的一种自动化：时间到了就跑，跑完就停。

你要决定三件事：什么时候跑（频率和时间点）、跑多久（超时就停，别让它卡住一直占资源）、跑出来的结果放哪（存成文件还是直接推给你）。定时任务最大的好处是可预期——你知道它明天八点会再来一次。最大的坑也是它"雷打不动"：周末你放假它也跑，节假日你不在它也跑，跑出来一堆没人看的结果。所以定时任务一定要和后面的"条件判断"配合：到点了先看看有没有真事，没事就闭嘴。

## 9.3 Event（事件）

Event（事件）是"某件具体的事发生了"。来新邮件、收到表单提交、网页更新了、数据库多了一条记录、代码仓库收到一个新 Pull Request——这些都是事件。事件触发和定时触发的区别是：定时是"到点就动"，事件是"有事才动"。

技术上，事件通知最常见的机制叫 Webhook（网络钩子）。零基础理解它：Webhook 就是"当某件事发生时，那个系统自动往你指定的一个地址发一条消息"。比如你的邮箱系统说"有新邮件了"，它就自动把这个消息推给你的自动化工作流，工作流这才醒过来开始干活。你不用每隔五分钟去邮箱问一句"有没有新邮件"，有邮件它自己会来敲门。

事件触发比定时更省资源、也更及时，但它更依赖外部系统"会不会真的来敲门"。所以重要的事件流，往往还要配一个定时检查作为兜底——万一 Webhook 漏了，定时任务还能补一次。

## 9.4 Condition（条件）

Condition（条件）是"触发之后，先别急着干活，判断一下该不该真干"。它是整条流水线里最能帮你"少被打扰"的零件。

举个例子：每天早上八点抓取了一批新信息，这时候不能直接把整批信息发给你——那样你每天早上都会收到一大坨没用的东西。要先过一道条件：这批新信息和昨天相比，有没有真正重要的变化？所谓"重要"，是你事先定好的规则：出现了我关注的关键词、数字变动超过了某个幅度、来了一条新的官方公告。有，才往下走；没有，这一轮直接结束，连通知都不发。

条件这一步的价值，是把"每次都跑满全程"变成"没事就快速退出"。设计自动化时，条件写得越具体，你被打扰得越少。最忌讳的条件是"如果有新内容就通知"——新内容天天有，等于没条件。

## 9.5 Action（动作）

Action（动作）就是条件满足之后，Agent 实际去做的那件事：抓网页、读邮件、写摘要、更新表格、起草回复、发通知。它就是前八讲你已经很熟悉的那些活，只不过现在被条件拉着自动跑。

设计 Action 时记住两点。第一，每个动作都要有明确的输入和输出，跑一轮就要有一轮的产物（一个文件、一条消息、一行记录），不能"跑了但什么都没留下"。第二，动作本身要分级：只读、只读文件和搜索网页这种，放手让它跑；要往外发、要改线上数据、要花钱的动作，不能放在全自动段里——它们要走到下面 9.6 的人工审批那一步。

## 9.6 Human Approval（人工审批）

这是本 Part 最重要的一节，请单独看。

Human Approval（人工审批）就是：在动作执行到某个关键节点时，流水线自动停下来，把"我打算这么做"摆到你面前，你点头，它才继续；你不点头，它就停在那儿，什么都不发。

为什么必须有这个节点？因为自动化的可怕之处，不在于它做错，而在于它"错得很有规律、而且停不下来"。它可以在你睡觉的时候，按错误的判断，把措辞不当的邮件发给客户、把没核完的数据贴到公开文档、把一行写岔的代码推到线上。一次错，是事故；自动重复一百次错，就是灾难。

所以铁律是：**凡是对外的、不可逆的、影响别人的动作，都必须经过人工审批，不能让全自动流水线直接执行。**具体说：

- 发邮件、发消息、发帖——草稿自动生成，发送由你点。
- 覆盖原文件、删除数据、Git Push、改云端正式文档——自动生成改动，执行由你确认。
- 花钱、下单、改权限、对外提交——绝不自动化。
- 只读、在副本上分析、写草稿、做摘要——可以自动跑。

审批节点怎么设？不是"每一步都问你"，那样你比手动还累。而是把动作分成两段：全自动段负责读、想、起草、准备好；到了"最后一脚"——发送、发布、提交——才停。你要审的是成品，不是过程。审批消息里必须包含：它打算干什么、依据是什么、你点哪个按钮同意、点哪个按钮拒绝。糊里糊涂的"请确认是否继续"，等于没审。

## 9.7 Notification（通知）

Notification（通知）是流水线跑完后怎么告诉你。它有三个原则。

第一，有价值才通知。没有变化、没有异常、没有需要你决策的事，就别出声。"一切正常"这种话，发一次是礼貌，发十次就是噪音，最后你会把整个通知关掉，真出事也看不到。

第二，通知要短、要带结论、要告诉你下一步干什么。好的通知是："这三条有变化，摘要如下，要我展开吗？"坏的通知是："今日已扫描 47 个网页，完成分析。"

第三，通道要对。需要你决策的（审批），推到你随时看的地方；纯结果摘要，攒到每天一封汇总；错误和异常，立刻推。不要把所有东西都塞进同一个提示音里。

## 9.8 Recurring Workflow（重复工作流）

Recurring Workflow（重复工作流）是上面这些零件组合起来之后，长期反复运行的那条流水线本身。它和单次任务的区别在于：它会记着上一轮干到哪了、昨天抓的是什么、上次通知你的是哪条。没有这个记忆，它每一轮都从零开始，就没法做"和昨天比有没有变化"这种事。

运行一个重复工作流，你要维护三样东西：一份规则说明（触发、条件、动作、审批点都写清楚），一份运行记录（每轮什么时候跑的、结果如何、有没有报错），一份定期复核（每周或每月看一眼：它最近通知我的东西还有价值吗？条件是不是该调了？有没有哪轮悄悄失败了）。自动化最大的隐患不是第一天，而是第三个月——规则没人维护，它还在按三个月前的判断标准天天跑。

```text
抓取你关心的几个来源的新信息（Action：抓网页/查更新）
   ↓
和昨天存下的版本对比（Condition：有无真正重要的变化）
   ↓
   ├─ 有变化 → 写一条摘要，列出变化点和来源 → 推送给你（Notification）
   └─ 无变化 → 这一轮直接结束，不打扰你
```

注意这里的设计：定时触发后，先抓、再比、再判断；判断为"没事"就静默退出，通知只在有事时发。整个过程没有任何对外动作，所以不需要审批节点。这是全自动安全跑的典型。

先导图：邮件自动处理人工审批示例（待插入 F23）

第二个流程，邮件分类与回复。

```text
收到新邮件（Event：Webhook 来敲门）
   ↓
分析邮件类型：需要回复 / 仅通知 / 待办事项 / 垃圾
   ↓
提取需要你处理的任务，归入待办（Action）
   ↓
对"需要回复"的邮件，起草回复草稿（Action：只起草，不发送）
   ↓
停下来等你（Human Approval）
   ↓
   ├─ 你看了草稿，说"发" → 它才把邮件发出去
   └─ 你说"重写"或"不回" → 它按你的指示重来，或就此结束
```

这个流程里，读邮件、分类、起草草稿都是只读和在你这边的动作，可以自动跑；但"发送"是对外的、发出就收不回的动作，必须停在审批节点，由你点。这就是人工审批节点为什么不可省：它把自动化省下来的时间，和不可撤销动作的风险，隔开了。

## 几个必须分清的概念

定时任务就是 Schedule 那一整套：到点跑、跑完停。条件触发是 Event 加 Condition：有事来敲门，且符合你定的判断标准，才动手。Webhook 是事件能"自动敲门"的技术机制，不是你要写代码去造的东西，理解它"来敲门"这个作用就够了。

自动化平台是现成的、把上面这些零件拼起来的工具：你在上面用连线或填表格的方式，把"当某事件发生、满足某条件、就执行某动作、再通知某人"搭出来，不用自己写程序。挑平台时看三点：支持哪些触发源、支不支持中间插一个"等人工批准"的节点、失败了有没有日志能查。

最后说一个新手最容易混的：Agent 和传统 RPA（Robotic Process Automation，机器人流程自动化）有什么区别。RPA 是"模拟人手去点软件"——它把你的鼠标键盘录下来，然后机械地重复，画面一变、按钮挪个位置它就崩。Agent 自动化的区别在于：它看懂的是任务的意思，不是屏幕上的像素；页面布局变了，它能理解"那个提交按钮大概在哪、我要完成的事是什么"，自己再找路。代价是 Agent 更灵活、也更不可预测——所以对 Agent 自动化，人工审批节点比 RPA 时代更重要，而不是更不重要。

## 案例 1：每日信息监控（完整可运行）

这个案例把上面第一个流程落成一个真实脚本，位置在 `examples/automation/daily_monitor.py`。它抓 GitHub Releases 这个稳定只读数据源，和昨日快照对比，只有出现新版本才写摘要。纯 Python 标准库，不需要 pip 安装任何东西。

它对应八个零件的方式是：Schedule 由 Windows 任务计划程序负责，Action 是抓取与比对，Condition 是"和上次快照比有没有新 Release"，Notification 是写一份摘要文件，Logging 全程写 monitor.log。整个流程只读不对外，所以不需要人工审批节点。

先把脚本跑通（在 `examples/automation/` 目录下）：

```powershell
# 离线自测：用内置样例数据，不联网
python daily_monitor.py --offline
# 第二次跑，模拟"今天出了新版本"，应看到一条变更摘要写进 reports/
python daily_monitor.py --offline --update
# 再跑一次，应静默退出（已记过，幂等）
python daily_monitor.py --offline --update
```

第一次正式跑会先建立基准快照、不发通知；之后每天跑，只有出现新 Release 才在 `reports/` 目录生成一份带日期的摘要，其余日子静默。想监控别的仓库，加 `--repo owner/name`，例如 `python daily_monitor.py --repo pallets/click`。

把它注册成 Windows 每天早上八点自动跑，用任务计划程序 schtasks。下面这条命令在管理员 PowerShell 里执行一次即可：

```powershell
schtasks /Create /TN "DailyMonitor" /TR "python D:\AISOP\AI-Agent-Tutorial\examples\automation\daily_monitor.py" /SC DAILY /ST 08:00
```

几点说明，别照抄出错：`/TN` 是任务名字，自取；`/TR` 后面是要跑的命令，路径用绝对路径，因为任务计划程序的工作目录和你手动不一样；如果 `python` 在任务计划的 PATH 里找不到，把它换成 `python.exe` 的完整路径（先在 PowerShell 里跑 `(Get-Command python).Source` 查到）。查看任务用 `schtasks /Query /TN "DailyMonitor"`，删掉用 `schtasks /Delete /TN "DailyMonitor" /F`。

本机实测输出（2026-09-18）：首次离线建基准写"建立基准快照，不生成通知"；第二次检出 1 条新 Release 并写出 `reports/change_*.md`；第三次静默退出。日志落在 `monitor.log`。

## 案例 2：邮件分类审批工作流（完整可运行）

这个案例把第二个流程落成 `examples/automation/email_triage.py`。它读 `emails/` 目录里的样例邮件，按关键词分成"工作 / 个人 / 通知"三类，给"工作"和"个人"起草回复，放进 pending 队列停住，等你人工批准后再发送。

先把三条样例邮件放在 `examples/automation/emails/`（已随教程附带，分别对应三类），然后跑：

```powershell
# 扫描 emails/ 目录，分类+起草+入队
python email_triage.py run
# 查看队列
python email_triage.py list
# 批准某条（把 <id> 换成 list 里看到的真实 id）
python email_triage.py approve <id>
# 拒绝某条，标记为不回复
python email_triage.py reject <id>
```

安全设计是这个案例的重点：分类和起草是只读、本地动作，可以自动跑；但"发送"是对外、不可逆动作。脚本默认不真发——它把待发邮件的收件人、主题、正文写进 `outbox.log`，等你人工外发。只有当你真的在环境变量里配齐 `SMTP_HOST`、`SMTP_USER`、`SMTP_PASS` 三个值时，approve 才会通过 SMTP 真的把信发出去。也就是说：没填凭据，就永远不会真的把邮件发出去。

```powershell
# 仅示例：真要发信时才设这三个变量（不写进代码、不提交公开仓库）
$env:SMTP_HOST = "smtp.example.com"
$env:SMTP_USER = "you@example.com"
$env:SMTP_PASS = "你的授权码"
python email_triage.py approve <id>
```

本机实测输出（2026-09-18）：三条样例邮件分别被判为"工作 / 个人 / 通知"并各自拿到草稿；批准工作邮件时因未配 SMTP 凭据，状态记为 `approved` 并把待发内容落进 `outbox.log`；拒绝朋友聚餐邮件记为 `rejected`。

这个案例和真实邮箱之间还差一层对接——真要让它读你收件箱，需要按邮箱服务商的 IMAP 设置写一段拉取代码替换掉"读 emails/ 目录"这一步；审批节点和"无凭据不真发"的安全设计原样保留即可。这一步涉及读取真实邮件，建议先在样例数据上把流程跑顺，再换成真邮箱。

## Mission：搭一个真正长期跑的小自动化

- 名称：每日信息监控或邮件草稿
- 难度：L6（自动化）。
- 目标：搭一条每周至少跑五天的流水线，跑满两周你再评价它。
- 怎么做：先选一个真正值得每天看的主题；按上面第一个或第二个流程搭；审批节点一定留；通知控制在有事才发。
- 成功标准：连续跑两周，你能说出它帮你抓住了哪几条你本来会漏看的变化；同时这两周里，它没有在没问你的情况下发出过任何对外消息。
- 常见失败：条件定得太松，每天给你推一堆，一周后你关了通知。修法是把"重要变化"的门槛定得更严，宁可不推，不要刷屏。

# PART 10：构建自己的 Agent

先导图：构建自己的 Agent 蓝图（待插入 F24）

这一部分只面向一类读者：你已经走完了前面九个 Part，用 Agent 帮自己干了几个月真活，现在想知道"我能不能自己造一个 Agent，让它专门服务我的专业"。

如果你还没到这一步，这一 Part 可以先跳过——它不影响你成为一个熟练的 Agent 用户。它讲的是"拆开一台机器看看里面"，而你前面学的是"把这台机器用好"。

下面二十三个零件，按"它是干什么的、你为什么需要它、零基础的你掌握到什么程度"来讲。不需要每个都自己实现，重要的是你听得懂每个零件解决什么问题、什么时候需要它。

## 一、入口与规则：System Prompt 与 Runtime

1. System Prompt（系统提示词）。这是你给这个 Agent 的"岗位说明书"：它是谁、服务谁、擅长什么、不能做什么、按什么流程干活、输出长什么样。前面所有"8 要素任务法"里的目标、约束、流程、验收，长期化之后就是 System Prompt。它不是一句口号，而是一套这个 Agent 每次启动都会先读的工作守则。

2. Agent Runtime（运行时）。这是真正把模型、工具、记忆跑起来的那个底座。你写好了岗位说明书、配好了工具，是运行时在负责：把用户的话交给模型、模型说要调工具就去调、调完再把结果喂回去、循环往复直到任务完成。零基础的你不用自己写一个运行时，用现成的 Agent 框架就行；但你要知道，Agent 之所以能"自动循环干活"，靠的就是这个运行时在背后转。

## 二、工具这一侧：Tool Schema、Function Calling、Skill、Plugin、MCP Server、API

3. Tool Schema（工具定义）。你要让 Agent 能用一个工具，光说"你可以搜索"不够，得写清楚：这个工具叫什么、干嘛用的、需要给它什么参数、每个参数什么意思、什么时候该用它。这份"填表式说明"就是 Tool Schema。模型之所以知道"哦这个情况该调搜索"，就是靠读这份说明。

4. Function Calling（函数调用）。这是模型的一种能力：它不直接回答你，而是输出"我要调用哪个工具、传什么参数"，由运行时真正去执行，再把结果拿回来。你前面用 Agent 时看到的"它决定去搜一下、读一下文件"，底层就是 Function Calling。

5. Skill 开发。当你发现自己反复给 Agent 写同一套指令、配同一套模板、用同一套脚本，就该把它沉淀成一个 Skill——一份说明文件加配套资产。这是最适合零基础起步的"自己开发"：你写的主要是文字和流程，不是代码。

6. Plugin 开发。Plugin 是挂在某个平台上、给该平台扩展能力的模块。它比 Skill 更"平台绑定"，通常要按该平台的规范来做。对你来说，知道它和 Skill 的区别（平台扩展 vs 通用技能）就够了。

7. MCP Server 开发。MCP（Model Context Protocol，模型上下文协议）是一套让 Agent 连接外部工具和数据的标准。写一个 MCP Server，就是把你想用的某个系统（比如你的文献库、你的数据表）按这套标准暴露给任何支持 MCP 的 Agent。它需要一点编程，但好处是"写一次，到处能用"。

8. API 设计。API（应用程序接口）是软件之间互相喊话的标准方式。你要让 Agent 用某个服务，多半是通过调它的 API。零基础的你不用自己设计 API，但要看得懂"这个服务要我提供什么地址、什么密钥、会返回什么"。

## 三、记忆与上下文：Context Management、State、Memory、RAG

9. Context Management（上下文管理）。模型一次能看的信息有上限（Context Window）。任务一长，它就会忘掉开头说的事。上下文管理就是决定"这一轮把哪些信息塞给它、哪些先放一边、哪些从档案里再捞回来"。核心原则前面讲过：最小充分上下文——给它正好够用的，别一股脑全倒进去。

10. State（状态）。状态是"这个任务现在干到哪了"：做到第几步、上一步结果是什么、还差什么。它和 Memory 的区别是：State 是"这一件事的进度"，任务结束就没用了；Memory 是跨任务、长期攒下来的。

11. Memory（记忆）。让 Agent 跨对话记得你的偏好、你正在做的项目、之前的决定。长期记忆要省着用、定期整理，不然它会把过时的偏好当成今天的事实。

12. RAG（Retrieval-Augmented Generation，检索增强生成）。材料太多塞不进上下文时，做法是：先把材料存成一个库，每轮先从库里"检索"出最相关的几段，再让模型基于这几段回答。这就是你前面"让 Agent 读二十篇论文"背后的原理——不是二十篇全塞进去，是每次先捞出最相关的。

## 四、大脑的分工：Planner、Executor、Evaluator 与 Sub-agent

先导图：Planner/Executor/Evaluator 架构（待插入 F25）

13. Planner（规划器）。把一个大任务拆成一步步的小任务。强推理的模型适合干这个——它负责想"先干嘛后干嘛"。

14. Executor（执行器）。真正去干每一小步：搜、读、写、算。它可以用快一点、便宜一点的模型，因为它干的是执行而不是思考。

15. Evaluator（评估器）。干完一步检查一步：结果合不合格、要不要重来。用一个独立的"挑刺角色"，往往比让干活的人自己评价自己更可靠。这正是全书 PART 4 讲的"独立审查"。

16. Sub-agent（子智能体）。主 Agent 忙不过来时，派一个分身专门处理一个子任务，干完把结果交回来。好处是每个分身只看自己那摊事，不会被主任务的长上下文拖垮；代价是你要设计好"派出去什么、拿回来什么"。

## 五、把人和安全接进来：Human-in-the-loop、Hooks、Sandbox、Security

17. Human-in-the-loop（人在回路）。就是 PART 9 反复讲的：关键节点停下来等人确认。设计自己的 Agent 时，第一件事就是标好哪些节点必须等人。

18. Hooks（钩子）。钩子是"在某件事发生时自动触发一段你指定的动作"——任务开始前先检查环境、每次写文件后自动跑一遍格式检查、出错时自动通知你。它是把全书的"验收纪律"变成自动执行的手段。

19. Sandbox（沙箱）。沙箱是一个隔离的、安全的小房间：Agent 可以在里面跑代码、装东西、折腾，但出了事也只关在小房间里，碰不到你真正的文件。凡是让 Agent 跑代码，都尽量先在沙箱里跑。

20. Security（安全）。做自己的 Agent，安全是底线不是加分项：密钥不写进提示词、不提交公开仓库；给外部工具的权限最小够用；装别人的 Skill/MCP 之前按那十二问查一遍；对外动作一律走人工审批。前面 PART 7 的 L1–L4 风险分级，搬到这里就是你自己 Agent 的权限设计。

## 六、让它可看、可测、可上线：Observability、Evaluation、Deployment

21. Observability（可观测性）。你的 Agent 跑起来之后，你得能看见它每一轮干了什么：调了哪个工具、给了什么参数、拿到什么结果、为什么这一步这么决定。没有这个，它出错了你就是瞎猜。让它把每一步记成日志，是可观测性的起点。

22. Evaluation（评估）。怎么知道你这个 Agent 做得好不好？不能靠感觉。准备一组固定的测试用例（十个二十个典型任务），每次改完它都跑一遍，看哪些过了、哪些退化了。这就是前面 LAB F 的 Test 和 Regression Test，只不过对象换成了你自己的 Agent。

23. Deployment（部署）。把你做好的 Agent 从"你电脑上能跑"变成"你（和别人）真的能日常用"。对零基础起步，先用最现成的方式跑起来，别一上来就学服务器运维；能用稳定，比架构炫重要。

## 零基础怎么迈出第一步

把这二十三个零件列出来，不是要你全部自己造一遍。对刚毕业的人，正确的顺序是反过来：先挑一个现成的 Agent 平台或开源框架，把上面能直接用的零件用起来——别人已经做好的运行时、工具调用、记忆管理，直接拿来；你真正要自己花心思的，只有三样：写清楚你的 System Prompt（这个 Agent 到底服务什么、怎么干）、接好它要读的资料和要调的工具、以及设计好"怎么算干得好"的测试。框架会换、模型会升级，这三样不会变。

不要一上来就想"我要从零写一个 Agent Runtime"。那是几十人团队几年的活，不是你毕业项目的目标。你的目标是"用现成零件，拼出一个真正替你干活的东西"。判断你有没有学会，标准也很朴素：一个你不懂技术的同学，拿着你写的说明书，能不能照着装好、跑起来、出一次合格结果；出了错，你能不能靠 Observability 留下的日志，说出它错在哪一步。能做到这两点，这个 Agent 就不只是一次作业，而是你以后真能用的工具。

### 毕业项目

走到这里，你的毕业项目是一件事：**设计、实现、测试并交付一个面向你自己专业的 Agent。**

它不需要技术多高深，需要的是把前面学的东西真的用一遍。建议这样做：

第一步，选定一个你本专业里每周都要做、而且做得烦的活。它可能是：文献研究、法律案例梳理、历史史料整理、宏观数据跟踪、市场调研、财务分析、软件维护、课程学习——任何一个你自己真用得上的。别选一个"听起来很酷但你自己不会用"的题目。

第二步，按 8 要素把这个 Agent 的岗位书写清楚：它服务谁、解决什么、材料从哪来、能用哪些工具、哪些动作必须人工批、怎么算干得好。这份说明书就是你的 System Prompt。

第三步，配好它需要的工具和资料：要读文件就接文件能力，要查网络就接搜索，要读你的资料库就配一个 RAG。

第四步，按 Planner–Executor–Evaluator 的思路把流程串起来：它先规划、再执行、自己先查一遍。

第五步，准备十到二十个测试用例，把它跑一遍，记录哪些过、哪些漏、哪些胡说。针对失败点改，改完用同一套用例再跑一遍——这就是它的回归测试。

第六步，交付。交付物不只是"能跑"，还包括：一份说明书（别人拿过去知道怎么用）、一套测试用例和结果记录、一份"它做不到什么、什么情况必须你来"的诚实说明。

最后，记住全书的结论：Agent 的价值不在于它会说多少，而在于它在明确的目标、合适的工具、可控的权限和可靠的验证下，持续完成真实工作。你造出的这个 Agent，能不能让你下周还愿意用它、敢把真事交给它，就是毕业与否的唯一标准。
