# PART 6：Agent 由什么组成——四个基本系统，加一个扩展接口层

> 先导图：Agent 构成概念地图（待插入 F11：中央是"推理系统 Model"，周围并列"信息系统""行动系统""编排系统"三个环，最外层是一圈"扩展接口层"，Result 收在中心）

## 本章你要解决什么问题

前面几个 Part，我们一直在讲"怎么把一件事交给 Agent 做"：怎么下任务、怎么管长任务、怎么验收、怎么识别它会怎么失败。到这一章，才正式打开发动机盖。

先立一个判断标准：本章不要求你会写代码，也不要求背术语全称。你只需要做到——下次听到一个新名词时，能把它对号入座，知道它大概在解决哪类问题、和隔壁概念有什么不一样。

## 一张总览图：不是五层，是四个系统加一个接口层

过去流行把 Agent 画成"五层架构"，把 Model 放在最上、把扩展件压在中间某一层。这个画法的问题是：它把"能力本身"和"能力怎么接进来"混成了一层，越学越乱。

更干净的画法是：Agent 由**四个基本系统**构成，再由**一个扩展接口层**负责把外部能力接进来。四个系统是"它本身是什么"，接口层是"它怎么向外伸手"。

```text
            ① 推理系统 Model
            谁在思考和决策
                ▲
   ② 信息系统   │   ③ 行动系统
   现在知道什么   │   以前记得什么
   任务做到哪     │   材料太多怎么办
   怎么作用于外部世界
                ▼
            ④ 编排系统
        谁决定先做什么后做什么

   ┌─────────────────────────────────────┐
   │  扩展接口层：API / Connector / Plugin │
   │  / MCP / Skill                       │
   │  不是"第五个系统"，而是接入和封装机制  │
   └─────────────────────────────────────┘
```

用一句话压住这张图：

> 一个 Agent，就是"一个会思考的 Model"，在"信息"和"手脚"的支持下，由"编排"把这些能力组织成一次任务；而它能用哪些信息和手脚，是靠最外面那圈接口层接进来的。

为什么要这么分？因为同一个词，在不同位置含义完全不同。比如"工具"：行动系统讲的是 Search、File 这种**动作本身**；扩展接口层讲的是把动作**包装成可插拔单元**。不分清楚，就会把"一只手"和"一双手套"当成一个东西。

下面每一节只回答三件事：**它是什么 / 为什么需要它 / 它和谁最容易混**。各平台具体怎么做，统一收进"现实世界实现"框里，不打断主线。例子尽量引用前面已经做过的 Mission——PART 1 的文件整理、PART 3 的断点续跑、PART 4 的网页核验。

## ① 推理系统 Model：谁在思考和决策

### 6.1 是什么

Model 就是这个 Agent 的"脑子"。所有理解、推理、写句子、做计划、决定"下一步该调用哪个工具"，都是它在干。没有 Model，后面所有信息、手脚、流程都只是一堆不会动的零件。

几乎所有 Agent 背后都是"一个主模型 + 若干配套模型"：主模型负责理解与决策，有的产品再配一个小模型做分类、摘要、路由，或配多模态模型负责看图、听音频。模型本身按"一次给它一段输入、它吐一段输出"来计费和运行，Agent 是在这个循环外面套上信息、手脚和编排的外壳。

### 6.2 为什么需要它

因为"这个任务该用哪种脑子"是一个真实的决策点，不是玄学。让它改一段跑不通的代码，和让它写一封客气的请假邮件，用的模型往往不是同一个。下次任务没做好，先别急着重写 Prompt，先判断是不是"这次该换个脑子"。

挑脑子不靠排行榜，靠八把尺子，每一把对应一类真实痛点：

| 维度 | 大白话 | 什么时候这把尺子重要 |
|---|---|---|
| Reasoning | 能不能一步步把难题想明白，而不是凭直觉瞎答 | 复杂决策、改 bug、做分析、写论证 |
| Coding | 能不能看懂、写出、改对可运行的代码 | 让它动文件、做数据处理、改软件 |
| Context Window | 这一次对话它最多能同时看进去多少字、多少文件 | 你要一次塞几十篇论文、一整个文件夹 |
| Tool Calling | 能不能准确决定调用哪个工具、参数填对没有 | 只要任务要联网、读文件、操作外部系统，这一条就是命门 |
| Computer Use | 能不能看懂屏幕截图、移动鼠标、点按钮 | 需要它操作没有 API 的老式网页或桌面软件 |
| Multimodal | 能不能看图、看表、看截图、听音频 | 你要给它 PPT 截图、手写笔记、图表照片 |
| Latency | 多久回你一句 | 你在等它连续操作，或做即时对话 |
| Cost | 每用一次花多少钱 | 长任务反复跑、自动化每天跑，账单会堆起来 |

更省事的思路：**简单任务用快的、便宜的；难任务切到强推理的；做检查的那一步，最好换一个和执行者不同的模型。**

### 6.3 和谁最容易混

最容易和"信息系统"混在一起。Context Window 这把尺子看起来是在讲 Model，其实它是 Model 和信息系统的交界处——窗口大小是 Model 的出厂规格，但"窗口里塞什么"是信息系统在管。看到一个名词跨了两个系统，不要纠结它算哪边，问它在解决哪类问题就行。

> **现实世界实现（平台差异）**
> ChatGPT、Gemini 这类对话产品：模型选择藏在"自动/高级"档位里，高级用户可手动切型号。Claude、Codex 这类偏编程/Agent 的产品：更强调"推理档"和"执行档"分开，常让你在同一任务里切换或串联。Cursor 这类 IDE 内嵌产品：模型选择直接暴露在编辑器角落，且对"补全""对话""改代码"分别允许选不同模型。
> 底层事实：各平台的模型名单、档位、价格、能力边界变化极快，本节不点名具体型号，也不做排行榜。任何排名都活不过一个季度，以你所用平台 2026 年 9 月的官方文档为准。

**真实例子：同一个任务，换"脑子"的差别**

下面三个例子都来自本教程配套项目 `examples/my-agent/` 的真实运行记录，不是编的：

- **要逐步排错的活，用强推理档。** `agent.log` 里有这么一段：第一次跑 `计算 2+3*4`，计算器报错 `module 'ast' has no attribute 'Num'`——因为老写法用了 `ast.Num`，而 Python 3.14 已经把它移除了。后来把 `tools.py` 里的判断改成 `isinstance(node, ast.Constant)`，再跑才输出 `14`。这种"读报错、定位版本差异、改对一处"的活，靠快模型的直觉是改不对的，得用会一步步推理的脑子。
- **客套、格式化的活，用便宜快档。** 让它把一段会议纪要改成一封客气的请假邮件，不涉及推理，快档几秒出活，强推理档是浪费。
- **做检查的那一步，换一个脑子。** 按 6.2 那句"做检查的那一步最好换一个和执行者不同的模型"，写完综述后，换一个模型当挑刺人，专门问它"这十条论断里，哪条我没给来源"——用同一个模型自己审自己，容易护短。

这三个例子合起来说明一件事：**推理系统不是"装一个最强模型就完事"，而是按任务类型在"快/便宜"和"强推理"之间换挡。**

## ② 信息系统：现在知道什么、以前记得什么、做到哪了

这个系统解决"信息"问题：Agent 这一次睁眼能看到什么、关了机还记得什么、要查自己资料库时去哪查、任务做到哪一步。四个概念从"临时"到"长期"、从"现成"到"检索"，排成一个连续谱。

### 6.4 Context：这一次睁眼看到的全部

**是什么。** Context 就是模型"这一次睁眼时，眼前摊着的全部东西"：你这轮打的字、它刚才的回答、你拖进来的文件、搜到的网页、它刚读出来的文件内容。它只能基于眼前这些东西回答。模型自己"记不住你电脑里有什么"，也不知道你是谁。

**为什么需要它。** 记住一句话：**你不放进 Context 的东西，等于不存在。** 这也是前面讲过的"上下文污染"和"最小充分上下文"的根源——眼前堆太多会被带偏，给太少它会瞎编。你让它"改这篇论文的引言"，就必须把论文全文（至少引言）放进 Context，否则它只能凭空写一段漂亮但和你论文无关的话。

**和谁最容易混。** 和 Memory 混。Context 是"这一次睁眼看到的"，对话一结束就没了；Memory 是"跨对话留下来的"。一个活在当下，一个活在跨次。

### 6.5 Memory：跨对话留下来的

**是什么。** 每次新开对话，模型都是"失忆"的。Memory 就是平台帮你跨对话保留的那部分信息：你偏好的格式、你常用的背景、上次做到哪、它帮你总结过的笔记。

**为什么需要它。** 这样你不用每次从头自我介绍。两种主流做法：一种是产品自动把你说过的偏好存成"长期记忆"，下次自动带进来；另一种是你自己在项目里放一个说明文件（如 README、AGENTS.md 这类"岗位说明书"），让它每次开工前先读。后者本质上是你手写的 Memory，比自动记忆更可控。

**和谁最容易混。** 和 State 混。Memory 记的是"关于你"的长期事实；State 记的是"关于这件事进行到哪"的进度。你告诉过它"我是马克思主义理论方向、在做计算社会科学"——这是 Memory；它告诉你"已经处理完前 80 个文件"——这是 State。

### 6.6 State：任务进行到哪一步

**是什么。** State 是任务进行中的中间信息：现在做到第几步、已经试了哪几条路、哪些文件已经改过、当前假设是什么。它介于 Context 和 Memory 之间——比一次对话的 Context 活得长，又不像 Memory 那样是"关于你"的长期事实。

**为什么需要它。** 这正是 PART 3 断点续跑那个 Mission 的核心。让它整理 200 个文件，中途崩了，有 State 的 Agent 下次开工能说"已经处理完前 80 个，从第 81 个继续"；没有 State 的只能从头再来。长任务里，学会时不时问一句："你现在做到哪一步了？已经完成了什么？下一步打算干什么？"让它把 State 说出来，你才不会以为它停了、或重复劳动。

**和谁最容易混。** 和 Memory 混，上一节已说清。另外它和"结果文件"也要分开：State 是"进度记录"，不是"最终交付物"。

### 6.7 RAG：材料太多装不下怎么办

**是什么。** RAG（Retrieval-Augmented Generation，检索增强生成）的做法是：先把你的资料切块存进一个"小图书馆"，每次提问时，先从里面挑出最相关的几段，再把这几段喂给模型回答。它解决的是"资料太多，Context 装不下"的问题。

**为什么需要它。** 平台先把文档切块、做索引（通常是把文字转成向量，再按相似度检索）；提问时先跑一次检索，把最相关的几段抓出来，连同你的问题一起放进 Context。所以 RAG 不是"让模型记住你全部资料"，而是"每次临时把相关几段翻出来给它看"。你把一学期 30 份 PPT 灌进 RAG，之后问"第三章讲的那个模型有什么局限"，它会先找出第三章相关段落再回答，而不是凭训练记忆瞎编。

**和谁最容易混。** 和 Memory 混。Memory 存的是零散的、关于你的偏好；RAG 存的是成体系的资料库，靠"相似度"临时翻出来。最大的风险是**检索出来的片段不对题**，所以要养成习惯：要求它每次回答都标"这段依据来自哪份文件哪一段"，标不出来源的，不要信。

> **现实世界实现（平台差异）**
> Context：有的产品窗口大、长对话不太需要你管；有的窗口小，多聊几轮就"忘事"。编程类产品（Codex、Cursor）往往主动把整个项目文件结构读进来当 Context，对话类产品默认只放当前对话。差异不在"有没有 Context"，而在"它替你自动塞了多少、超了窗口怎么处理"。
> Memory：有的对话产品有显式"个人记忆"开关和查看页，你能看到它记了你什么、能随时删；有的编程产品完全靠项目里的说明文件，没有自动记忆。前者省心但可能记错，后者啰嗦但完全透明。
> RAG：有的产品提供现成"知识库"，拖文件进去就建好索引；有的需要你自己搭索引、自己配检索逻辑。差异在"谁来建索引"，原理都是"先检索、再生成"。
> State：偏"一次性对话"的产品基本没有显式 State，聊完就结束；偏"长任务/异步任务"的产品会有任务列表、断点续跑、中间产物留存。

**真实例子：四个概念，落到一个文件上看**

把这四个概念落到本教程 `examples/my-agent/` 的真实文件上，一眼就能分清：

- **Context（这一次睁眼看到的）**：就是 `agent.py` 里的 `self.history` 列表，每一轮 `chat()` 往里塞一条 `{"role": "user"/"assistant", "text": ...}`。对话一关，这个列表就没了。
- **Memory（跨对话留下来的）**：对应 `system_prompt.txt` 里那段"你是一个助教式 Agent，服务于零基础学习者……"，以及项目里手写的 README。它记的是"关于你、关于这个岗位"的长期事实。
- **State（这件事做到哪了）**：就是真实存在的 `state.json`，内容是 `{"task_status": "done", "turns": 8, "last_message": "检索笔记 Agent 零件"}`。下一次开工，`_load_state()` 读它，就知道上次跑到第 8 轮。**这正是 PART 3 断点续跑那个 Mission 的代码版**——没有这个文件，下次就得从 0 轮重来。
- **RAG（材料太多临时翻出来）**：对应 `tools.py` 里的 `search_notes`。`agent.log` 里真实跑过一次"检索笔记 工具 安全"，它返回 `note_02_tools_safety.md`（命中 21 次）、`note_04_plan_exec_eval.md`（12 次）、`note_03_rag_simplified.md`（9 次）——这就是"先从 docs/ 里挑最相关的几段，再喂给模型"的实物。注意：它是词频打分，不是向量检索，这是教学简化。

一句话：**你不放进 Context 的东西等于不存在；而 State 让你崩了能从第 81 个文件接着做，RAG 让你不用把 30 份 PPT 全塞进窗口。**

## ③ 行动系统：怎么作用于外部世界

这个系统是 Agent 直接碰现实世界的"原始手"。和扩展接口层的区别在于：这里讲的是**动作本身**，是未包装的原子能力。

### 6.8 Search：联网查最新事实

**是什么。** 模型的训练数据有截止日期，也不可能背下全世界所有网页。Search 就是让它像你打开搜索引擎那样，去网上查最新的、具体的、它训练时没见过的信息。

**为什么需要它。** 凡是涉及"今天的事实"——最新政策、刚发布的论文、某软件现在的版本号——都该让它搜。让它查"2026 年某领域最新的综述"，它必须真的去搜，而不是凭训练记忆列几篇三年前的老文章。

**和谁最容易混。** 和 Browser 混。Search 是"输入关键词，看返回的链接和摘要"；Browser 是真的打开网页、点鼠标、翻页。PART 4 那个网页核验的 Mission 之所以要动用 Browser，正是因为 Search 返回的摘要不够、必须进到网站里把内容"读出来"。

### 6.9 Browser：真的打开网页操作

**是什么。** 很多信息藏在搜索引擎返回不了的地方：需要登录的后台、要点几下才展开的表格、要翻页的论坛帖子。Browser 就是让 Agent 真的打开一个浏览器，像人一样看屏幕、点鼠标、敲键盘。

**为什么需要它。** "把某份公开榜单前 50 名连同公司名、成立时间、融资轮次抓成一张表"——搜索做不到（结果分散在十几页），浏览器可以逐页翻。它在真操作网页时，你应该在旁边看着第一步点的对不对，尤其是涉及登录、下单、发消息的页面。

**和谁最容易混。** 和 Computer Use 混。两者边界见下表。

### 6.10 Computer Use：直接操作整个桌面

**是什么。** 有些软件根本没有网页版、没有 API，只有桌面客户端，或是一个很老的系统。Computer Use 就是让 Agent 直接看你的整个屏幕、移动鼠标、敲键盘，像一个远程坐在你电脑前的人。

**为什么需要它。** 让它打开你电脑上某个只能用 Windows 客户端的老系统，按步骤改尺寸、导出图片——它真的会移动你的鼠标，你会在屏幕上看到光标自己动。第一次开这个能力时全程盯着，它动鼠标就是真的动你的鼠标，误点一个"确认删除"就是真删。

**和谁最容易混。** 和 Browser、Code Execution 三者最容易混，用一张表划清：

| 能力 | 活动范围 | 自由度 | 风险 |
|---|---|---|---|
| Browser | 只在浏览器标签页里 | 中 | 中 |
| Computer Use | 整个桌面、任何软件 | 最高 | 最高 |
| Code Execution | 隔离的代码沙箱 | 受限 | 较低 |

### 6.11 File System：读你硬盘上的文件

**是什么。** 你的论文、PPT、Excel、下载的资料都存在硬盘文件夹里。File System 访问就是让 Agent 能读、新建、改、整理你电脑上的文件。没有它，你只能一个个手动把文件拖进对话框。

**为什么需要它。** PART 1 第一个 Mission"整理混乱的下载文件夹"，靠的就是这只手：它真的去建文件夹、移动文件，而不只是口头建议。原则是：永远告诉它"只在这个文件夹里工作，不要碰别的地方"，原始材料留备份，让它去改副本。

**和谁最容易混。** 和 Terminal 混。文件工具通常只做"读、写、列文件夹"这类相对安全的操作；Terminal 是更底层、更通用的命令通道。

### 6.12 Terminal：敲命令指挥电脑

**是什么。** Terminal（终端/命令行/Shell）是你用鼠标点图标之外，另一种指挥电脑的方式：直接敲一行文字指令，电脑照做。Agent 要装软件、跑脚本、看系统状态、动 Git，很多时候靠敲命令完成。

**为什么需要它。** 让它跑一个开源项目，它可能敲一行把项目下载下来，再敲一行装依赖，再敲一行启动。中间任何一行写错，影响的都是你的真实环境。你自己一般不需要学敲命令，你需要会问："你这条命令打算干什么？"尤其带删除、覆盖、联网下载含义的命令，让它解释一遍再放行。

**和谁最容易混。** 和 Code Execution 混。Terminal 在真实系统里，Code Execution 在隔离小房间里——这是两者最本质的区别。

### 6.13 Code Execution：在隔离沙箱里跑代码

**是什么。** 遇到算数、统计、画图表、清洗 Excel、批量处理文件这类活，让模型"心算"是靠不住的——它会算错、会编数字。Code Execution 是给它一个隔离的小环境，让它真写一小段代码、真运行、真把结果打印出来。结果是跑出来的，不是它猜的。

**为什么需要它。** 任何涉及精确数字的活——数据清洗、回归分析、画统计图、批量改名、合并表格——都让它用代码执行，而不是"看着表格估算"。并要求它把"跑出来的代码和结果"都留在工作文件夹里，方便你回头复查：代码能重跑，结果才算数。

**和谁最容易混。** 和 Terminal 混，上一节已划清。它和 File System 的关系：它读文件、写结果通常也在一个受限目录里，而不是你整台硬盘。

### 6.14 API：软件之间的标准对话窗口

**是什么。** 你想用某款软件的功能，但不想打开它的界面、不想手动点。API（Application Programming Interface，应用程序接口）就是软件之间"对话用的标准窗口"：你不用进厨房，通过传菜口下单，菜从窗口递出来。软件厂商对外开一组"接口地址"，你用一串身份凭证（API Key）去调用，它返回数据或执行动作。

**为什么需要它。** 让 Agent "把你飞书日历里明天的会列出来"，它就是通过飞书开放的 API，以你的身份去读日历数据。判断一个 Agent 强不强，API 能调哪些，本身就是能力的一部分。

**和谁最容易混。** 和扩展接口层的 Connector 混。API 是技术通道，需要自己填密钥、自己拼调用；Connector 是把这种通道包装好、给普通用户用的成品。API 属于"动作"，Connector 属于"接入和封装"——这正是本章反复强调的那条分界线。

> **现实世界实现（平台差异）**
> Search：有的产品默认常开，模型自己决定什么时候查；有的默认关，要你显式说"搜一下"；有的还接了学术库、代码库这类垂直搜索。
> Browser / Computer Use：有的产品把浏览器操作做成一键工具；有的需要你开"网页操作"权限；有的能让你看到实时画面，有的在后台静默跑。Computer Use 有的在隔离虚拟机里跑，不碰你本机。能力越强，越要在隔离环境里开。
> File System：有的只让它访问你主动拖进去的文件；有的允许访问整个项目文件夹；有的默认隔离沙箱，碰不到你本机真实目录。原则都是越窄越好。
> Terminal：编程类产品（Codex、Cursor 等）几乎把它当标配，因为跑项目、装依赖、跑测试都要它；普通对话产品一般不给，或放在隔离环境里。有 Terminal 的产品风险也最高。
> Code Execution：几乎所有主流产品都带某种代码执行，差别在沙箱里预装了哪些库、能不能联网、能跑多久。
> API：普通对话产品一般不让你直接手写 API 调用，而是把常见服务封装成 Connector 或 Plugin；编程类产品允许它自己写代码去调任意 API。

**真实例子：每只"手"都对应一件你真干过的事**

行动系统的七只手，每只都能落到一个你已经做过的 Mission 上：

- **Search ← PART 4**：让它查"2026 年某领域最新综述"，它必须真去搜，而不是凭训练记忆列三年前的老文章。这是 PART 4 网页核验 Mission 的第一只手。
- **Browser ← PART 4**：PART 4 之所以要开 Browser，是因为 Search 返回的摘要不够，必须进到网站里把榜单逐页"读出来"。Search 给链接，Browser 才真翻页。
- **Computer Use**：让它操作一个只有 Windows 客户端的老系统、移动你屏幕上的光标——第一次开全程盯着，误点"确认删除"就是真删。
- **File System ← PART 1**：PART 1 第一个 Mission"整理混乱的下载文件夹"靠的就是这只手——它真去建文件夹、移文件，不是口头建议。铁律：只让它在指定文件夹里干活，原始材料留备份。
- **Terminal**：让它 `git clone` 一个项目、装依赖、跑测试（LAB F 里 `git clone --depth 1` 就是这只手）。中间任何一条写错，影响的是你真实环境。
- **Code Execution**：`examples/my-agent/tools.py` 里的 `calculator` 就是一只受限的手——它在 AST 白名单里算 `2+3*4` 得 14，但你喂它 `__import__('os').system('echo hi')`，它直接拒掉，报错"表达式只允许数字和 + - * / // % ** 运算"。**结果是跑出来的，不是它猜的。**
- **API**：让它读你飞书日历明天的会，走的就是飞书开放 API。判断一个 Agent 强不强，API 能调哪些本身就是能力。

一句话：**这七只手，从"只读一个网页"到"动你整个桌面"，自由度和风险一路上涨；越往右，越要在隔离环境里开。**

## ④ 编排系统：谁决定先做什么后做什么

前三个系统是零件，这个系统是"项目经理"：把零件组织成一次真实任务。它回答的不是"能不能做"，而是"先做什么、后做什么、要不要派人、要不要停下来问人"。

### 6.15 Workflow：把多步任务固定下来

**是什么。** 复杂任务不是一句话说完的，而是一连串步骤：搜、筛、读、建表、分析、写、查。Workflow 就是把这一串步骤固定下来，下次同类任务直接按这条流水线走，不用每次重新指挥。

**为什么需要它。** 当你发现自己每周都在重复同一套多步操作时，就该把它画成一张箭头图：第一步出什么、第二步凭什么、最后怎么验收。"每天早上 8 点，搜今天的行业新闻，和昨天的摘要对比，有重大变化才把摘要推给我"——这就是一条固定 Workflow。

**和谁最容易混。** 和 Automation 混。Workflow 是"步骤怎么排"（菜谱），Automation 是"什么时候自动跑这条 Workflow"（定时器）。

### 6.16 Planner：让它自己规划路线

**是什么。** Planner（规划器）是编排里更"自主"的一面：不预设死步骤，而是让 Model 在开工前先列一份计划，执行中再根据结果调整。它和 Workflow 的关系是：Workflow 是你写死的流水线，Planner 是它自己现想现走。

**为什么需要它。** 面对"调查 X 公司"这种步骤事先排不全的任务，硬套一条死 Workflow 反而捆住手脚；让它先规划、再执行、边执行边修正，更合适。但 Planner 的风险是它会跑偏、会自作主张加步骤，所以关键节点要设"停下来给你看"的检查点。

**和谁最容易混。** 和 Workflow 混（如上），也和 Sub-agent 混。Planner 决定"路线"，Sub-agent 决定"派谁去走某一段"。

### 6.17 Sub-agent：临时派出去的分身

**是什么。** 一个 Agent 自己干长了，会顾不过来、会忘、会串味。Sub-agent 就是主 Agent 临时派出去的"分身"：一个负责搜资料，一个负责读文件，一个负责写初稿，最后主 Agent 把三份结果汇总。分身之间默认互不可见，只通过主 Agent 传话。

**为什么需要它。** 主 Agent 接到"调查 X 公司"，派子 Agent A 查工商信息、B 查新闻舆情、C 查产品；A、B、C 各交一份摘要，主 Agent 合并成最终报告。但记住：分身越多，汇总成本和出错率越高。新手先把单 Agent 跑顺，再考虑拆分；派出去的分身，交回来的东西也要验收——它不会因为叫"子 Agent"就自动可靠。

**和谁最容易混。** 和 Planner 混（如上）。它也容易被和"多开几个对话"混为一谈：区别在于 Sub-agent 是系统帮你派、帮你汇总；你自己手动开多个对话再自己拼，那不叫 Sub-agent，那叫手动编排。

### 6.18 Automation 与 Human Approval：什么时候自动跑、什么时候停下问你

**是什么。** Automation 是把 Workflow 接上一个"闹钟"或"触发器"：定时跑、收到邮件跑、网页变了跑。Human Approval（人工确认）则是反过来的一道闸：到了关键步骤，它必须停下来等你点头才继续。

**为什么需要它。** 第一版自动化一定先设成"跑完先把结果给我看，别自己发出去"。跑稳两周、你确认它不会乱来，再逐步放开发送权限。这和 PART 前面讲过的验收原则一脉相承：越是不可逆的动作，越要把 Human Approval 这道闸留在最后。适合全自动的事有规律、触发条件明确、且低风险；高风险、需要你每次判断的事不适合。

**和谁最容易混。** 和 Workflow 混（如上）。它也常被和"权限"混：Automation 决定"要不要停下来问"，权限分级（PART 7 的 L1–L4）决定"哪类动作必须问"——两者配合，但不是一回事。

> **现实世界实现（平台差异）**
> Workflow：偏自动化的产品有专门的工作流画布，节点、条件、循环都能配；普通对话产品没有显式 Workflow，靠你在任务里口述步骤。脑子里的流程和画布上的流程，原理相同。
> Sub-agent：有的产品有显式"派子任务"机制；有的靠你手动开多个对话再自己汇总；编程类产品常把不同文件、不同模块分给不同子 Agent。差异在"分身是系统帮你派，还是你自己拆"。
> Automation：有的产品有专门"自动化/定时任务"页，能设 cron 式时间表；有的只能在工作流画布里接触发器；普通对话产品基本没有 Automation。差异在"触发器好不好设、能不能无人值守"。
> Human Approval：有的产品在执行 L3/L4 动作前自动弹确认；有的默认全自动，需要你自己在设置里把关键动作设成"需人工确认"。

**真实例子：编排系统的四个零件，落到 my-agent 和 daily_monitor 上**

- **Workflow（步骤固定）**：`examples/my-agent/pipeline.py` 的 `run_task()` 就是一条小流水线——先 `plan()` 把任务拆成步骤，再 `execute()` 顺序调用工具，最后 `evaluate()` 用断言验收。下次同类任务直接走这条线。
- **Planner（它自己现想现走）**：同一个 `pipeline.py` 里的 `plan()`，按关键词把"计算 2+3*4 并检索笔记 Planner"拆成两步：先算、再检索。教学版是模板，真项目里换成强推理模型来规划。
- **Sub-agent（临时派分身）**：主 Agent 接到"调查 X 公司"，派 A 查工商、B 查舆情、C 查产品，各自交摘要，主 Agent 合并。分身越多，汇总成本越高——新手先把单 Agent 跑顺。
- **Automation + Human Approval**：`examples/automation/daily_monitor.py` 是 Automation 的活（每天 8 点抓 GitHub Release）；`agent.py` 里的 `DANGEROUS_PATTERNS = ["删除","发送","覆盖",...]` 命中就走 `_ask_approval()`，停下问你 `y/N`——`agent.log` 里真实记录了两条：`删除旧备份 config.bak` 被批准、`发送全部客户邮件` 被拒绝。**第一版自动化一定先设成"跑完给我看，别自己发出去"。**

一句话：**前三个系统是零件，编排系统是把零件组织成一次任务的项目经理；Human Approval 就是它在关键节点必须停下来等你点头的那道闸。**

## 扩展接口层：能力怎么接进来

四个系统回答了"Agent 本身是什么"，还有最后一个问题：**它能用的这些能力，是从哪接进来的？** 这就是扩展接口层。

它不是"第五个系统"。系统是 Agent 本身的器官，接口层是它向外接线、封装能力的机制。API、Connector、Plugin、MCP、Skill 都长在这一层——它们不是并列的五种零件，而是"接入和封装"的五种不同实现。下一章（PART 7）会专门讲怎么安全地发现、安装、验证、撤销它们，这里只先把概念边界划清。

- **API**：最底层的技术通道。你自己填密钥、自己拼调用。它是"传菜口"本身。
- **Connector**：把 API 包装好、给普通用户点一下就能用的成品线。通常走 OAuth 登录授权，偏"把你个人的某个账号接进来"。
- **Plugin**：平台定义的一类扩展包。**注意它不必然是"官方商店成品"**——不同平台的 Plugin 内部可能包含 Tool、Skill、Connector 等不同能力，边界以你所用平台的定义为准。它是"平台帮你打包好的一块功能"。
- **MCP（Model Context Protocol）**：一套让工具按统一标准暴露自己的协议。它**不是"写一次到处可用"的魔法**，而是"降低多客户端重复适配的成本"；具体兼容性仍取决于客户端支持的 MCP 版本、transport、auth 和 capabilities。它是"传菜口的统一规格"。
- **Skill**：把"怎么做某件专业事"写成一个可复用的包（一份 SKILL.md 加模板、脚本、示例）。它更像一份"操作手册加工具箱"，而不是一个按钮。

一个类比收尾：API 是传菜口，MCP 是传菜口的统一规格，Connector 是餐厅已经帮你接好的成品线，Plugin 是餐厅直接给你上的一桌菜，Skill 是一份"这道菜该怎么炒"的手册。这五个词在不同平台经常混用，别纠结名字，看它实际碰了什么数据、干了什么活。

为了把这层讲死，下面这张表把五种实现放在同一张坐标里比。读它的方法：从左到右，是"从最底层技术通道"到"最像一份说明书"的光谱；越靠左越要你自己动手、越靠右越像点一下就能用，但封装得越好、你能审计的空间反而越小。

| 维度 | API | Connector | Plugin | MCP | Skill |
|---|---|---|---|---|---|
| 它是什么 | 最底层技术通道 | 把 API 包成"点一下" | 平台定义的扩展包 | 工具自描述的统一协议 | 一份操作手册加工具箱 |
| 你要做的动作 | 自己填 Key、自己拼请求 | 点"连接"+走 OAuth 授权 | 在商店点"安装" | 在配置文件写一段+重启 | 丢一个文件夹+刷新识别 |
| 它碰什么数据 | 按你写的请求决定 | 你授权的那个账号 | 包内作者定义 | Server 自己暴露的目录/接口 | 被指示去读的文件 |
| 要什么钥匙 | API Key（自己管） | 账号 OAuth 通行证 | 平台商店账号 | 配置里那把 Key | 一般不用钥匙 |
| 失败长什么样 | 401/403、拼错参数 | 授权页 scope 勾错 | 装上却要额外权限 | 配了连不上、版本不兼容 | 放对位置却没被识别 |
| 怎么撤 | 去服务商后台删 Key | 账号侧 Settings 里 Revoke | 商店里卸载 | 删配置那一段再重启 | 删文件夹再确认无残留 |
| 本教程的真实例子 | 自己写代码调飞书 API | 点"连接 GitHub"走 gh 授权 | 装官方 PDF 插件 | filesystem MCP 暴露一个沙箱目录 | minimax-pdf 这类 SKILL.md |

一句话压表：**API 是你亲手接线，Connector 是别人帮你接好线，Plugin 是别人连菜都炒好端上桌，MCP 是给所有传菜口定了同一个尺寸，Skill 是塞给你一本菜谱。** 越往右越省心，越要在"装之前"把 7.3 的 12 问过一遍——因为封装得越好，里面干了什么你越看不见。

**Mission 6-A：给你手上的 Agent 画一张"四系统+接口层"图**

拿你最近在用的那个 Agent，逐格回答：推理系统用哪个 Model、看重哪把尺子？信息系统这一轮能看到哪些 Context、有没有 Memory、要不要 RAG、长任务有没有 State？行动系统开了哪几只手（Search、Browser、File、Terminal、Code、API）？编排系统是 Workflow 还是 Planner、会不会派 Sub-agent、哪些动作会停下来问你？扩展接口层接了哪些 Connector / Plugin / MCP / Skill？你会立刻发现自己之前一直在"裸用"，很多能力其实没开。

**Mission 6-B：判断一次失败到底卡在哪个系统**

回想最近一次它没做好的任务。对着四系统判断：是推理系统 Model 不够聪明？还是信息系统没给够（漏了材料、该检索没检索）？还是行动系统手没开（该让它搜它没搜）？还是编排系统乱了（步骤没串好、分身派错了）？定性之后，下次任务对症下药，而不是只会重写一遍 Prompt。

**Mission 6-C：分清三对最容易混的概念**

用自己的话写三句话：Context 和 Memory 差在哪？Search 和 Browser 差在哪？MCP 和 Connector 差在哪？写不出人话版，就回去重读对应那一节。这三对分清了，这一章就过关了。

# PART 7：能力供应链——怎么安全地给 Agent 加能力

> 先导图：能力供应链闭环图（待插入 F15：从"我缺一种能力"出发，依次经过"发现来源→判断可信度→读权限→安装→沙箱验证→升级→撤销"，最后回到"我缺一种能力"的循环）

## 本章你要解决什么问题

上一章讲清楚了 Agent 由哪些系统组成，以及能力是靠最外面那圈接口层接进来的。本章解决一个非常实际的问题：**这些能力不是出厂全装好的，很多要你自己去"插上去"**。

但这一章的主线，不是教你"怎么装"，而是教你把装能力当成一条**能力供应链（Capability Supply Chain）**来管：

> 我缺一种能力 → 去哪里发现 → 如何判断这个来源靠不靠谱 → 如何读懂它要的权限 → 如何安装 → 如何在沙箱里先验证 → 如何升级 → 如何撤销。

Skill、Plugin、MCP、Connector 只是这条供应链上不同的"包装形式"。贯穿全章的铁律只有一句：

> 不要看到社区资源就装，而是会审计。GitHub 上的 Star 数不等于安全，商店里的"热门推荐"不等于对你合适。每装一个，你都要知道它碰了什么数据、能干什么动作、钥匙放在了哪里。

## 7.1 能力从哪来：模型出厂，扩展后来

模型出厂时只会做一件事：读一段文字，吐一段文字。它不能读你电脑里的论文，不能查今天的新闻，不能动你的 Excel，也不能替你发邮件。这些"超能力"全是后来通过接口层接上去的。

所以判断一个 Agent 到底强不强，不要只看它用了多牛的 Model，而要看：它接了哪些 Tool、装了哪些 Skill / Plugin / MCP、连了哪些你的账号、你给了它多大操作权限。**模型决定天花板，扩展能力决定它能不能下地干活。**

## 7.2 发现：三层资源地图

不要靠刷社交平台碰运气。在心里建立一张资源地图，按三层去找，越靠上越可信：

1. **官方来源**：你所用 Agent 平台的官方文档、官方 Skill 商店、官方 GitHub 组织、官方 MCP 注册中心（registry.modelcontextprotocol.io）。信息最准、维护最勤，先查这里。
2. **聚合发现平台**：社区目录（如 SkillsMP、skills.sh 这类）会聚合公开的 Skill、MCP、Plugin，方便你搜索。它们的价值是"让你发现"，**不是让你直接装**。看到感兴趣的，记下来，回到第三层。
3. **源仓库**：打开这个 Skill / MCP 的 GitHub 或官方源码页，看谁做的、最近提交时间、Star 和 Issue 活跃度、README、License、有没有脚本、要什么权限。

> 一句话：**发现靠聚合站，决定靠源仓库。** 聚合平台上的排名、评分、"热门""推荐"，只代表它被很多人发现，不代表它安全、适合你、还在维护。

## 7.3 判断来源：读 SKILL.md 加 12 问

`SKILL.md` 就是一个 Skill 的"产品说明书加岗位说明书"，纯文本、几百行以内，用记事本就能打开。打开后按这个顺序读：

| 你要找的信息 | 它通常写在哪 | 你要判断什么 |
|---|---|---|
| 这个 Skill 是干嘛的 | 开头简介 | 和你要做的事对不对得上 |
| 支持哪些 Agent / 平台 | 安装说明 | 你用的平台装不装得上 |
| 前置条件 | Requirements / Prerequisites | 要不要额外装软件、要不要账号 |
| 读哪些文件、写哪些文件 | 权限说明 / 工作方式 | 会不会动到你的原始材料 |
| 会不会联网、会不会调付费 API | 网络/费用说明 | 会不会偷偷跑钱、外发数据 |
| 附带什么脚本 | Files / Scripts | 脚本是最需要警惕的部分 |
| 怎么卸 | Uninstall | 装之前先确认能撤 |

读完后，在心里过一遍这 12 问：

1. 来源是谁？是知名公司官方仓库，还是匿名账号？
2. 源代码在哪里？能不能看到完整代码，而不是只有"一键安装"？
3. 最近有没有维护？最近一次提交是上周还是三年前？
4. 它会执行什么脚本？有没有和宣传功能无关的操作？
5. 它能读什么文件？会不会去翻你的文档、桌面、下载文件夹？
6. 它能写什么文件？会不会往系统目录、配置目录塞东西？
7. 它能访问哪些网站 / API？除了该用的服务，还会不会连到别的地址？
8. 它需要哪些账号权限？连邮箱时是"只读"还是"能发邮件"？连 GitHub 时是"只读代码"还是"能替你 push"？
9. 它会不会把我的数据发到第三方？
10. 它会不会调用付费 API？跑一次花多少钱、有没有上限？
11. 它有没有删除、覆盖、修改能力？误操作能不能找回来？
12. 能不能先在测试目录跑一遍？

特别强调两句话：**Star 数不等于安全**（热门只说明流行，不说明干净）；**"官方"两个字要看清楚**（有些聚合站名字带 Official，不代表它是某家公司官方办的，认准域名和 GitHub 组织名）。

打开一个 Skill 文件夹，里面通常有三类东西：说明文档（最安全，纯文本）、模板和资产（半成品、示例，本身不会自己跑，风险低）、**脚本（真正会被执行的代码，风险最高）**。看不懂脚本写了什么，就把它丢给 Agent，问："这段脚本从头到尾干了什么？有没有删文件、联网、发数据的动作？"

## 7.4 读权限：用 gh CLI 把 OAuth 和 scope 看清楚

当你点"连接邮箱"时，跳出来的登录页问你"是否允许 XX 应用访问你的邮箱"——背后走的是 **OAuth**：你不把账号密码告诉这个应用，而是通过官方登录页给它发一张有时效的通行证。

要把这件事看清楚，最适合当"活标本"的是 GitHub 官方命令行工具 `gh`。**注意：gh CLI 本身是一个开发者工具，不是一个 Connector；这里用它，只是因为它把 OAuth 的授权、scope、撤销全过程暴露得最清楚，方便你理解任何 Connector 的授权页。**

在这台 Windows 机器上真实走一遍：

**第一步：看当前授权状态。**

```powershell
gh auth status
```

真实输出大意：已登录到 github.com，当前账号为 TZUKWAN，token 存在系统密钥环里，**当前 token 的权限范围（scopes）是 `gist, read:org, repo, workflow`**。这串 scopes 就是"OAuth 授权边界"的实物——你一眼能看到：它能读写仓库（repo）、能操作工作流（workflow）、能读组织信息（read:org）、能写 Gist（gist），但它**没有** `delete_repo` 这种删除权限，也没有 `admin:org` 这种管理员权限。这就是授权该有的样子：能做的列得清清楚楚，不该有的没有。

**第二步：理解每个 scope 的含义。**

| 它请求的 scope | 翻译成大白话 | 该不该给 |
|---|---|---|
| `repo` | 能读、写你的仓库代码 | 你要让它动代码，就给 |
| `workflow` | 能改 GitHub Actions 工作流 | 你要让它自动跑 CI，才给 |
| `read:org` | 只读你所在组织的信息 | 一般够用 |
| `delete_repo` | **能删仓库** | 没有明确需要就别勾 |

第一次跑 `gh auth login` 选浏览器登录，它会打开 GitHub 官方页面，列清楚这次要哪些权限，你同意后才拿到通行证。**关键不是这个机制多方便，而是你在那个页面上要逐行看：它要的每一项权限，是不是你真打算给的。**

**第三步：事后收权或撤销。**

```powershell
gh auth refresh -s read:org   # 重新走一次浏览器授权，收缩或扩大 scope
gh auth logout                # 一键撤销本机这张通行证
```

更彻底的做法，是直接去 GitHub 网页的 Settings → Applications → Authorized OAuth Apps 里，找到这个应用，点 Revoke。**这和后面 7.9 讲的"去账号侧撤销授权"是同一个动作。**

Notion、Slack、Google Workspace 这类真正的 Connector，本机无法替你登录授权（需要你本人账号、验证码、二次确认），但流程和 gh 一模一样：点连接 → 跳到官方登录页 → **逐行看权限** → 同意 → 回来核对授权状态。差别只在登录页是哪家公司的，授权那一页你要做的事完全相同。

## 7.5 安装：四种实现各是什么

接口层的四种包装形式，安装动作各有侧重。**别把它们想成"四种零件"，它们是同一条供应链上四种不同的封装。**

### 7.5.1 装 Skill

通用动作四步：找到它 → 读它的 SKILL.md → 放进指定位置（通常是一个叫 skills 的文件夹，不同平台路径不同）→ 重启或刷新让它认识。

以本机真实目录走一遍（**命令路径是这台机器的真实情况，照做时换成你自己的用户名和平台路径**）。先看本机有哪些 Skill：

```powershell
Get-ChildItem "$env:USERPROFILE\.claude\skills" -Directory | Select-Object Name
```

本机真实存在的包括 `arxiv-research`、`minimax-pdf`、`find-skills`、`skill-creator` 等。按关键词找：

```powershell
Get-ChildItem "$env:USERPROFILE\.claude\skills" -Directory | Where-Object { $_.Name -match 'pdf|research' } | Select-Object Name
```

源仓库核验：看一个已装 Skill 的最后提交时间（仅当它本身是 git 仓库时才有输出）：

```powershell
git -C "$env:USERPROFILE\.claude\skills\minimax-pdf" log -1 --format="%ci  %s"
```

权限审计：打开 SKILL.md 前 60 行，再看它带了哪些文件、有没有可执行脚本：

```powershell
Get-Content "$env:USERPROFILE\.claude\skills\minimax-pdf\SKILL.md" -TotalCount 60
Get-ChildItem "$env:USERPROFILE\.claude\skills\minimax-pdf" -Recurse | Select-Object FullName, Length
```

判断标准回到 7.3 的表和 12 问：出现"联网下载""删除文件""读环境变量外发"这类字眼，先打问号。装完测试：重启 Agent，对它说"请读一下这个 Skill 的 SKILL.md，然后用它处理我这个 PDF"，再丢一个小 PDF 试一次。

> 标注：**"在你自己的 Agent 产品里加载并测试"这一步，本教程运行环境无法替你完成**——那是另一个图形化产品里的交互，不在这台命令行机器上。你需要在自己的产品里实际开一次，确认它真的认识这个 Skill、真按说明书走了。

### 7.5.2 装 Plugin

**先纠正一个常见误解：Plugin 不必然是"官方商店成品"。** 准确说法是：Plugin 是平台定义的一类扩展包；不同平台的 Plugin 内部可能包含 Tool、Skill、Connector 等不同能力，边界以你所用平台的定义为准。

落到安装动作上：Plugin 通常来自平台官方商店，你在界面上点"安装"，它就挂上了。相对省心，但"平台商店"不代表"绝对安全"——你依然要在安装弹窗里看一眼它要什么权限、会不会收费、会不会读你的账号数据。商店审核一般会拦住明显的恶意件，但审不到"这个插件是否过度收集你的数据"这种灰色问题。

### 7.5.3 添加 MCP Server

**再纠正一个常见误解：MCP 不是"写一次到处可用"的魔法。** 准确说法是：MCP 降低了多客户端重复适配同一工具的成本；但一个 MCP Server 能不能在你的客户端里正常工作，仍取决于客户端支持的 MCP 版本、transport（stdio / HTTP / SSE 等）、auth 方式和 capabilities。所以配完一定要实测连通性，不能"配置写对了就以为能用了"。

添加方式：在你的 Agent 配置文件里写一段"我要用哪个 MCP Server、它怎么启动、钥匙放哪"，改完重启。不同平台配置文件位置和格式不同，**不要照抄网上三年前的教程**，以你所用客户端官方文档为准。

以官方维护、用途明确的 `filesystem` MCP Server 为例（它只做一件事：把你指定的一个文件夹暴露给 Agent 读写，适合第一次试手）。在常见的 Claude 系客户端配置 JSON 里加一段（**格式只作示意，键名和路径以官方文档为准**）：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "D:\\AISOP\\mcp-sandbox"
      ]
    }
  }
}
```

这段配置的关键，是把它可访问的目录**限定**在 `D:\AISOP\mcp-sandbox` 这一个文件夹。**这一步是 MCP 安全的核心：只给它一个专用沙箱目录，不要把整个用户目录或 C 盘根目录填进去。**

改配置前，先单独跑一下启动命令，确认包能拉起来、不报错：

```powershell
npx -y @modelcontextprotocol/server-filesystem "D:\AISOP\mcp-sandbox"
```

它启动后通常会停在那里等标准输入（因为 MCP 是通过 stdin/stdout 对话的进程），看到它没报错、没立刻退出，就说明这一步通了，按 `Ctrl+C` 退出。

> 标注：**"用一个最小 MCP 客户端脚本真正连上、列出工具、调用一次"这一步，需要你在自己的开发环境里写几行客户端代码，或用客户端自带的连接测试功能来做。** 原理是：启动上面那个进程，按 MCP 协议握手，让它报出自己提供了哪些工具（一般是 read_file、write_file、list_directory 之类），再调一次 `list_directory` 看能不能列出沙箱目录里的文件。本教程运行环境不替你执行这一步。如果连不上，先查三件事：npx 在不在、目录路径写对没有、客户端有没有重启加载新配置。

添加 MCP 同样要过 12 问：这个 Server 是谁写的？它要访问什么？要什么密钥？会不会把数据转给第三方？一个标着"MCP"的开源 Server，本质和一个 Skill 一样，是会跑的代码。

### 7.5.4 添加 Connector

Connector 是最贴近普通用户的扩展方式：界面上一个"连接邮箱""连接日历""连接云盘"的按钮，点一下，跳到你那个账号的登录页，授权，回来就连上了。它把技术细节包起来了，你不用碰配置文件——但授权那一步要做的事，和 7.4 用 gh CLI 演示的一模一样：逐行看 scope，别直接滑到底点同意。

## 7.6 密钥放哪：环境变量的真实定位

**先纠正一个误解：环境变量不是"保险箱"。** 它真正解决的问题是"不要把 Secret 写进代码和 Git"——仅此而已。真正的密钥保护，应优先使用系统凭据库、Secret Manager，或你所用平台自己的 Secrets 功能。

为什么这么说？把 API Key 直接写在对话 Prompt 里，是最危险的做法：你在对话框里贴一次，它就可能被记进聊天历史、被模型日志带走；写进代码再提交到 GitHub，业界每年都有成百上千个 Key 因为误传公开仓库被自动化扫描器扫走、被盗刷。环境变量的作用，是让 Agent 要用 Key 时按约定的名字去取，而不是每次从对话里读到、更不是写进代码提交。

在 Windows 上临时看一眼当前有哪些 Key 类环境变量名（**只看名字，不要把值打印出来**）：

```powershell
Get-ChildItem env: | Where-Object { $_.Name -match 'KEY|TOKEN|SECRET' } | Select-Object Name
```

各平台设置环境变量的入口不同（有的在设置页，有的在配置文件里，有的在系统环境变量里），以平台文档为准。你只需要建立这个习惯：

> 凡是钥匙类的东西（API Key、Token、密码），优先用系统凭据库 / Secret Manager / 平台 Secrets；代码和 Git 里不写死、对话里不粘贴。环境变量是中间手段，不是终极保险箱。

另外记住 API Key 的三条铁规矩：不要写进普通对话 Prompt；不要提交到公开仓库；Key 要能随时作废、随时重发（每个服务商后台都有"重新生成 / 作废旧 Key"的功能，怀疑泄露就立刻换）。

## 7.7 沙箱验证：先在干净地方跑一次

供应链里最容易被跳过、却最关键的一环是**沙箱验证**：装完别急着拿真材料试，先在一个干净的、可丢弃的文件夹里跑一次。

做法很朴素：

1. 建一个专用沙箱目录（如上面 MCP 例子里的 `D:\AISOP\mcp-sandbox`），往里放一份副本文件，不要用原始材料。
2. 让新装的 Skill / Plugin / MCP 在这个目录里干一次它该干的活。
3. 观察三件事：它有没有跑出你预期的结果？它有没有去碰沙箱以外的目录？它有没有发起你没预料到的联网请求或付费调用？
4. 都正常，再回到真实任务里用；任何一项不对，按 7.9 撤销。

## 7.8 最小权限：L1–L4 风险分级表

装上了能力，就要管住它能干什么。核心原则一句话：**只给完成这件事所需的最小权限，多一分都不给。**

把 Agent 的所有可能动作，按"做错了能不能收回来"分成四级：

| 风险级别 | 典型动作 | 默认策略 |
|---|---|---|
| **L1 低风险** | 读文件、搜索网页、分析数据副本、读你给的材料 | 可以自动执行，不用每次问你 |
| **L2 可逆修改** | 新建文件、改工作副本、在 Git 上建分支、改草稿 | 可以执行，但要留记录（改了什么、改前是什么） |
| **L3 高影响** | 覆盖你原来的文件、Git push 到远程、改云端共享文档、替你发消息或邮件 | 建议每一步都停下来让你确认 |
| **L4 不可逆 / 高风险** | 删除数据、支付、公开发布、改生产数据库、改权限、对外发正式公告 | 必须你明确说"确认执行"才做，且最好先备份 |

一个朴素的判断：**凡是错了找不回来的事，最后那一下永远你自己按。**

## 7.9 升级与撤销：让供应链能闭环

### 7.9.1 撤销 / 卸载

装上去的东西，要能撤下来。三种动作要分清：

- **临时禁用**：Agent 里往往有开关，把某个 Skill / Plugin / MCP 关掉，它暂时不生效，但文件还在。适合"现在不想用，以后可能还开"。
- **卸载**：把这个扩展从 Agent 里移除。适合"确定不用了"。以本机 Skill 为例，删掉文件夹再确认无残留：

```powershell
Remove-Item "$env:USERPROFILE\.claude\skills\minimax-pdf" -Recurse -Force
Test-Path "$env:USERPROFILE\.claude\skills\minimax-pdf"
```

第二条应返回 `False`。但光删文件夹不算完整卸载——如果它在配置文件里登记过、或连过你的账号，还要去配置里移除、去对应账号撤销授权。
- **撤销账号授权**：如果它连了你的邮箱 / GitHub / 云盘，去对应账号的第三方授权页把它踢掉——光在 Agent 里卸载，有时你那个账号上的授权还挂着。

一个好习惯：每季度花十分钟，去常用账号（邮箱、GitHub、云盘、社交平台）的"第三方应用授权"列表里扫一眼，把不认识、不再用的授权全部撤销。

### 7.9.2 升级

社区件会更新：修 bug、加功能、改权限。但**不要开启全自动更新**。理由很简单：一个昨天还干净的 Skill，今天的版本可能加了联网、加了付费调用。正确姿势：

1. 更新前先看更新说明（changelog / release notes）——这版改了什么？
2. 尤其注意"新增了什么权限、新增了什么网络请求、新增了什么依赖"。
3. 更新后跑一次你常用的 Mission，确认它没跑偏。
4. 出问题就回到上一个版本。

平台官方商店的 Plugin 更新相对省心，但也别假设"官方更新 = 对你更好"。

### 7.9.3 完整走一遍：用 filesystem MCP 把供应链八环走穿

前面七节是拆开讲零件，这一小节把它们串成一条真实操作链。**目标能力**：让 Agent 安全地读写 `D:\AISOP\mcp-sandbox` 这一个文件夹，别的地方碰不到。照着走一遍，以后装任何 Skill / Plugin / MCP 都是这条链。

**第 0 环：我缺一种能力。** 我发现每次都得手动把文件拖进对话框，想让 Agent 自己在一个专用文件夹里读写。需求说清楚：**只要一个文件夹的读写权，不要全盘。**

**第 1 环：发现来源。** 先去官方 MCP 注册中心 `registry.modelcontextprotocol.io`，搜 filesystem，找到官方维护的 `@modelcontextprotocol/server-filesystem`。**不是**从聚合站搜一个 Star 最多的就装。

**第 2 环：判断可信度。** 打开它的源仓库：作者是 ModelContextProtocol 官方组织、License 是开源许可、最近有提交、Issue 区有人在维护。再读一遍它的 README——它只做一件事：把你指定的目录暴露出去。这一步过 7.3 的 12 问，重点看第 4、5、6、7 问：它跑什么脚本、读哪些文件、写哪些文件、连哪些地址。

**第 3 环：读权限。** 它不要 OAuth（不是连你个人账号），但它要"文件系统读写"这只手。关键动作是：**在启动参数里只填那一个沙箱目录**，把权限收窄到最小：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "D:\\AISOP\\mcp-sandbox"]
    }
  }
}
```

注意那个 `D:\\AISOP\\mcp-sandbox`——**这就是最小权限的实物**。填成 `D:\\` 或用户根目录，就等于把整盘交给它。

**第 4 环：安装。** 把上面这段写进你客户端的 MCP 配置文件，重启客户端让它认识。

**第 5 环：沙箱验证。** 别急着接真活。先单独跑启动命令，确认包拉得起来：

```powershell
npx -y @modelcontextprotocol/server-filesystem "D:\AISOP\mcp-sandbox"
```

它启动后停在那里等标准输入（MCP 走 stdin/stdout 对话），看到没报错、没立刻退出，按 `Ctrl+C` 退出。然后在客户端里调一次 `list_directory`，确认它只能列出沙箱里的文件；再试一次让它读沙箱外的路径，确认它拒掉。**三样都对：结果对、不越界、没有没预料的联网或付费。**

**第 6 环：升级。** 它更新时，先看 release notes 改了什么，尤其看"新增了什么权限、什么网络请求、什么依赖"。**不开自动更新**——昨天干净的版本，今天可能加了联网。更新后跑一次你常用的 Mission，确认没跑偏。

**第 7 环：撤销。** 不用了，就把配置文件里那一段 `filesystem` 删掉，重启客户端，确认它的工具列表里 `list_directory` 已经消失。这个 MCP 不连你个人账号，所以不用再去账号侧 Revoke；但如果是连了 GitHub / 邮箱的 Connector，撤销这一环必须回到对应账号的"第三方应用授权"页踢掉它——光在 Agent 里卸载，你账号上的授权可能还挂着。

走完这七环，你就给以后装所有扩展打了个样。**记住：发现靠聚合站，决定靠源仓库；装之前先在沙箱跑一遍；不用了能干净撤掉。**
