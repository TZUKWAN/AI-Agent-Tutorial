# PART 6：Agent 到底由什么组成

> 先导图：Agent 五层认知结构图（待插入 F11：Model 在最上，向下依次是"记忆与上下文""感官与操作""扩展能力""编排"，Result 收在最底的分层关系图）

## 本章你要解决什么问题

前面五个 Part，我们一直在讲"怎么把一件事交给 Agent 做"：怎么下任务、怎么管长任务、怎么验收、怎么识别它会怎么失败。但你心里可能一直有个没说出口的疑问：它到底是个什么东西？为什么有的事它能做，有的事它做不了？为什么同一个任务，换个模型、开个插件，结果就不一样？

到这一章，我们才正式打开发动机盖。

请记住一个判断标准：本章不要求你会写任何一行代码，也不要求你背下任何一个术语的英文全称。你需要做到的是——下次听到一个新名词时，能把它对号入座到这张五层图里，知道它大概在解决什么问题，知道它和隔壁概念有什么不一样。这就够了。

## 一张总览图：Agent 的五层结构

不要被下面这堆名词吓到。它们其实可以压成一句话：

> 一个 Agent，就是"一个足够聪明的模型"，在"信息"和"手脚"的支持下，把这些能力按"一套编排"组织起来，持续地把一件事做完，最后交出一个结果。

对应到五层，每一层只解决一类问题：

```text
第一层   Model（模型）            —— 脑子：它有多聪明、多快、多贵
   │
第二层   记忆与上下文              —— 信息：它此刻能看到什么、跨次记得什么、
   │                                   去哪检索、任务进行到哪一步
   │        Context / Memory / RAG / State
   │
第三层   感官与操作                —— 原始通道：它直接碰现实世界的七只手
   │        Search / Browser / Computer Use / File System /
   │        Terminal / Code Execution / API
   │
第四层   扩展能力                  —— 封装：把通道标准化、产品化、可插拔
   │        Tool / Connector / Plugin / MCP / Skill
   │
第五层   编排                      —— 调度：把以上四层组织成一次任务
            Workflow / Sub-agent / Automation
   │
   ↓
        Result（结果：最后交出来的东西）
```

你可以把它想象成一个刚入职的员工：Model 是他的脑子；第二层是他桌上摊着的材料、抽屉里的笔记本、公司资料室、以及他正在做的进度看板；第三层是他本人伸手够得到的电话、打印机、电脑、文件柜；第四层是公司给他办的门卡、接好的专线、买好的软件订阅、以及一份培训手册；第五层是项目经理，把这一切安排成流程、分身和定时任务。

为什么要分五层，而不是像零件清单那样平铺？因为同一个名词，在不同层的含义完全不同。比如"工具"：第三层讲的是搜索、读文件这种**原始动作**；第四层讲的是把这些动作**包装成可插拔单元**。不分层，就会把"一只手"和"一双手套"当成一个东西，越学越乱。

下面 20 节，每一节都用同一套五段模板，只回答这五个问题：

1. **概念本身**：它是什么（通用定义，不绑定任何平台）；
2. **常见实现**：各平台通常怎么做；
3. **不同平台差异**：ChatGPT / Claude / Codex / Gemini / Cursor 这类产品分别长什么样；
4. **零基础用户掌握到什么程度**：你要学到哪一步就够；
5. **一个实际例子**：拿一件真事说清楚。

## 第一层：Model（模型）

### 6.1 Model（模型）

**1. 概念本身**

Model 就是这个员工的"脑子"本身。所有理解、推理、写句子、做计划、决定"下一步该调用哪个工具"，都是它在干。没有 Model，后面所有工具、记忆、流程都只是一堆不会动的零件。

**2. 常见实现**

几乎所有 Agent 产品背后都是"一个大语言模型（LLM）+ 若干配套模型"：主模型负责理解与决策，有的产品会再配一个小模型做分类、摘要、路由，或配多模态模型负责看图、听音频。模型本身是按"一次给它一段输入、它吐一段输出"来计费和运行的，Agent 是在这个循环外面套上工具和记忆的外壳。

**3. 不同平台差异**

- ChatGPT、Gemini 这类对话产品：模型选择对普通用户藏在"自动/高级"等档位里，高级用户可在设置里手动切具体型号。
- Claude、Codex 这类偏编程/Agent 的产品：更强调"推理档"和"执行档"分开，常让你在同一个任务里切换或串联不同模型。
- Cursor 这类 IDE 内嵌产品：模型选择直接暴露在编辑器角落，且针对"补全""对话""改代码"分别允许选不同模型。
- 底层事实：各平台的模型名单、档位、价格、能力边界变化极快，本节不点名任何具体型号，也不做排行榜。任何排名都活不过一个季度，以你所用平台 2026 年 9 月的官方文档为准。

**4. 零基础用户掌握到什么程度**

你要学的不是"哪个模型最强"，而是"挑脑子的八把尺子"，每一把对应一类真实痛点：

| 维度 | 大白话 | 什么时候这把尺子重要 |
|---|---|---|
| Reasoning（推理能力） | 能不能一步步把难题想明白，而不是凭直觉瞎答 | 复杂决策、改 bug、做分析、写论证 |
| Coding（写代码能力） | 能不能看懂、写出、改对可运行的代码 | 让它动文件、做数据处理、改软件 |
| Context Window（上下文窗口） | 这一次对话它最多能同时看进去多少字、多少文件 | 你要一次塞 40 篇论文、一整个文件夹 |
| Tool Calling（工具调用） | 它能不能准确地决定调用哪个工具、参数填对没有 | 只要任务要联网、读文件、操作外部系统，这一条就是命门 |
| Computer Use（电脑操作） | 它能不能看懂屏幕截图、移动鼠标、点按钮 | 需要它操作没有 API 的老式网页或桌面软件 |
| Multimodal（多模态） | 它能不能看图、看表、看截图、看音频 | 你要给它 PPT 截图、手写笔记、图表照片 |
| Latency（响应速度） | 它多久回你一句 | 你在等它连续操作，或者做即时对话 |
| Cost（成本） | 每用一次花多少钱 | 长任务反复跑、自动化每天跑，账单会堆起来 |

更省事的思路：**简单任务用快的、便宜的；难任务再切到强推理的；做检查的那一步，最好换一个和执行者不同的模型。** 知道"原来可以换"，就已经超过绝大多数用户了。

**5. 一个实际例子**

让 Agent 改一段跑不通的代码，和让它写一封客气的请假邮件，用的模型往往不是同一个。前者要 Reasoning 和 Coding 都强；后者反应快、便宜、语气自然的模型就够。下次任务没做好，先别急着重写 Prompt，先判断是不是"这次该换个脑子"。

## 第二层：记忆与上下文

这一层解决的是"信息"问题：Agent 这一次睁眼能看到什么、关了机还记得什么、要查自己资料库时去哪查、任务做到哪一步了。四个概念从"临时"到"长期"、从"现成"到"检索"，正好排成一个连续谱。

### 6.2 Context（上下文）

**1. 概念本身**

Context（上下文）就是模型"这一次睁眼时，眼前摊着的全部东西"：你这轮打的字、它刚才的回答、你拖进来的文件、搜索到的网页、它刚读出来的文件内容。它只能基于眼前这些东西回答。模型自己"记不住你电脑里有什么"，也不知道你是谁。

**2. 常见实现**

平台把当前对话里的全部内容压进一个"窗口"里发给模型。窗口有上限（即 Context Window），装不下时，产品通常会自动截断最旧的消息、或把旧内容总结成摘要再塞回去。你拖进去的文件、它读到的网页，最终也都是被转成文字、塞进这个窗口。

**3. 不同平台差异**

有的产品窗口大、长对话不太需要你管；有的窗口小，多聊几轮就开始"忘事"，需要你手动开新对话或重新贴材料。编程类产品（如 Codex、Cursor）往往会主动把整个项目文件结构读进来当 Context，对话类产品则默认只放当前对话。差异不在"有没有 Context"，而在"它替你自动塞了多少、超了窗口怎么处理"。

**4. 零基础用户掌握到什么程度**

记住一句话：**你不放进 Context 的东西，等于不存在。** 这也是 PART 5 讲过的"上下文污染"和"最小充分上下文"的根源——眼前堆太多会被带偏，给太少它会瞎编。

**5. 一个实际例子**

你让它"帮我改这篇论文的引言"，就必须把论文全文（至少引言）放进 Context，否则它只能凭空写一段漂亮但和你论文无关的话。

### 6.3 Memory（记忆）

**1. 概念本身**

每次新开对话，模型都是"失忆"的。Memory（记忆）就是平台帮你跨对话保留下来的那部分信息：你偏好的格式、你常用的背景、上次做到哪一步、它帮你总结过的笔记。这样你不用每次从头自我介绍。

**2. 常见实现**

两种主流做法：一种是产品自动把你说过的偏好存成"长期记忆"，下次自动带进来；另一种是你自己在项目里放一个说明文件（如 README、AGENTS.md 这类"岗位说明书"），让它每次开工前先读。后者本质上是你手写的 Memory，比自动记忆更可控。

**3. 不同平台差异**

有的对话产品有显式的"个人记忆"开关和查看页，你能看到它记了你什么、能随时删；有的编程产品完全靠项目里的说明文件，没有自动记忆。前者省心但可能记错，后者啰嗦但完全透明。没有哪种绝对更好，取决于你愿不愿意自己掌控。

**4. 零基础用户掌握到什么程度**

会检查"它这次记得的，是不是还是对的"。Memory 的风险是会记错、记偏、把过时信息一直带着。发现它拿旧印象套新任务，直接纠正。重要背景宁可每次在任务里明说，也别全押在"它应该记得"上。

**5. 一个实际例子**

你告诉过它"我是马克思主义理论方向、在做计算社会科学"。自动记忆型产品下次会自动带上这个背景；说明文件型产品则靠你在项目里写一句。两种方式目的一样：让它不用每次重新认识你。

### 6.4 RAG（检索增强生成）

**1. 概念本身**

RAG（Retrieval-Augmented Generation，检索增强生成）的做法是：先把你的资料切块存进一个"小图书馆"，每次提问时，先从里面挑出最相关的几段，再把这几段喂给模型回答。它解决的是"资料太多，Context 装不下"的问题。

**2. 常见实现**

平台先把你的文档切成小块、做索引（通常是把文字转成向量，再按相似度检索）；提问时先跑一次检索，把最相关的几段抓出来，连同你的问题一起放进 Context。所以 RAG 不是"让模型记住你全部资料"，而是"每次临时把相关几段翻出来给它看"。

**3. 不同平台差异**

有的产品提供现成的"知识库"功能，你拖文件进去它就建好索引，问答时自动检索；有的需要你自己搭索引、自己配检索逻辑。前者面向普通用户，后者面向有技术能力的人。差异在"谁来建索引"，原理都是"先检索、再生成"。

**4. 零基础用户掌握到什么程度**

会要求它每次回答都标"这段依据来自哪份文件哪一段"。RAG 最大的风险是**检索出来的片段不对题**，标不出来来源的，不要信。

**5. 一个实际例子**

你把一学期 30 份 PPT 灌进 RAG，之后问"第三章讲的那个模型有什么局限"，它会先从这 30 份里找出第三章相关段落再回答，而不是凭训练记忆瞎编。

### 6.5 State（状态）

**1. 概念本身**

State（状态）是任务进行中的中间信息：现在做到第几步了、已经试了哪几条路、哪些文件已经改过、当前假设是什么。它介于 Context 和 Memory 之间——比一次对话的 Context 活得长，又不像 Memory 那样是"关于你"的长期事实，而是"关于这件事进行到哪了"的进度记录。

**2. 常见实现**

长任务型 Agent 通常会维护一份"工作记录"：已完成的步骤、待办、中间产物路径、失败过的尝试。有的把它写进项目里的一个进度文件，有的存在平台自己的后台，对话中断后下次接着跑时先读这份记录。

**3. 不同平台差异**

偏"一次性对话"的产品基本没有显式 State，聊完就结束；偏"长任务/异步任务"的产品会有任务列表、断点续跑、中间产物留存。差别在于：这个任务是你盯着它一次做完，还是它挂在后台自己跑几小时。

**4. 零基础用户掌握到什么程度**

长任务里，学会时不时问一句："你现在做到哪一步了？已经完成了什么？下一步打算干什么？" 让它把 State 说出来，你才不会以为它停了、或重复劳动。

**5. 一个实际例子**

让它整理 200 个文件。中途它崩了，有 State 的 Agent 下次开工能告诉你"已经处理完前 80 个，从第 81 个继续"；没有 State 的只能从头再来。

## 第三层：感官与操作

这一层是 Agent 直接碰现实世界的七只"原始手"。它们和第四层的区别在于：这里讲的是**动作本身**，是未包装的原子能力。你可以把它们理解成七只手，每只手擅长一类接触。

### 6.6 Search（搜索）

**1. 概念本身**

模型的训练数据有截止日期，也不可能背下全世界所有网页。Search（联网搜索）就是让它像你打开搜索引擎那样，去网上查最新的、具体的、它训练时没见过的信息。

**2. 常见实现**

平台接一个搜索服务，模型决定需要查时，发一个关键词，拿回一串链接和摘要，再自己读其中几条。本质是"输入关键词，看返回的链接和摘要"。

**3. 不同平台差异**

有的产品搜索默认常开，模型自己决定什么时候查；有的默认关，要你显式说"搜一下"；有的还接了学术库、代码库这类垂直搜索。差异在"默认开不开、接了哪几种搜索源"。

**4. 零基础用户掌握到什么程度**

知道"它给的每个事实性结论，最好都带回来源链接"。凡是涉及"今天的事实"——最新政策、刚发布的论文、某软件现在的版本号——都该让它搜。没带来源的事实，一律当成待核验。

**5. 一个实际例子**

让它查"2026 年某领域最新的综述"，它必须真的去搜学术库，而不是凭训练记忆列几篇三年前的老文章。

### 6.7 Browser（浏览器）

**1. 概念本身**

很多信息藏在搜索引擎返回不了的地方：需要登录的后台、要点几下才展开的表格、要翻页的论坛帖子、要点"加载更多"的评论区。Browser（浏览器控制）就是让 Agent 真的打开一个浏览器，像人一样看屏幕、点鼠标、敲键盘。

**2. 常见实现**

平台内置一个受控浏览器，模型看到网页截图或结构化内容，决定点哪个按钮、填哪个框。活动范围通常限定在浏览器标签页内。

**3. 不同平台差异**

有的产品把浏览器操作做成一键工具，点了就用；有的需要你开"网页操作"权限；有的能让你看到它正在操作的实时画面，有的在后台静默跑。越透明越可控。

**4. 零基础用户掌握到什么程度**

当 Search 返回的摘要不够用、必须进到网站里把内容"读出来"时，才用 Browser。它在真操作网页时，你应该在旁边看着第一步点的对不对，尤其是涉及登录、下单、发消息的页面。

**5. 一个实际例子**

"把某份公开榜单前 50 名连同公司名、成立时间、融资轮次抓成一张表"——搜索做不到（结果分散在十几页），浏览器可以逐页翻。

### 6.8 Computer Use（电脑操作）

**1. 概念本身**

有些软件根本没有网页版、没有 API，只有桌面客户端，或是一个很老的系统。Computer Use（电脑操作）就是让 Agent 直接看你的整个屏幕、移动鼠标、敲键盘，像一个远程坐在你电脑前的人一样操作任何软件。

**2. 常见实现**

平台定期截屏给模型看，模型输出"移到某坐标点一下、敲某段字"，系统执行。它的活动范围是整个桌面，不限于浏览器。

**3. 不同平台差异**

有的产品提供专门的"电脑操作"模式，屏幕共享给模型；有的把它和浏览器操作合在一起；有的在隔离的虚拟机里跑，不碰你本机。能力越强，越要在隔离环境里开。

**4. 零基础用户掌握到什么程度**

第一次开这个能力时全程盯着屏幕。它动鼠标就是真的动你的鼠标，误点一个"确认删除"就是真删。和相邻两只手的边界要清楚：

| 能力 | 活动范围 | 自由度 | 风险 |
|---|---|---|---|
| Browser | 只在浏览器标签页里 | 中 | 中 |
| Computer Use | 整个桌面、任何软件 | 最高 | 最高 |
| Code Execution | 隔离的代码沙箱 | 受限 | 较低 |

高风险操作前先让它停下来问你。

**5. 一个实际例子**

让它打开你电脑上某个只能用 Windows 客户端的老系统，按你说的步骤改尺寸、导出图片。它真的会移动你的鼠标——你会在屏幕上看到光标自己动。

### 6.9 File System（文件系统）

**1. 概念本身**

你的论文、PPT、Excel、下载的资料都存在硬盘的文件夹里。File System（文件系统）访问就是让 Agent 能读你电脑上的文件、新建文件、改文件、整理文件夹。没有它，你只能一个个手动把文件拖进对话框。

**2. 常见实现**

平台给它一组受限的文件操作接口：列目录、读文件、写文件、移动文件。通常先让你授权"允许访问哪个文件夹"，而不是整台电脑随便读。

**3. 不同平台差异**

有的产品只让它访问你主动拖进去的文件；有的允许它访问整个项目文件夹；有的默认隔离沙箱，碰不到你本机真实目录。差异在"授权范围多大"，原则都是越窄越好。

**4. 零基础用户掌握到什么程度**

永远告诉它"只在这个文件夹里工作，不要碰别的地方"。原始材料留备份，让它去改副本。它和 Terminal 的区别：文件工具通常只做"读、写、列文件夹"这类相对安全的操作，Terminal 是更底层、更通用的命令通道。

**5. 一个实际例子**

PART 1 的第一个 Mission"整理混乱的下载文件夹"，靠的就是这只手：它真的去建文件夹、移动文件，而不只是口头建议。

### 6.10 Terminal（终端 / 命令行）

**1. 概念本身**

Terminal（终端，也叫命令行、Shell）是你平时用鼠标点图标之外，另一种指挥电脑的方式：直接敲一行文字指令，电脑照做。Agent 要装软件、跑脚本、看系统状态、动 Git，很多时候靠敲命令完成。

**2. 常见实现**

平台给它一个命令行通道，它生成一行命令，系统执行并把输出回给它。它面对的通常是**你整台电脑**的真实环境，而不是隔离沙箱。

**3. 不同平台差异**

编程类产品（Codex、Cursor 等）几乎把 Terminal 当标配，因为跑项目、装依赖、跑测试都要它；普通对话产品一般不给 Terminal，或放在一个隔离环境里。有 Terminal 的产品，风险也最高。

**4. 零基础用户掌握到什么程度**

你自己一般不需要学敲命令。你需要会问："你这条命令打算干什么？" 尤其是带删除、覆盖、联网下载含义的命令，让它解释一遍再放行。它和 Code Execution 的区别：Terminal 在真实系统里，Code Execution 在隔离小房间里。

**5. 一个实际例子**

让它跑一个开源项目，它可能敲一行把项目下载下来，再敲一行把依赖装好，再敲一行启动。中间任何一行写错，影响的都是你的真实环境。

### 6.11 Code Execution（代码执行）

**1. 概念本身**

遇到算数、统计、画图表、清洗 Excel、批量处理文件这类活，让模型"心算"是靠不住的——它会算错、会编数字。Code Execution（代码执行）是给它一个隔离的小环境，让它真的写一小段代码、真的运行、真的把结果打印出来。结果是跑出来的，不是它猜的。

**2. 常见实现**

平台起一个临时沙箱（内置 Python 等运行环境），模型写代码、执行、看报错、改、再跑，最后把结论和图表交回来。沙箱用完即销毁，通常动不到你本机的重要文件。

**3. 不同平台差异**

几乎所有主流产品都带某种代码执行，差别在沙箱里预装了哪些库、能不能联网、能跑多久。数据类产品往往预装了一整套数据分析库，编程类产品更灵活但默认更干净。

**4. 零基础用户掌握到什么程度**

任何涉及精确数字的活——数据清洗、回归分析、画统计图、批量改名、合并表格——都让它用代码执行，而不是"看着表格估算"。并要求它把"跑出来的代码和结果"都留在工作文件夹里，方便你回头复查：代码能重跑，结果才算数。

**5. 一个实际例子**

你丢给它一个 5000 行的问卷 Excel，让它"按学院分组算平均分并画图"。它写一段代码跑出来，比让它心算可靠得多。

### 6.12 API（应用程序接口）

**1. 概念本身**

你想用某款软件的功能，但不想打开它的界面、不想手动点。API（Application Programming Interface，应用程序接口）就是软件之间"对话用的标准窗口"：你不用进厨房，通过传菜口下单，菜从窗口递出来。

**2. 常见实现**

软件厂商对外开一组"接口地址"，你用一串身份凭证（API Key）去调用，它返回数据或执行动作。Agent 要读日程、查数据库、调翻译，背后都是拼一个 API 调用。

**3. 不同平台差异**

普通对话产品一般不让你直接手写 API 调用，而是把常见服务封装成 Connector 或 Plugin；编程类产品允许它自己写代码去调任意 API。前者对你友好，后者灵活但要你自己管密钥。

**4. 零基础用户掌握到什么程度**

知道"它能调 API，就意味着它能以你的身份去读或写那个软件里的东西"。授权前想清楚：它能读哪些？能改哪些？它和第四层 Connector 的区别：API 是技术通道，需要自己填密钥、自己拼调用；Connector 是把这种通道包装好、给普通用户用的成品。

**5. 一个实际例子**

让 Agent "把你飞书日历里明天的会列出来"，它就是通过飞书开放的 API，以你的身份去读日历数据。

## 第四层：扩展能力

第三层是"原始的手"，这一层是"把手标准化、产品化、可插拔的包装"。五个概念抽象程度递增：Tool 是最小单元，Connector 接你的账号，Plugin 是成品功能，MCP 是通用插座标准，Skill 是教它怎么做专业活的手册。

### 6.13 Tool（工具）

**1. 概念本身**

没有工具的 Agent 本质上还是一张"嘴"：它能写、能分析、能出主意，但碰不到任何真实的东西。Tool（工具）就是给它接上的、可被它调用的一个个具体动作单元：一个搜索工具、一个读文件工具、一个跑代码工具。第三层那七只手，到了这一层就变成一个个有名字、有参数的 Tool。

**2. 常见实现**

每个 Tool 对外暴露三样东西：名字、它要什么参数、它干什么。模型在每一步决定"要不要调某个 Tool、参数填什么"，系统执行后把结果还给模型。所以"工具调用"是模型和现实世界之间的标准握手。

**3. 不同平台差异**

编程类产品（Codex、Cursor）把工具细到"读哪个文件、跑哪条命令"；对话类产品把工具做得更粗粒度（"联网搜索""画图"）。差异在"工具切得多细"，但握手方式都一样。

**4. 零基础用户掌握到什么程度**

知道"它每说一句要干活，背后必然调用了某个具体工具"，并会在它调用时瞄一眼"它现在碰的是哪个东西"。Tool 是抽象大类：Search、Browser、File System、API，以及下面的 Connector、MCP，本质都是 Tool 的具体形态。

**5. 一个实际例子**

你说"帮我把这个文件夹按类型分好类"，没有文件 Tool 它只能口头建议；有了 Tool，它才真的去建文件夹、移动文件。

### 6.14 Connector（连接器）

**1. 概念本身**

让普通用户也能用 API，不用懂技术。Connector（连接器）就是平台提前做好的"数据线"：你在界面上点一下"连接邮箱""连接日历""连接云盘"，走一个登录授权，Agent 就能读你邮箱、看你日程、动你云盘。

**2. 常见实现**

它通常走 OAuth 授权（见 PART 7 第 7.9 节）：点连接 → 跳到对方账号的官方登录页 → 列出要哪些权限 → 你同意 → 平台拿到一张有时效的通行证。技术细节被包起来，你只看到一个按钮。

**3. 不同平台差异**

各平台官方对接的服务清单不同：有的接了邮箱、日历、云盘全家桶；有的只接了少数几家；有的完全不做 Connector，全靠 MCP。差异在"官方帮你接好了哪几家"。

**4. 零基础用户掌握到什么程度**

每接一个 Connector，都去它的授权页看一眼："它现在能读我哪些东西？能替我做哪些事？"看完再点同意。它和 Plugin、MCP 的区别：Connector 偏"把你个人的某个账号接进来"，通常走登录授权；Plugin 偏"加一类功能"；MCP 偏"一套通用的、谁都能插的标准插座"。三者在不同平台经常混用，别纠结名字，看它实际碰了什么数据。

**5. 一个实际例子**

点一下连接你的邮箱账号，Agent 就能每天早上帮你看新邮件、归类、起草回复——但它能不能"替你真的发出去"，取决于你授权时勾没勾"发送"那一项。

### 6.15 Plugin（插件）

**1. 概念本身**

Plugin（插件）是平台打包好的一个"功能模块"：装一个幻灯片插件，Agent 就能读 PPT、写 PPT；装一个 PDF 插件，它就能拆 PDF、合并 PDF。本质是把一组相关的工具和使用说明打包在一起，让你一键开启。

**2. 常见实现**

插件通常来自平台官方商店，你在界面上点"安装"，它就挂上了，背后常连的是平台认证过的服务。有的插件是纯本地功能，有的一装上去就开始调某个在线服务。

**3. 不同平台差异**

早年对话产品的"插件商店"形态最典型；编程类产品里，类似能力更多以 Skill 或 MCP 的形式出现，而不叫 Plugin。到 2026 年，Plugin、Skill、MCP 三者边界仍在快速融合，以你所用平台的界面为准——界面上叫什么，你就当它是什么。

**4. 零基础用户掌握到什么程度**

装之前看三样：这个插件要什么权限、谁做的、最近还更不更新。不要看到"热门"就点。它和 Skill、MCP 的区别：Plugin 是商店式成品，装好就用；Skill 是一份"操作手册加工具箱"；MCP 是底层通用连接标准。

**5. 一个实际例子**

让它处理一个扫描版 PDF，纯文本模型读不了图；装一个 PDF 处理插件后，它就能识别里面的文字和表格。

### 6.16 MCP（Model Context Protocol，模型上下文协议）

**1. 概念本身**

早年每做一个工具，都要为每一个不同的 Agent 单独适配一遍——像每个国家的插头形状都不一样。MCP（Model Context Protocol）是 2024 年底开始被广泛采用的一套"万能插座标准"：任何按 MCP 标准写的工具（叫一个 MCP Server），理论上任何支持 MCP 的 Agent 都能直接插上用。

**2. 常见实现**

你在 Agent 的配置文件里写一段："我要用哪个 MCP Server、它怎么启动、钥匙放哪"。重启后，这个 Server 暴露的工具就自动出现在 Agent 的工具列表里。一个 MCP Server 可以被多个不同的 Agent 共用。

**3. 不同平台差异**

编程类产品（Claude 系、Codex 系等）对 MCP 支持最积极，配置写在各自的配置文件里；对话类产品有的支持、有的还不支持；MCP 的官方注册中心和客户端配置方式各平台不一。具体怎么写配置，以你所用客户端 2026 年 9 月的官方文档为准，不要照抄网上三年前的教程。

**4. 零基础用户掌握到什么程度**

知道"MCP Server 也是一段会跑的代码"，所以和装任何社区脚本一样，要先看它是谁做的、要什么权限。不要因为它"叫标准协议"就放松警惕。用一个类比收尾：API 是"传菜口"，MCP 是"传菜口的统一规格"，Connector 是"餐厅已经帮你接好的成品线"，Plugin 是"餐厅直接给你上的一桌菜"。MCP 本身不解决某个具体问题，它解决的是"别再一对一接线了"。

**5. 一个实际例子**

你配一个 GitHub 的 MCP Server，之后支持 MCP 的 Agent 就能读你的仓库、看 issue、查代码，不用你教它怎么调 GitHub API。完整安装演示见 PART 7 第 7.7 节。

### 6.17 Skill（技能）

**1. 概念本身**

教 Agent 做某件专业的事，光靠一次 Prompt 说不清楚。Skill（技能）就是把"怎么做这件事"写成一个可复用的包：里面有一份说明书（通常叫 SKILL.md）、一套模板、有时还附带现成脚本和示例素材。装上之后，Agent 遇到同类任务就按这套打法来。

**2. 常见实现**

一个 Skill 就是一个文件夹，核心是那份 SKILL.md（纯文本说明书），外加模板、脚本、示例。你把文件夹放进 Agent 的 skills 目录，它遇到相关任务时先读说明书再动手。它和 Plugin 的区别是：Plugin 是商店里点一下的成品功能，Skill 更像你从社区下载的一个文件夹，要自己放、自己读。

**3. 不同平台差异**

不同 Agent 产品对 Skill 的目录位置、加载方式命名不同（有的叫 skills 目录，有的叫别的），但"一个文件夹加一份 SKILL.md"的形态高度一致。编程类产品普遍支持用户自建 Skill；对话类产品更多用商店式 Plugin 替代。

**4. 零基础用户掌握到什么程度**

会打开一个 Skill 的 SKILL.md，读完前三段就知道"它想让 Agent 干什么、要碰什么文件、要联网吗"。当你发现"这件事我每次都要跟它解释半天、而且每次解释还不一样"时，就该把它沉淀成一个 Skill。完整安装与审计演示见 PART 7 第 7.2 节。

**5. 一个实际例子**

一个"学术综述写作 Skill"可能规定：先建证据矩阵、再按研究脉络分节、所有引用必须回原文核验、最后附未解决问题清单。装上它，你以后只要说"用综述 Skill 处理这批论文"，它就按这套流程走。

## 第五层：编排

前四层是零件，这一层是"项目经理"：把零件组织成一次真实任务。三个概念从"固定步骤"到"派分身"再到"定时自动跑"，抽象程度递增。

### 6.18 Workflow（工作流）

**1. 概念本身**

复杂任务不是一句话说完的，而是一连串步骤：搜、筛、读、建表、分析、写、查。Workflow（工作流）就是把这一串步骤固定下来，下次同类任务直接按这条流水线走，不用每次重新指挥。

**2. 常见实现**

有的产品提供可视化"拖节点连线"的工作流编辑器；有的就是你自己写在 Prompt 或说明文件里的一套固定步骤；有的是 Skill 里规定的流程。本质都是"第一步出什么、第二步凭什么、最后怎么验收"的箭头图。

**3. 不同平台差异**

偏自动化的产品有专门的工作流画布，节点、条件、循环都能配；普通对话产品没有显式 Workflow，靠你在任务里口述步骤。差异在"有没有把流程显式画出来"，脑子里的流程和画布上的流程，原理相同。

**4. 零基础用户掌握到什么程度**

当你发现自己每周都在重复同一套多步操作时，就该把它画成一张箭头图：第一步出什么、第二步凭什么、最后怎么验收。画清楚了，Workflow 就设计出来了。它和 Automation、Sub-agent 的关系见下面两节。

**5. 一个实际例子**

"每天早上 8 点，搜今天的行业新闻，和昨天的摘要对比，有重大变化才把摘要推给我"——这就是一条固定 Workflow。

### 6.19 Sub-agent（子智能体）

**1. 概念本身**

一个 Agent 自己干长了，会顾不过来、会忘、会串味。Sub-agent（子智能体）就是主 Agent 临时派出去的"分身"：一个负责搜资料，一个负责读文件，一个负责写初稿，最后主 Agent 把三份结果汇总。

**2. 常见实现**

主 Agent 把一个子任务连同必要的上下文交给一个新的、独立的 Agent 实例去跑，跑回来一份摘要或产物，主 Agent 合并。分身之间默认互不可见，只通过主 Agent 传话。

**3. 不同平台差异**

有的产品有显式"派子任务"机制；有的靠你手动开多个对话再自己汇总；编程类产品常把不同文件、不同模块分给不同子 Agent。差异在"分身是系统帮你派，还是你自己拆"。

**4. 零基础用户掌握到什么程度**

不是任务越复杂就越要开一堆分身。分身越多，汇总成本和出错率越高。新手先把单 Agent 跑顺，再考虑拆分。并且记住：派出去的分身，交回来的东西也要验收——它不会因为叫"子 Agent"就自动可靠。

**5. 一个实际例子**

主 Agent 接到"调查 X 公司"，派子 Agent A 查工商信息、B 查新闻舆情、C 查产品；A、B、C 各交一份摘要，主 Agent 合并成最终报告。

### 6.20 Automation（自动化）

**1. 概念本身**

最理想的状态是：这件事不用你每天去说，它到点自己跑、有事自己通知你、没事不打扰。Automation（自动化）就是把 Workflow 接上一个"闹钟"或"触发器"：定时跑、收到邮件跑、网页变了跑。

**2. 常见实现**

平台提供一个触发器（每天几点、某个事件发生）和一个动作（跑某条 Workflow、把结果发给你）。中间的 Workflow 照常是第四层、第三层那些能力在跑。

**3. 不同平台差异**

有的产品有专门的"自动化/定时任务"页，能设 cron 式时间表；有的只能在工作流画布里接触发器；普通对话产品基本没有 Automation。差异在"触发器好不好设、能不能无人值守"。

**4. 零基础用户掌握到什么程度**

第一版自动化一定先设成"跑完先把结果给我看，别自己发出去"。它和 Workflow 的关系：Workflow 是"步骤怎么排"，Automation 是"什么时候自动跑这条 Workflow"——前者是菜谱，后者是定时器。跑稳两周、你确认它不会乱来，再逐步放开发送权限。

**5. 一个实际例子**

每天早上抓一次 arXiv 上你关心方向的新论文，过滤后给你发一份 5 条摘要；有新论文才打扰，没有就静默。注意：这种事有规律、触发条件明确、且低风险，才适合全自动；高风险、需要你每次判断的事不适合。

## 本章 Mission

学完这一章，你不需要背术语，但要能完成下面三个任务。

**Mission 6-A：给你手上的一个 Agent 画一张"五层构成图"**

拿你最近在用的那个 Agent，从第一层到第五层逐层回答：它用的是哪个 Model、看重哪把尺子？第二层里它这一轮能看到哪些 Context、有没有 Memory、要不要 RAG、长任务有没有 State？第三层它开了哪几只手（搜索、浏览器、文件、终端、代码、API）？第四层它装了哪些 Tool / Connector / Plugin / MCP / Skill？第五层它有没有 Workflow、会不会派 Sub-agent、能不能 Automation？你会立刻发现自己之前一直在"裸用"，很多能力其实没开。

**Mission 6-B：判断一次失败到底卡在哪个层**

回想最近一次它没做好的任务。对着这五层判断：是第一层 Model 不够聪明（Reasoning/Coding 不行）？还是第二层信息没给够（漏了材料、该检索没检索）？还是第三层手没开（该让它搜它没搜）？还是第四层缺了某个扩展（该接的服务没接）？还是第五层编排乱了（步骤没串好）？定性之后，下次任务对症下药，而不是只会重写一遍 Prompt。

**Mission 6-C：分清三对最容易混的概念**

用自己的话写三句话：Context 和 Memory 差在哪？Search 和 Browser 差在哪？MCP 和 Connector 差在哪？写不出人话版，就回去重读对应那一节。这三对分清了，这一章就过关了。

# PART 7：给 Agent 安装和扩展能力

> 先导图：Agent 能力扩展安装与授权流程图（待插入 F15：从发现资源 → 读说明 → 查安全 → 授权/装密钥 → 最小权限 → 验证 → 交付/卸载的闭环）

## 本章你要解决什么问题

上一章讲清楚了 Agent 由哪些零件组成。本章解决一个非常实际的问题：**这些零件不是出厂全装好的，很多要你自己去"插上去"**。就像新手机买回来只能打电话，导航、外卖、修图都得你自己装 App。

但这里有一条贯穿全章的铁律，请你先记住：

> 社区里的 Skill、Plugin、MCP、Connector，不能因为"很多人装"你就装。GitHub 上的 Star 数不等于安全，商店里的"热门推荐"不等于对你合适。每装一个，你都要知道它碰了什么数据、能干什么动作、钥匙放在了哪里。

## 7.1 从"模型能力"到"Agent 能力"

模型出厂时只会做一件事：读一段文字，吐一段文字。它不能读你电脑里的论文，不能查今天的新闻，不能动你的 Excel，也不能替你发邮件。这些"超能力"全是后来装上去的。

所以判断一个 Agent 到底强不强，不要只看它用了多牛的 Model，而要看：

- 它接了哪些 Tool（搜索？文件？浏览器？代码？）；
- 它装了哪些 Skill / Plugin / MCP；
- 它连了哪些你的账号（邮件？日历？云盘？GitHub？）；
- 你给了它多大的操作权限。

**模型决定天花板，扩展能力决定它能不能下地干活。** 一个用中档模型但工具齐全、权限合理的 Agent，往往比一个用顶级模型却"赤手空拳"的 Agent 有用得多。

## 7.2 安装 Skill

Skill 的安装在各平台上长得不一样，但通用动作就四步：

1. **找到它**：从平台官方 Skill 商店、官方 GitHub 组织、或你信任的 Skill 目录里找到一个具体的 Skill，记下它的来源地址。
2. **读它的说明书**：每个 Skill 根目录下都有一个 `SKILL.md` 文件，这是它的脸，下一节专门讲怎么读。
3. **放进指定位置**：把这个 Skill 文件夹放到你的 Agent 配置目录里——通常是一个叫 skills 的文件夹，不同平台路径不同，以该平台文档为准。
4. **让 Agent 认识它**：重启或刷新 Agent，或者直接对它说"你现在有一个叫 XX 的 Skill，请先读它的 SKILL.md"。第一次用之前，让它先自己读一遍说明书。

### 7.2.1 一次完整安装演示（以本机 Claude 系 skills 目录为例）

下面用一台真实 Windows 机器上的真实目录走一遍，让你看清每一步长什么样。**注意：本节命令路径是这台机器的真实情况，你照做时要换成你自己的用户名和平台路径；凡标注"本环境无法替你完成"的步骤，请在你自己的 Agent 产品里照做。**

**第一步：发现。** 在本机的 skills 目录里，每个子文件夹就是一个 Skill。用一条命令就能看清单：

```powershell
Get-ChildItem "$env:USERPROFILE\.claude\skills" -Directory | Select-Object Name
```

这台机器上真实存在的 Skill 包括 `arxiv-research`、`minimax-pdf`、`find-skills`、`skill-creator` 等。假设你想找一个"处理 PDF"或"做文献研究"的 Skill，关键词是 `pdf`、`research`：

```powershell
Get-ChildItem "$env:USERPROFILE\.claude\skills" -Directory | Where-Object { $_.Name -match 'pdf|research' } | Select-Object Name
```

本机真实命中：`minimax-pdf`（pdf）、`arxiv-research`（research）。如果你是从 SkillsMP、skills.sh 这类聚合站或官方 GitHub 组织发现的，做法一样：记下它的来源仓库地址。

**第二步：源仓库核验。** 打开这个 Skill 对应的 GitHub 仓库（不是只看聚合站的卡片），用眼睛或让 Agent 帮你看四样东西：README 讲清楚了没有、有没有 License 文件、最近一次提交是什么时候、Issue 区有没有人报安全问题。本机可以用命令看一个已装 Skill 的最后提交时间：

```powershell
git -C "$env:USERPROFILE\.claude\skills\minimax-pdf" log -1 --format="%ci  %s"
```

> 说明：上面这条只在该 Skill 本身是 git 仓库时才有输出。如果你的 Skill 是直接下载的文件夹、不是 git clone 下来的，这一步就打开 GitHub 网页看"最近提交"那一栏。本环境不对第三方仓库的安全性下任何结论，核验动作由你本人完成。

**第三步：权限审计。** 打开它的 `SKILL.md`，重点看有没有脚本、会不会执行 Shell、会不会往你电脑写文件、要不要联网。本机真实操作：

```powershell
Get-Content "$env:USERPROFILE\.claude\skills\minimax-pdf\SKILL.md" -TotalCount 60
```

再看一眼它带了哪些文件、有没有可执行脚本：

```powershell
Get-ChildItem "$env:USERPROFILE\.claude\skills\minimax-pdf" -Recurse | Select-Object FullName, Length
```

判断标准回到 7.3 节那张表和 7.4 节的 12 问：出现"联网下载""删除文件""读环境变量外发"这类字眼，先打问号。

**第四步：安装。** 如果是从 GitHub 下载的新 Skill，就是把整个文件夹放进 skills 目录。本机这台机器上，目标目录就是 `C:\Users\lauze\.claude\skills`（对应 `%USERPROFILE%\.claude\skills`）。如果你用的是别的 Agent 产品，这个目录名可能不同，以它的文档为准。

**第五步：测试。** 重启或刷新你的 Agent 产品，对它说："请读一下你 skills 目录里的 `minimax-pdf`（或你新装的那个）SKILL.md，然后用它处理我这个 PDF。" 再丢一个小 PDF 让它试一次。

> 标注：**"在你自己的 Agent 产品里加载并测试"这一步，本教程运行环境无法替你完成**——因为那是另一个图形化产品里的交互，不在这台命令行机器上。你需要在自己的产品里实际开一次，确认它真的认识这个 Skill、真按说明书走了。

**第六步：验证卸载无残留。** 装完不满意要撤，就是删掉那个文件夹，再确认没有别的残留：

```powershell
Remove-Item "$env:USERPROFILE\.claude\skills\minimax-pdf" -Recurse -Force
Test-Path "$env:USERPROFILE\.claude\skills\minimax-pdf"
```

第二条命令应返回 `False`，说明文件夹已删干净。如果这个 Skill 之前还在某个配置文件里登记过、或连过你的账号，记得按 7.13 节再去配置里移除、去对应账号撤销授权——光删文件夹不算完整卸载。

**新手最容易踩的坑**：从某个聚合网站上看到一个"排名很高"的 Skill，直接一键安装，从没打开过它的 SKILL.md。这等于没看合同就签字。下一节起我们就是要治这个毛病。

## 7.3 阅读 SKILL.md

`SKILL.md` 是什么？它就是一个纯文本的 Markdown 文件，是这个 Skill 的"产品说明书加岗位说明书"。它一般不长，几百行以内。你不需要懂代码，用记事本就能打开。

打开之后，重点找下面这几段，按顺序读：

| 你要找的信息 | 它通常会写在哪 | 你要判断什么 |
|---|---|---|
| 这个 Skill 是干嘛的 | 开头的简介 | 和你要做的事对不对得上 |
| 它支持哪些 Agent / 平台 | 安装说明 | 你用的平台到底装不装得上 |
| 它需要什么前置条件 | Requirements / Prerequisites | 要不要额外装软件、要不要账号 |
| 它会读哪些文件、写哪些文件 | 权限说明 / 工作方式 | 会不会动到你的原始材料 |
| 它会不会联网、会不会调付费 API | 网络/费用说明 | 会不会偷偷跑钱、会不会外发数据 |
| 它附带什么脚本 | Files / Scripts 部分 | 脚本是最需要警惕的部分，见 7.5 |
| 怎么卸 | Uninstall | 装之前先确认能撤 |

读 SKILL.md 不需要你读懂代码，只需要你回答一个问题：**"这个东西装进我的 Agent 之后，它可能对我的电脑、我的账号、我的钱做什么？"** 答得上来，再装；答不上来，先别装。

## 7.4 判断一个 Skill 是否可信：12 问安全检查清单

下面这 12 个问题，是你每次装社区 Skill 前必须在心里过一遍的。它来自本教程的安全要求，也对应行业通用的开源件审查习惯。请把它当成一张检查表，装之前逐条问自己：

1. **来源是谁？** 是知名公司官方仓库，还是一个匿名账号？作者过去有没有别的可信项目？
2. **源代码在哪里？** 能不能看到完整代码，而不是只有一个"一键安装"按钮？
3. **最近有没有维护？** 最近一次提交是上周还是三年前？三年没动的东西，装之前要更谨慎。
4. **它会执行什么脚本？** 附带的脚本大概是干什么的？有没有看起来和它宣传的功能无关的操作？
5. **它能读什么文件？** 会不会去翻你的文档、桌面、下载文件夹？
6. **它能写什么文件？** 会不会往系统目录、配置目录里塞东西？
7. **它能访问哪些网站 / API？** 除了它该用的那个服务，还会不会连到别的地址？
8. **它需要哪些账号权限？** 连你的邮箱时，是"只读"还是"能发邮件"？连你的 GitHub 时，是"只读代码"还是"能替你 push"？
9. **它会不会把我的数据发到第三方？** 读出来的内容除了给模型用，会不会还发给别人？
10. **它会不会调用付费 API？** 跑一次花多少钱？有没有上限？
11. **它有没有删除、覆盖、修改能力？** 误操作时能不能找回来？
12. **能不能先在测试目录跑一遍？** 有没有一个干净的文件夹、一份副本，让它先在里面玩一次？

**特别强调两句话**：

- **Star 数不等于安全。** 一个热门项目可能被很多人装，但它的代码你没看过，风险就在你这台机器上。Star 只能说明"它流行"，不能说明"它干净"。
- **"官方"两个字要看清楚。** 有些聚合站名字里带 Official，不代表它是某家公司官方办的。认准域名和 GitHub 组织名，别被名字带跑。

第一次做这 12 问会很慢。做过四五次之后，你会形成直觉：这个 Skill 靠不靠谱，扫一眼开头和脚本列表就有数了。

## 7.5 Skill 中的脚本、模板和资产

打开一个 Skill 文件夹，你通常会看到三类东西：

- **说明文档**：就是 SKILL.md，你刚才读过的那份。最安全，纯文本。
- **模板和资产**：半成品文档、示例数据、图片、配置样例。它们本身不会自己跑，是给 Agent 参考着用的。风险低。
- **脚本**：真正会被执行的代码，可能是 Python、Shell、或平台自己的命令。这是**风险最高**的部分——它装上去之后，Agent 可能在你没注意的时候跑它。

新手不需要会写脚本，但要会"看脚本在干嘛"。一个粗略的原则：

- 如果脚本只是"格式化文本""生成一个固定表格"，风险低；
- 如果脚本里出现了"联网下载""删除文件""改系统配置""读环境变量并外发"这类字眼，立刻提高警惕，回去把 12 问里对应的问题问清楚再决定。

看不懂脚本写了什么，就把它丢给你正在用的 Agent，问："这段脚本从头到尾干了什么？有没有删文件、联网、发数据的动作？"让它用人话讲给你听。

## 7.6 安装 Plugin

Plugin 和 Skill 很像，都是"给 Agent 加一块能力"，差别主要在来源和形态：

- **Plugin** 通常来自平台官方商店，一键安装，背后常连的是平台认证过的服务。你在界面上点"安装"，它就挂上去了。
- **Skill** 更像从开源社区下载的一个文件夹，你要自己放到配置目录、自己读 SKILL.md。

装 Plugin 相对省心，但"平台官方商店"不代表"绝对安全"：你依然要在安装弹窗里看一眼它要什么权限、会不会收费、会不会读你的账号数据。商店审核一般会拦住明显的恶意件，但审不到"这个插件是否过度收集你的数据"这种灰色问题。

## 7.7 添加 MCP Server

MCP 的添加方式，通常是在你的 Agent 配置文件里，写上一段说明："我要用哪个 MCP Server，它怎么启动，它的钥匙放哪"。改完配置，重启 Agent，它就插上了这个"万能插座"。

以 2026 年 9 月各平台现状为准，不同平台的配置文件位置和格式不同，**不要照抄网上三年前的教程**，以你所用平台官方文档里的"添加 MCP"一节为准。

### 7.7.1 一次完整安装演示（以 filesystem 这个轻量 Server 为例）

下面用真实存在、官方维护、用途明确的 `filesystem` MCP Server 走一遍。它只做一件事：把你指定的一个文件夹暴露给 Agent 读写，非常适合第一次试手。**同样地，标注"本环境无法替你完成"的步骤，要在你自己的客户端里做。**

**第一步：在官方注册中心发现。** 打开 MCP 官方注册中心（registry.modelcontextprotocol.io），浏览或搜索 `filesystem`。你会看到一个官方维护的文件系统 Server，描述是"在你限定的目录里读写文件"。注意：注册中心的目录会持续变动，以你打开时的实时页面为准，本节只教你怎么挑——挑"官方/知名组织维护、描述清楚、只碰你指定目录"的轻量 Server。

**第二步：源仓库核验。** 点进它的源码仓库，看：README 有没有讲清楚怎么启动、要什么参数、License 是什么、最近还更不更新。它和装任何开源件一样，过一遍 7.4 的 12 问。

**第三步：安装配置（真实配置示例）。** 以常见的 Claude 系客户端配置为例（**格式只作示意，你所用客户端的键名和路径以其官方文档为准**），在它的 MCP 配置 JSON 里加一段：

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": [
        "-y",
        "@modelcontextprotocol/server-filesystem",
        "D:\\AISOP\\mcp-sandbox"
      ]
    }
  }
}
```

这段配置的意思是：用 `npx` 启动官方的 `@modelcontextprotocol/server-filesystem`，并把它可访问的目录**限定**在 `D:\AISOP\mcp-sandbox` 这一个文件夹。把最后那行换成你自己希望 Agent 能碰的文件夹——**这一步是 MCP 安全的关键：只给它一个专用沙箱目录，不要把整个用户目录或 C 盘根目录填进去。**

**第四步：先手动验证它能启动。** 改完配置前，可以先在命令行单独跑一下启动命令，确认包能拉起来、不报错（首次运行 npx 会下载这个包，需要联网，耗时视网络而定）：

```powershell
npx -y @modelcontextprotocol/server-filesystem "D:\AISOP\mcp-sandbox"
```

它启动后通常会停在那里等标准输入（因为 MCP 是一个通过 stdin/stdout 对话的进程），你看到它没报错、没立刻退出，就说明这一步通了，按 `Ctrl+C` 退出即可。

> 标注：**"用一个最小 MCP 客户端脚本真正连上、列出工具、调用一次"这一步，需要你在自己的开发环境里写几行客户端代码或用客户端自带的连接测试功能来做。** 它的原理是：启动上面那个进程，按 MCP 的协议跟它握手，让它报出自己提供了哪些工具（一般是 read_file、write_file、list_directory 之类），再调一次 `list_directory` 看能不能列出 `D:\AISOP\mcp-sandbox` 里的文件。本教程运行环境不替你执行这一步，因为它属于"你自己客户端里的连通性验证"。如果连不上，先查三件事：npx 在不在、目录路径写对没有、客户端有没有重启加载新配置。

**第五步：在 Agent 里测试。** 重启你的 Agent 客户端，对它说："你现在应该连上了一个叫 filesystem 的 MCP，请列出它暴露了哪些工具，然后读一下 D:\AISOP\mcp-sandbox 里的文件。" 它能说出工具名、真的列出文件，才算装上。

**卸载**：把配置 JSON 里这一段 `filesystem` 删掉，重启客户端即可；`npx` 下载的包在本地缓存里，想彻底清掉就清 npm 缓存。

添加 MCP 时同样要过 12 问：这个 Server 是谁写的？它要访问什么？它需要什么密钥？会不会把你的数据转给第三方？一个标着"MCP"的开源 Server，本质和一个 Skill 一样，是会跑的代码。

## 7.8 添加 Connector

Connector 是最贴近普通用户的扩展方式：界面上一个"连接邮箱""连接日历""连接云盘"的按钮，点一下，跳到你那个账号的登录页，授权，回来就连上了。

它和手动配 MCP 的区别是：Connector 把技术细节包起来了，你不用碰配置文件。但授权那一步，你仍然要看清楚——这就引出下一节。

### 7.8.1 一次真实可验证示例：GitHub 官方集成（gh CLI 的 OAuth）

Connector 里最容易在本机完整走一遍、且能直接核对授权边界的，是 GitHub 官方命令行工具 `gh`。它走的就是标准的 OAuth 流程，你可以拿它当"理解 Connector 授权"的活标本。

**第一步：确认工具已装、当前授权状态。** 这台机器上真实执行：

```powershell
gh auth status
```

本机真实输出大意是：已登录到 github.com，当前账号为 TZUKWAN，token 存在系统密钥环里，**当前 token 的权限范围（scopes）是 `gist, read:org, repo, workflow`**。这串 scopes 就是"OAuth 授权边界"的实物——你一眼能看到：它能读写仓库（repo）、能操作工作流（workflow）、能读组织信息（read:org）、能写 Gist（gist），但它**没有** `delete_repo` 这种删除权限，也没有 `admin:org` 这种管理员权限。这就是 Connector 授权该有的样子：能做的列得清清楚楚，不该有的没有。

**第二步：理解 OAuth 授权边界。** 第一次用 `gh` 时跑 `gh auth login`，它会让你选"用浏览器登录"还是"粘贴 token"。选浏览器登录，它会打开 GitHub 官方页面，列清楚这次要哪些权限，你同意后才拿到那张通行证。**关键不是这个机制多方便，而是你在那个页面上要逐行看：它要的每一项权限，是不是你真打算给的。** 拿 gh 举例：

| 它请求的 scope | 翻译成大白话 | 该不该给 |
|---|---|---|
| `repo` | 能读、写你的仓库代码 | 你要让它动代码，就给 |
| `workflow` | 能改 GitHub Actions 工作流 | 你要让它自动跑 CI，才给 |
| `read:org` | 只读你所在组织的信息 | 一般够用 |
| `delete_repo` | **能删仓库** | 没有明确需要就别勾 |

**第三步：事后核对和收权。** 想临时收缩或扩大权限，本机真实命令：

```powershell
gh auth refresh -s read:org
```

它会重新走一次浏览器授权，让你确认新的权限范围。不想用了，一键撤销：

```powershell
gh auth logout
```

更彻底的做法，是直接去 GitHub 网页的 Settings → Applications → Authorized OAuth Apps 里，找到这个应用，点 Revoke。**这和 7.13 节讲的"去账号侧撤销授权"是同一个动作。**

**其他平台如实说明：** Notion、Slack、Google Workspace 这类 Connector，本机无法替你登录授权，因为它们需要你本人的账号、验证码、二次确认。流程和 gh 一模一样：点连接 → 跳到官方登录页 → **逐行看权限** → 同意 → 回来核对授权状态。差别只在登录页是哪家公司的，授权那一页你要做的事完全相同。

## 7.9 OAuth 与账号授权

当你点"连接邮箱"时，跳出来的那个登录页问你："是否允许 XX 应用访问你的邮箱？"——这背后走的就是 **OAuth**（一种业界通用的"第三方授权"机制，你可以先理解成"你不把账号密码告诉这个应用，而是通过官方登录页给它发一张有时效的通行证"）。

关键不是这个机制本身，而是你在授权页上要做的事：

**授权页会列出这个应用要哪些权限。你要逐条看，不要直接滑到底点"同意"。** 典型的权限粒度包括：

- 只读你的邮件 / 日历 / 文档，还是能替你发邮件、改日历、删文档？
- 能访问哪些数据？全部，还是只某个文件夹？
- 有效期多久？能不能随时撤销？

用一个类比：OAuth 授权就像你给朋友一把家里的钥匙。你要知道这把钥匙能开哪扇门——能开大门可以理解，能开保险箱就过分了。授权页列出的就是"这把钥匙能开哪些门"。

事后想反悔怎么办？去你那个账号（邮箱、云盘、GitHub）的"第三方授权 / 应用授权"设置页，找到这个 Agent，点"撤销授权"。这一步任何时候都可以做，别等出了事才找。

## 7.10 API Key

很多服务不给你登录授权页，而是让你填一串"密钥"。这串字符就是 **API Key**——你调它服务时的"门钥匙"。

先讲清楚三件最重要的事：

**第一，它是什么。** API Key 长得像一串随机字符（例如 `sk-xxxxxxxx...`）。拿着它，任何人都能以你的身份调用那个服务、用你的额度、甚至产生你的账单。

**第二，它不是密码，但比密码还不能外传。** 密码你还能登录后改，API Key 一旦泄露，要么去服务商那里重新生成一个、把旧的作废。它泄露的代价是真金白银和数据。

**第三，三条铁规矩：**

- **不要把 API Key 写进普通的对话 Prompt 里。** 你在对话框里贴一次，它就可能被记进聊天历史、被模型的日志带走。
- **不要把 API Key 提交到 GitHub 等公开仓库。** 哪怕你觉得"这个仓库只有我自己看"——仓库可能变公开、可能被 fork、可能被 AI 扫描器盯上。业界每年都有成百上千个 Key 因为误传 GitHub 被扫走、被盗刷。
- **Key 要能随时作废、随时重发。** 每个服务商后台都有"重新生成 / 作废旧 Key"的功能，怀疑泄露就立刻换。

那 Key 到底放哪？看下一节。

## 7.11 环境变量

直接在对话框里念 Key，是最危险的做法。正确做法是把 Key 放进一个专门的地方，让 Agent 要用时自己去取，而不是每次都从对话里读到。

这个专门的地方，就是**环境变量（Environment Variable）**。你可以先把它理解成"一个上锁的抽屉"：你把 Key 放进去，关上门；Agent 需要用的时候，按约定的名字去抽屉里拿，但它看不到别的东西，也不会把这串字打印到对话里、写进提交记录。

在 Windows 上临时看一眼当前环境变量名（**只看名字，不要把值打印出来**）：

```powershell
Get-ChildItem env: | Where-Object { $_.Name -match 'KEY|TOKEN|SECRET' } | Select-Object Name
```

各平台设置环境变量的入口不同（有的在设置页，有的在配置文件里，有的在你电脑的系统环境变量里），以你所用平台文档为准。你只需要建立这个习惯：

> 凡是钥匙类的东西（API Key、Token、密码），一律进环境变量或平台的密钥管理处，永远不进 Prompt、不进文档、不进 Git。

## 7.12 最小权限原则：L1–L4 风险分级表

装上了能力，就要管住它能干什么。核心原则一句话：**只给完成这件事所需的最小权限，多一分都不给。**

把 Agent 的所有可能动作，按"做错了能不能收回来"分成四级：

| 风险级别 | 典型动作 | 默认策略 |
|---|---|---|
| **L1 低风险** | 读文件、搜索网页、分析数据副本、读你给的材料 | 可以自动执行，不用每次问你 |
| **L2 可逆修改** | 新建文件、改工作副本、在 Git 上建分支、改草稿 | 可以执行，但要留记录（改了什么、改前是什么） |
| **L3 高影响** | 覆盖你原来的文件、Git push 到远程、改云端共享文档、替你发消息或邮件 | 建议每一步都停下来让你确认 |
| **L4 不可逆 / 高风险** | 删除数据、支付、公开发布、改生产数据库、改权限、对外发正式公告 | 必须你明确说"确认执行"才做，且最好先备份 |

这张表你可以直接抄下来，贴在你和 Agent 协作时的旁边。每次派任务时，心里过一遍："我现在授权它做的事，落在哪一级？"

- 做文献整理、读 PPT、分析 Excel 副本——L1，放手让它跑。
- 让它在工作文件夹里新建分析结果——L2，跑之前让它先说清楚要建哪几个文件。
- 让它改你那份要交的论文原稿——L3，先让它改一个副本，你看满意了再替换。
- 让它"把这封邮件发出去""把这个推到 GitHub 主分支""付这笔钱"——L4，停下来，你自己点最后一下。

一个朴素的判断：**凡是错了找不回来的事，最后那一下永远你自己按。**

## 7.13 如何卸载 / 禁用能力

装上去的东西，要能撤下来。三种动作要分清：

- **临时禁用**：Agent 里往往有开关，把某个 Skill / Plugin / MCP 关掉，它暂时不生效，但文件还在。适合"我现在不想用它，但以后可能还开"。
- **卸载**：把这个插件从 Agent 里移除。适合"我确定不用了"。
- **撤销账号授权**：如果它连了你的邮箱 / GitHub / 云盘，记得去对应账号的第三方授权页把它踢掉——光在 Agent 里卸载，有时你那个账号上的授权还挂着。

一个好习惯：每季度花十分钟，去你常用的账号（邮箱、GitHub、云盘、社交平台）的"第三方应用授权"列表里扫一眼，把不认识、不再用的授权全部撤销。

## 7.14 如何更新 Skill / Plugin / MCP

这些社区件会更新：修 bug、加功能、改权限。但**不要开启全自动更新**。理由很简单：一个昨天还干净的 Skill，今天的版本可能加了联网、加了付费调用。

正确姿势：

1. 更新前先看它的更新说明（changelog / release notes）——这版改了什么？
2. 尤其注意"新增了什么权限、新增了什么网络请求、新增了什么依赖"。
3. 更新后跑一次你常用的 Mission，确认它没跑偏。
4. 出问题就回到上一个版本。

平台官方商店的 Plugin 更新相对省心，但也别假设"官方更新 = 对你更好"。

## 7.15 如何发现新的 Agent 能力：资源地图概念

最后一个问题：我怎么知道"有什么新东西可装"？

不要靠刷社交平台碰运气。你需要在心里建立一张**资源地图**，按三层去找，越靠上越可信：

**第一层：官方来源。** 你所用 Agent 平台的官方文档、官方 Skill 商店、官方 GitHub 组织、官方 MCP 注册中心（registry.modelcontextprotocol.io）。先查这里，因为信息最准、维护最勤。

**第二层：聚合发现平台。** 一些社区目录（如 SkillsMP、skills.sh 这类）会聚合公开的 Skill、MCP、Plugin，方便你搜索。它们的价值是"让你发现"，**不是让你直接装**。看到感兴趣的，记下来，回到第三层。

**第三层：源仓库。** 打开这个 Skill / MCP 的 GitHub 或官方源码页，看：谁做的、最近提交时间、Star 和 Issue 活跃度、README、License、有没有脚本、要什么权限。过一遍 7.4 的 12 问，再决定装不装。

> 再次强调：聚合平台上的排名、评分、"热门""推荐"，只代表它被很多人发现，不代表它安全、不代表它适合你、不代表它还在维护。**发现靠聚合站，决定靠源仓库。**

具体的官方注册中心、Skill 目录、MCP 目录、社区 Awesome 列表，本教程配套的资源文件里会单独整理，并标注核验日期。本节只教你这套"三层找法"。
