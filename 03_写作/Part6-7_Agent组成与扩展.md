# PART 6：Agent 到底由什么组成

> 先导图：Agent 组成分层结构图（待插入 F01：Model 在上，Context / Tools / Memory 在中层，Agent 居中，Workflow 在下，Result 垫底的六层关系图）

## 本章你要解决什么问题

前面五个 Part，我们一直在讲"怎么把一件事交给 Agent 做"：怎么下任务、怎么管长任务、怎么验收、怎么识别它会怎么失败。但你可能心里一直有个没说出口的疑问：它到底是个什么东西？为什么有的事它能做，有的事它做不了？为什么同一个任务，换个模型、开个插件，结果就不一样？

到这一章，我们才正式打开发动机盖。

请记住一个判断标准：本章不要求你会写任何一行代码，也不要求你背下任何一个术语的英文全称。你需要做到的是——下次听到一个新名词时，能把它对号入座到这张分层图里，知道它大概在解决什么问题，知道它和隔壁概念有什么不一样。这就够了。

## 一张总览图：Agent 的六层结构

不要被下面这堆名词吓到。它们其实可以压成一句话：

> 一个 Agent，就是"一个足够聪明的模型"，在"它当前能看到的信息"和"它手里能用的工具"的支持下，按照"一套工作流程"，持续地把一件事做完，最后交出一个结果。

对应到分层，就是：

```text
                 Model（模型：它有多聪明）
                   │
       ┌───────────┼───────────┐
       ↓           ↓           ↓
    Context      Tools       Memory
   （眼前看到的）（手里能用的）（跨次记得的）
       │           │           │
       └───────────┼───────────┘
                   ↓
                 Agent（决策中枢：决定下一步干什么）
                   │
                   ↓
                Workflow（工作流程：按什么步骤推进）
                   │
                   ↓
                 Result（结果：最后交出来的东西）
```

你可以把它想象成一个刚入职的员工：Model 是他的脑子；Context 是他今天摊在桌上的材料；Memory 是他抽屉里的笔记本；Tools 是他工位上能用的电话、打印机、计算器；Workflow 是公司规定的办事流程；Result 是他最后交出来的那份报告。

下面 19 节，就是把这张图上每一块拆开讲。每一块都只回答五个问题：它解决什么问题？什么时候需要？举个实际例子？它和旁边那个概念差在哪？一个完全不会技术的人，掌握到什么程度就够了？

## 6.1 Model（模型）

**它解决什么问题？**

Model 就是这个员工的"脑子"本身。所有理解、推理、写句子、做计划、决定"下一步该调用哪个工具"，都是它在干。没有 Model，后面所有工具、流程、记忆都只是一堆不会动的零件。

**什么时候需要？**

你不需要在日常使用时反复"选模型"，但你需要在遇到以下情况时知道"换个脑子"可能有帮助：任务特别难、容易出错、特别长、要看图、要写代码、要赶时间、要省钱。

**实际例子？**

让 Agent 改一段跑不通的代码，和让 Agent 写一封客气的请假邮件，用的模型往往不是同一个。前者需要"推理（Reasoning）"和"写代码（Coding）"能力强的模型；后者反应快、便宜、语气自然的模型就够。

**新手应该掌握哪些选择维度？**

本章不给任何"模型排行榜"，因为模型迭代极快，任何排名都活不过一个季度。你要学的是"挑脑子的尺子"，每一把尺子对应一类真实痛点：

| 维度 | 大白话 | 什么时候这把尺子重要 |
|---|---|---|
| Reasoning（推理能力） | 能不能一步步把难题想明白，而不是凭直觉瞎答 | 复杂决策、改 bug、做分析、写论证 |
| Coding（写代码能力） | 能不能看懂、写出、改对可运行的代码 | 让它动文件、做数据处理、改软件 |
| Context Window（上下文窗口） | 这一次对话它最多能同时看进去多少字/多少文件 | 你要一次塞 40 篇论文、一整个文件夹 |
| Tool Calling（工具调用） | 它能不能准确地"决定该调用哪个工具、参数填对没有" | 只要任务需要联网、读文件、操作外部系统，这一条就是命门 |
| Computer Use（电脑操作） | 它能不能看懂屏幕截图、移动鼠标、点按钮 | 需要它操作没有 API 的老式网页或桌面软件 |
| Multimodal（多模态） | 它能不能看图、看表、看截图、看音频 | 你要给它 PPT 截图、手写笔记、图表照片 |
| Latency（响应速度） | 它多久回你一句 | 你在等它连续操作，或者做即时对话 |
| Cost（成本） | 每用一次花多少钱 | 长任务反复跑、自动化每天跑，账单会堆起来 |
| Output Limit（输出上限） | 它一次最多能写多长 | 让它一次性写完一篇长综述时会卡断 |
| Reliability（稳定性） | 同样的任务，它会不会这次对、下次错 | 高风险操作、要长期无人值守的自动化 |

有一个更省事的思路：**简单任务用快的、便宜的；难任务再切到强推理的；做检查的那一步，最好换一个和执行者不同的模型**。很多平台已经内置了"默认模型"，新手不需要一开始就纠结这个，知道"原来可以换"就够了。

**它和相邻概念的区别？**

Model 是"脑子"；Tool 是"手脚"。一个推理很强但没给工具的模型，只能陪你聊；一个反应很快但不会调工具的模型，说得再漂亮也动不了你的文件。

**新手掌握到什么程度？**

能说出"我这次任务最看重哪两三把尺子"，并在平台上知道去哪里切换模型，就已经超过绝大多数用户了。不要追"最强模型"，要追"这把任务最合适的模型"。

> 平台说明：各平台模型名单、档位、价格、能力边界变化极快，本节不点名具体型号。以 2026 年 9 月各平台官方文档现状为准。

## 6.2 Context（上下文）

**它解决什么问题？**

模型自己"记不住你电脑里有什么"，也不知道你是谁、要干什么。Context（上下文）就是它"这一次睁眼时，眼前摊着的全部东西"：你这轮打的字、它刚才的回答、你拖进来的文件、搜索到的网页、它刚读出来的文件内容。它只能基于眼前这些东西回答。

**什么时候需要？**

只要你希望 Agent 别答非所问，就要想清楚"这次要让它看到什么"。这就是 PART 5 里讲过的"上下文污染"和"最小充分上下文"的根源：眼前堆得太多，它会被无关信息带偏；眼前给得太少，它会瞎编。

**实际例子？**

你让它"帮我改这篇论文的引言"，就必须把论文全文（或至少引言部分）放进 Context，否则它只能凭空写一段漂亮但和你论文无关的话。

**它和 Memory 的区别？**

Context 是"今天桌面上摊着的纸"，对话一关就没了；Memory 是"收进抽屉、下次还能翻出来的纸"。下面 6.3 专讲 Memory。

**新手掌握到什么程度？**

记住一句话：**你不放进 Context 的东西，等于不存在**。别指望它"应该知道"。

## 6.3 Memory（记忆）

**它解决什么问题？**

每次新开对话，模型都是"失忆"的。Memory（记忆）就是平台帮你跨对话保留下来的那部分信息：你偏好的格式、你常用的背景、上次做到哪一步、它帮你总结过的笔记。这样你不用每次从头自我介绍。

**什么时候需要？**

当你反复和同一个 Agent 打交道、希望它"越来越懂你"时。比如你告诉过它"我是马克思主义理论方向、在做计算社会科学"，下次不用再说一遍。

**实际例子？**

一些平台会把你明确说过的偏好自动存成"长期记忆"；一些项目型 Agent 会在文件夹里放一个 README 或 AGENTS.md，让它每次开工前先读一遍自己的"岗位说明书"。后者本质上是你自己手写的 Memory，比自动记忆更可控。

**它和 Context 的区别？**

Context 是临时桌面，Memory 是档案柜。Memory 的风险在于：它可能记错、记偏，或者把过时的信息一直带着。所以重要的背景，宁可每次在任务里明说，也别全押在"它应该记得"上。

**新手掌握到什么程度？**

会检查"它这次记得的，是不是还是对的"。发现它拿旧印象套新任务时，直接纠正。

---

## 6.4 Tool（工具）

**它解决什么问题？**

没有工具的 Agent，本质上还是一个"嘴"：它能写、能分析、能出主意，但它**碰不到任何真实的东西**。Tool（工具）就是给它接上的"手"：搜索工具、读文件工具、跑代码工具、操作浏览器工具、调 API 工具。有了工具，它才能从"说"变成"做"。

**什么时候需要？**

只要任务要求"真的发生点什么"——真的查到网页、真的读出那个 Excel、真的新建那个文件——就需要至少一个 Tool。

**实际例子？**

你说"帮我把这个文件夹按类型分好类"，没有文件工具它只能说"我建议你按文档、图片、视频分"；有了文件工具，它才真的去建文件夹、移动文件。

**它和相邻概念的区别？**

Tool 是一个抽象的大类。Search、Browser、Computer Use、File System、Terminal、API、Connector、MCP，本质上都是 Tool 的具体形态。后面几节是把这个大类拆开。

**新手掌握到什么程度？**

知道"它每说一句要干活，背后必然调用了某个具体工具"，并会在它调用时瞄一眼"它现在碰的是哪个东西"。

---

## 6.5 Search（搜索）

**它解决什么问题？**

模型的训练数据有截止日期，也不可能背下全世界所有网页。Search（联网搜索）就是让它像你打开百度、谷歌那样，去网上查最新的、具体的、它训练时没见过的信息。

**什么时候需要？**

凡是涉及"今天的事实"：最新的政策、刚发布的论文、某公司最近一轮融资、某个软件现在的版本号。凡是你不希望它凭记忆瞎说的事实，都该让它搜。

**实际例子？**

让它查"2026 年某领域最新的综述"，它必须真的去搜学术库，而不是凭训练记忆给你列几篇三年前的老文章。

**它和 Browser 的区别？**

Search 是"输入关键词，看返回的链接和摘要"，适合找资料；Browser 是"真的打开那个网站，像人一样翻页、登录、点按钮、填表"，适合做搜索做不到的事。下面 6.6 讲。

**新手掌握到什么程度？**

知道"它给的每个事实性结论，最好都带回来源链接"；没带来源的事实，一律当成待核验。

---

## 6.6 Browser（浏览器）

**它解决什么问题？**

很多信息藏在搜索引擎返回不了的地方：需要登录的账号后台、需要点几下才能展开的表格、需要翻页的论坛帖子、需要点"加载更多"的评论区。Browser（浏览器控制）就是让 Agent 真的打开一个浏览器，像人一样看屏幕、点鼠标、敲键盘。

**什么时候需要？**

当 Search 返回的摘要不够用，必须进到网站里把内容"读出来"的时候。典型场景：抓一个需要翻页的列表、打开某个后台看数据、操作一个没有官方 API 的小网站。

**实际例子？**

你让它"把某份公开榜单的前 50 名连同公司名、成立时间、融资轮次抓成一张表"，搜索做不到（结果分散在十几页里），浏览器可以。

**它和 Computer Use 的区别？**

Browser 只在浏览器里活动；Computer Use 连桌面软件都能操作，自由度更大，风险也更大。下一节讲。

**新手掌握到什么程度？**

知道它在"真操作网页"时，你应该在旁边看着第一步点的对不对，尤其是涉及登录、下单、发消息的页面。

---

## 6.7 Computer Use（电脑操作）

**它解决什么问题？**

有些软件根本没有网页版、没有 API，只有桌面客户端，或者是一个很老的系统。Computer Use（电脑操作）就是让 Agent 直接看你的整个屏幕、移动鼠标、敲键盘，像一个远程坐在你电脑前的人一样操作任何软件。

**什么时候需要？**

当你想让它操作的东西"既不在浏览器里、也没有接口"时。比如某个只能在 Windows 客户端里用的老系统、某个必须手动点的工业软件。

**实际例子？**

让它打开你电脑上的某个设计软件，按你说的步骤改尺寸、导出图片。它真的会移动你的鼠标——你会在屏幕上看到光标自己动。

**它和 Browser、Code Execution 的区别？**

| 能力 | 活动范围 | 自由度 | 风险 |
|---|---|---|---|
| Browser | 只在浏览器标签页里 | 中 | 中 |
| Computer Use | 整个桌面、任何软件 | 最高 | 最高 |
| Code Execution | 隔离的代码沙箱 | 受限 | 较低 |

**新手掌握到什么程度？**

第一次开这个能力时，全程盯着屏幕。它动鼠标就是真的动你的鼠标，误点一个"确认删除"就是真删。高风险操作前先让它停下来问你。

---

## 6.8 File System（文件系统）

**它解决什么问题？**

你的论文、PPT、Excel、下载的资料，都存在硬盘的文件夹里。File System（文件系统）访问就是让 Agent 能读你电脑上的文件、新建文件、改文件、整理文件夹。没有它，你只能一个个手动把文件拖进对话框。

**什么时候需要？**

只要任务涉及"一堆本地文件"：整理下载文件夹、读完一个项目里的全部材料、把结果写回某个文件夹。

**实际例子？**

PART 1 的第一个 Mission"整理混乱的下载文件夹"，靠的就是这个能力。

**它和 Terminal 的区别？**

File System 工具通常只让它做"读、写、列文件夹"这类安全操作；Terminal 是更底层、更通用的命令通道，能干的事多得多，也危险得多。

**新手掌握到什么程度？**

永远告诉它"只在这个文件夹里工作，不要碰别的地方"。原始材料留备份，让它去改副本。

---

## 6.9 Terminal（终端 / 命令行）

**它解决什么问题？**

Terminal（终端，也叫命令行、Shell）是你平时用鼠标点图标之外，另一种指挥电脑的方式：直接敲一行文字指令，电脑照做。Agent 要装软件、跑脚本、看系统状态、动 Git，很多时候靠敲命令完成。

**什么时候需要？**

你自己一般不需要学敲命令。你需要知道的是：当 Agent 说"我需要装个依赖""我跑一下测试"，它背后多半就是在 Terminal 里敲命令。

**实际例子？**

让它跑一个开源项目，它可能会敲一行命令把项目下载下来，再敲一行把依赖装好，再敲一行启动它。

**它和 Code Execution 的区别？**

Terminal 面对的是**你整台电脑**，命令写错了真的会影响系统；Code Execution 通常是在一个隔离的小房间里跑代码，炸了也只炸那个小房间。所以 Code Execution 适合"算数、跑分析"，Terminal 适合"动整个项目环境"。

**新手掌握到什么程度？**

不用会写命令，但要会问："你这条命令打算干什么？"尤其是带删除、覆盖、联网下载含义的命令，让它解释一遍再放行。

---

## 6.10 Code Execution（代码执行）

**它解决什么问题？**

遇到算数、统计、画图表、清洗 Excel、批量处理文件这类活，让模型"心算"是靠不住的——它会算错、会编数字。Code Execution（代码执行）是给它一个隔离的小环境，让它真的写一小段代码、真的运行、真的把结果打印出来。结果是跑出来的，不是它猜的。

**什么时候需要？**

任何涉及精确数字的活：数据清洗、回归分析、画统计图、批量改名、合并表格。

**实际例子？**

你丢给它一个 5000 行的问卷 Excel，让它"按学院分组算平均分并画图"。它写一段代码跑出来，比让它"看着表格估算"可靠得多。

**它和 Terminal 的区别？**

如上所述：Code Execution 在沙箱里，默认动不到你本地的重要文件；Terminal 在真实系统里。

**新手掌握到什么程度？**

要求它把"跑出来的代码和结果"都留在工作文件夹里，方便你回头复查。代码能重跑，结果才算数。

---

## 6.11 API（应用程序接口）

**它解决什么问题？**

你想用某款软件的功能，但不想打开它的界面、不想手动点——比如想让 Agent 直接把今天的日程读出来、直接查一下数据库里的数。API（Application Programming Interface，应用程序接口）就是软件之间"对话用的标准窗口"：你不用进厨房，通过传菜口下单，菜从窗口递出来。

**什么时候需要？**

当你想让 Agent 用某个软件的"内部功能"，而不是只看它的网页界面时。查天气、查数据库、调翻译、调某个学术接口，背后都是 API。

**实际例子？**

让 Agent "把你飞书日历里明天的会列出来"，它就是通过飞书开放的 API，以你的身份去读日历数据。

**它和 Connector 的区别？**

API 是技术通道，需要自己填密钥、自己拼调用；Connector 是把这种通道包装好、给普通用户用的成品。下一节讲。

**新手掌握到什么程度？**

知道"它能调 API，就意味着它能以你的身份去读或写那个软件里的东西"。授权前想清楚：它能读哪些？能改哪些？

---

## 6.12 Connector（连接器）

**它解决什么问题？**

让普通用户也能用 API，不用懂技术。Connector（连接器）就是平台提前做好的"数据线"：你在界面上点一下"连接邮箱""连接日历""连接云盘"，走一个登录授权，Agent 就能读你邮箱、看你日程、动你云盘。

**什么时候需要？**

当 Agent 需要碰你个人账号里的数据时：邮件、日历、文档、云盘、项目管理工具。

**实际例子？**

点一下连接你的邮箱账号，Agent 就能每天早上帮你看新邮件、归类、起草回复。

**它和 Plugin、MCP 的区别？**

- Connector：偏"把你个人的某个账号接进来"，通常走登录授权（OAuth）；
- Plugin：偏"给 Agent 加一类功能"；
- MCP：偏"一套通用的、谁都能插的标准插座"。
三者在不同平台上经常混用，别纠结名字，看它实际碰了什么数据。

**新手掌握到什么程度？**

每接一个 Connector，都去它的授权页看一眼："它现在能读我哪些东西？能替我做哪些事？"看完再点同意。

---

## 6.13 Plugin（插件）

**它解决什么问题？**

Plugin（插件）是平台打包好的一个"功能模块"：装一个幻灯片插件，Agent 就能读 PPT、写 PPT；装一个 PDF 插件，它就能拆 PDF、合并 PDF。本质是把一组相关的工具和使用说明打包在一起，让你一键开启，不用自己配。

**什么时候需要？**

当你发现 Agent 反复在某类任务上"做不到"，而平台商店里正好有现成的现成方案时。

**实际例子？**

让它处理一个扫描版 PDF，纯文本模型读不了图；装一个 PDF 处理插件后，它就能识别里面的文字和表格。

**它和 Skill、MCP 的区别？**

- Plugin：平台官方商店式的成品功能，装好就用；
- Skill：更像一份"操作手册+工具箱"，教 Agent 怎么做某类专业活；
- MCP：底层的通用连接标准，一个 MCP Server 可以被多个不同的 Agent 共用。
三者边界在 2026 年仍在快速融合，以你所用平台的界面为准。

**新手掌握到什么程度？**

装之前看三样：这个插件要什么权限、谁做的、最近还更不更新。不要看到"热门"就点。

---

## 6.14 MCP（Model Context Protocol，模型上下文协议）

**它解决什么问题？**

早年每做一个工具，都要为每一个不同的 Agent 单独适配一遍——像每个国家的插头形状都不一样。MCP（Model Context Protocol）是 2024 年底开始被广泛采用的一套"万能插座标准"：任何按 MCP 标准写的工具，理论上任何支持 MCP 的 Agent 都能直接插上用。

**什么时候需要？**

当你想让 Agent 接一个具体的外部系统——连 GitHub、连数据库、连某家笔记软件、连某个搜索服务——而这个系统提供了一个"MCP Server"时。

**实际例子？**

你配一个 GitHub 的 MCP Server，之后支持 MCP 的 Agent 就能读你的仓库、看 issue、查代码，不用你教它怎么调 GitHub API。

**它和 Connector、Plugin 的区别？**

用一个类比收尾：API 是"传菜口"，MCP 是"传菜口的统一规格"，Connector 是"餐厅已经帮你接好的成品线"，Plugin 是"餐厅直接给你上的一桌菜"。MCP 本身不解决某个具体问题，它解决的是"别再一对一接线了"。

**新手掌握到什么程度？**

知道"MCP Server 也是一段会跑的代码"，所以和装任何社区脚本一样，要先看它是谁做的、要什么权限。不要因为它"叫标准协议"就放松警惕。

> 平台说明：MCP 的注册中心、客户端支持情况、配置方式各平台不一，且仍在快速变化。以 2026 年 9 月各平台官方文档与官方 Registry 为准。

---

## 6.15 Skill（技能）

**它解决什么问题？**

教 Agent 做某件专业的事，光靠一次 Prompt 说不清楚。Skill（技能）就是把"怎么做这件事"写成一个可复用的包：里面有一份说明书（通常叫 SKILL.md）、一套模板、有时还附带现成脚本和示例素材。装上之后，Agent 遇到同类任务就按这套打法来。

**什么时候需要？**

当你发现"这件事我每次都要跟它解释半天、而且每次解释还不一样"时，就该把它沉淀成一个 Skill。比如"按我校格式写开题报告""按我们组的口径做竞品调查"。

**实际例子？**

一个"学术综述写作 Skill"可能规定：先建证据矩阵、再按研究脉络分节、所有引用必须回原文核验、最后附未解决问题清单。装上它，你以后只要说"用综述 Skill 处理这批论文"，它就按这套流程走。

**它和 Workflow、Plugin 的区别？**

- Skill：偏"教方法+带材料"，核心是那份 SKILL.md；
- Workflow：偏"把固定步骤串成流水线"；
- Plugin：偏"给一个成品功能按钮"。
一个成熟的 Skill 里常常会引用一个 Workflow，也可能调用一个 MCP。

**新手掌握到什么程度？**

会打开一个 Skill 的 SKILL.md，读完前三段就知道"它想让 Agent 干什么、要碰什么文件、要联网吗"。这正好是 PART 7 的主题。

---

## 6.16 RAG（检索增强生成）

**它解决什么问题？**

你有一堆自己的资料：课程 PPT、导师给的内部文档、你多年的读书笔记。模型训练时根本没见过这些。直接把几百份文件塞进 Context 既装不下、又太贵。RAG（Retrieval-Augmented Generation，检索增强生成）的做法是：先把你的资料切块存进一个"小图书馆"，每次提问时，先从里面挑出最相关的几段，再把这几段喂给模型回答。

**什么时候需要？**

当你有大量私有资料、又希望 Agent "基于你的资料"而不是"凭它训练记忆"回答时。做个人知识库、做公司制度问答、做课程复习，都是典型场景。

**实际例子？**

你把一学期的 30 份 PPT 灌进 RAG，之后问"第三章讲的那个模型有什么局限"，它会先从这 30 份里找出第三章相关段落，再回答你，而不是瞎编。

**它和 Memory、Context 的区别？**

Memory 存的是"你和它对话的偏好和历史"；RAG 存的是"你的原始资料库"，靠检索动态取用。RAG 的关键风险是：**它检索出来的片段可能不对题**，所以回答里要能看到"它引用了哪份资料哪一段"。

**新手掌握到什么程度？**

会要求它每次回答都标"这段依据来自哪份文件"。标不出来的，不要信。

## 6.17 Workflow（工作流）

**它解决什么问题？**

复杂任务不是一句话说完的，而是一连串步骤：搜→筛→读→建表→分析→写→查。Workflow（工作流）就是把这一串步骤固定下来，下次同类任务直接按这条流水线走，不用每次重新指挥。

**什么时候需要？**

当你发现自己**每周都在重复同一套多步操作**时：每周出竞品周报、每批新文献走一遍"检索→筛选→综述"。

**实际例子？**

"每天早上 8 点，搜今天的行业新闻，和昨天的摘要对比，有重大变化才把摘要推给我"——这就是一条固定 Workflow。

**它和 Automation、Sub-agent 的区别？**

Workflow 是"步骤的固定顺序"；Automation 是"让它到点/触发就自己跑"；Sub-agent 是"把其中某一步派给一个专门的分身去做"。三者常一起出现：一条 Automation 按时间触发一条 Workflow，Workflow 里某一步派给一个 Sub-agent。

**新手掌握到什么程度？**

会把一个重复任务画成一张"箭头图"，问自己：第一步出什么、第二步凭什么、最后怎么验收。画清楚了，Workflow 就设计出来了。

---

## 6.18 Sub-agent（子智能体）

**它解决什么问题？**

一个 Agent 自己干长了，会顾不过来、会忘、会串味。Sub-agent（子智能体）就是主 Agent 临时派出去的"分身"：一个负责去搜资料，一个负责去读文件，一个负责去写初稿，最后主 Agent 把三份结果汇总。

**什么时候需要？**

任务能明显拆成几块、且每块需要专注时。比如写综述时，让一个子 Agent 专门去核实所有引用，另一个专门去查最新进展，主 Agent 专心写。

**实际例子？**

主 Agent 接到"调查 X 公司"，派子 Agent A 查工商信息，子 Agent B 查新闻舆情，子 Agent C 查产品；A、B、C 各交一份摘要，主 Agent 合并成最终报告。

**它和多平台"多 Agent"噱头的区别？**

不是任务越复杂就越要开一堆分身。分身穿得越多，汇总成本和出错率越高。新手先把单 Agent 跑顺，再考虑拆分。

**新手掌握到什么程度？**

知道"派出去的分身，交回来的东西也要验收"——它不会因为叫"子 Agent"就自动可靠。

---

## 6.19 Automation（自动化）

**它解决什么问题？**

最理想的状态是：这件事不用你每天去说，它到点自己跑、有事自己通知你、没事不打扰。Automation（自动化）就是把 Workflow 接上一个"闹钟"或"触发器"：定时跑、收到邮件跑、网页变了跑。

**什么时候需要？**

当这件事**有规律、有明确触发条件、且低风险**时。高风险、需要你每次判断的事，不适合全自动。

**实际例子？**

每天早上抓一次 arXiv 上你关心方向的新论文，过滤后给你发一份 5 条摘要；有新论文时才打扰，没有就静默。

**它和 Workflow 的区别？**

Workflow 是"步骤怎么排"，Automation 是"什么时候自动跑这条 Workflow"。前者是菜谱，后者是定时器。

**新手掌握到什么程度？**

第一版自动化一定先设成"跑完先把结果给我看，别自己发出去"。跑稳两周、你确认它不会乱来，再逐步放开发送权限。

## 本章 Mission

学完这一章，你不需要背术语，但要能完成下面三个任务。

**Mission 6-A：给你手上的一个 Agent 画一张"构成图"**

拿你最近在用的那个 Agent，回答：它现在用的是哪个 Model？它这一轮能看到哪些 Context？它有哪些 Tool（搜索、文件、浏览器、代码、MCP……）？它有没有 Memory？把答案列成一张清单。你会立刻发现自己之前一直在"裸用"，很多能力其实没开。

**Mission 6-B：判断一次失败到底卡在哪个零件上**

回想最近一次它没做好的任务。对着这张六层图判断：是 Model 不够聪明（Reasoning/Coding 不行）？还是 Context 没给够（漏了材料）？还是 Tool 没开（该让它搜它没搜）？还是 Workflow 没设计（步骤乱了）？定性之后，下次任务就对症下药，而不是只会重写一遍 Prompt。

**Mission 6-C：分清三个最容易混的概念**

用自己的话写三句话：Context 和 Memory 差在哪？Search 和 Browser 差在哪？MCP 和 Connector 差在哪？写不出人话版，就回去重读对应那一节。这三对概念分清了，这一章就过关了。

# PART 7：给 Agent 安装和扩展能力

> 先导图：Agent 能力扩展安装与授权流程图（待插入 F02：从发现资源 → 读说明 → 查安全 → 授权/装密钥 → 最小权限 → 验证 → 交付/卸载的闭环）

## 本章你要解决什么问题

上一章讲清楚了 Agent 由哪些零件组成。本章解决一个非常实际的问题：**这些零件不是出厂全装好的，很多要你自己去"插上去"**。就像新手机买回来只能打电话，导航、外卖、修图都得你自己装 App。

但这里有一条贯穿全章的铁律，请你先记住：

> 社区里的 Skill、Plugin、MCP、Connector，不能因为"很多人装"你就装。GitHub 上的 Star 数不等于安全，商店里的"热门推荐"不等于对你合适。每装一个，你都要知道它碰了什么数据、能干什么动作、钥匙放在了哪里。

## 7.1 从"模型能力"到"Agent 能力"

模型出厂时只会做一件事：读一段文字，吐一段文字。它不能读你电脑里的论文，不能查今天的新闻，不能动你的 Excel，也不能替你发邮件。这些"超能力"全是后来装上去的。

所以判断一个 Agent 到底强不强，不要只看它用了多牛的 Model，而要看：

- 它接了哪些 Tool（搜索？文件？浏览器？代码？）；
- 它装了哪些 Skill / Plugin / MCP；
- 它连了哪些你的账号（邮件？日历？云盘？GitHub？）；
- 你给了它多大的操作权限。

**模型决定天花板，扩展能力决定它能不能下地干活。** 一个用中档模型但工具齐全、权限合理的 Agent，往往比一个用顶级模型却"赤手空拳"的 Agent 有用得多。

## 7.2 安装 Skill

Skill 的安装在各平台上长得不一样，但通用动作就四步：

1. **找到它**：从平台官方 Skill 商店、官方 GitHub 组织、或你信任的 Skill 目录里找到一个具体的 Skill，记下它的来源地址。
2. **读它的说明书**：每个 Skill 根目录下都有一个 `SKILL.md` 文件，这是它的脸，下一节专门讲怎么读。
3. **放进指定位置**：把这个 Skill 文件夹放到你的 Agent 配置目录里——通常是一个叫 skills 的文件夹，不同平台路径不同，以该平台文档为准。
4. **让 Agent 认识它**：重启或刷新 Agent，或者直接对它说"你现在有一个叫 XX 的 Skill，请先读它的 SKILL.md"。第一次用之前，让它先自己读一遍说明书。

**新手最容易踩的坑**：从某个聚合网站上看到一个"排名很高"的 Skill，直接一键安装，从没打开过它的 SKILL.md。这等于没看合同就签字。下一节起我们就是要治这个毛病。

## 7.3 阅读 SKILL.md

`SKILL.md` 是什么？它就是一个纯文本的 Markdown 文件，是这个 Skill 的"产品说明书+岗位说明书"。它一般不长，几百行以内。你不需要懂代码，用记事本就能打开。

打开之后，重点找下面这几段，按顺序读：

| 你要找的信息 | 它通常会写在哪 | 你要判断什么 |
|---|---|---|
| 这个 Skill 是干嘛的 | 开头的简介 | 和你要做的事对不对得上 |
| 它支持哪些 Agent / 平台 | 安装说明 | 你用的平台到底装不装得上 |
| 它需要什么前置条件 | Requirements / Prerequisites | 要不要额外装软件、要不要账号 |
| 它会读哪些文件、写哪些文件 | 权限说明 / 工作方式 | 会不会动到你的原始材料 |
| 它会不会联网、会不会调付费 API | 网络/费用说明 | 会不会偷偷跑钱、会不会外发数据 |
| 它附带什么脚本 | Files / Scripts 部分 | 脚本是最需要警惕的部分，见 7.5 |
| 怎么卸 | Uninstall | 装之前先确认能撤 |

读 SKILL.md 不需要你读懂代码，只需要你回答一个问题：**"这个东西装进我的 Agent 之后，它可能对我的电脑、我的账号、我的钱做什么？"** 答得上来，再装；答不上来，先别装。

## 7.4 判断一个 Skill 是否可信：12 问安全检查清单

下面这 12 个问题，是你每次装社区 Skill 前必须在心里过一遍的。它来自本教程的安全要求，也对应行业通用的开源件审查习惯。请把它当成一张检查表，装之前逐条问自己：

1. **来源是谁？** 是知名公司官方仓库，还是一个匿名账号？作者过去有没有别的可信项目？
2. **源代码在哪里？** 能不能看到完整代码，而不是只有一个"一键安装"按钮？
3. **最近有没有维护？** 最近一次提交是上周还是三年前？三年没动的东西，装之前要更谨慎。
4. **它会执行什么脚本？** 附带的脚本大概是干什么的？有没有看起来和它宣传的功能无关的操作？
5. **它能读什么文件？** 会不会去翻你的文档、桌面、下载文件夹？
6. **它能写什么文件？** 会不会往系统目录、配置目录里塞东西？
7. **它能访问哪些网站 / API？** 除了它该用的那个服务，还会不会连到别的地址？
8. **它需要哪些账号权限？** 连你的邮箱时，是"只读"还是"能发邮件"？连你的 GitHub 时，是"只读代码"还是"能替你 push"？
9. **它会不会把我的数据发到第三方？** 读出来的内容除了给模型用，会不会还发给别人？
10. **它会不会调用付费 API？** 跑一次花多少钱？有没有上限？
11. **它有没有删除、覆盖、修改能力？** 误操作时能不能找回来？
12. **能不能先在测试目录跑一遍？** 有没有一个干净的文件夹、一份副本，让它先在里面玩一次？

**特别强调两句话**：

- **Star 数不等于安全。** 一个热门项目可能被很多人装，但它的代码你没看过，风险就在你这台机器上。Star 只能说明"它流行"，不能说明"它干净"。
- **"官方"两个字要看清楚。** 有些聚合站名字里带 Official，不代表它是某家公司官方办的。认准域名和 GitHub 组织名，别被名字带跑。

第一次做这 12 问会很慢。做过四五次之后，你会形成直觉：这个 Skill 靠不靠谱，扫一眼开头和脚本列表就有数了。

## 7.5 Skill 中的脚本、模板和资产

打开一个 Skill 文件夹，你通常会看到三类东西：

- **说明文档**：就是 SKILL.md，你刚才读过的那份。最安全，纯文本。
- **模板和资产**：半成品文档、示例数据、图片、配置样例。它们本身不会自己跑，是给 Agent 参考着用的。风险低。
- **脚本**：真正会被执行的代码，可能是 Python、Shell、或平台自己的命令。这是**风险最高**的部分——它装上去之后，Agent 可能在你没注意的时候跑它。

新手不需要会写脚本，但要会"看脚本在干嘛"。一个粗略的原则：

- 如果脚本只是"格式化文本""生成一个固定表格"，风险低；
- 如果脚本里出现了"联网下载""删除文件""改系统配置""读环境变量并外发"这类字眼，立刻提高警惕，回去把 12 问里对应的问题问清楚再决定。

看不懂脚本写了什么，就把它丢给你正在用的 Agent，问："这段脚本从头到尾干了什么？有没有删文件、联网、发数据的动作？"让它用人话讲给你听。

## 7.6 安装 Plugin

Plugin 和 Skill 很像，都是"给 Agent 加一块能力"，差别主要在来源和形态：

- **Plugin** 通常来自平台官方商店，一键安装，背后常连的是平台认证过的服务。你在界面上点"安装"，它就挂上去了。
- **Skill** 更像从开源社区下载的一个文件夹，你要自己放到配置目录、自己读 SKILL.md。

装 Plugin 相对省心，但"平台官方商店"不代表"绝对安全"：你依然要在安装弹窗里看一眼它要什么权限、会不会收费、会不会读你的账号数据。商店审核一般会拦住明显的恶意件，但审不到"这个插件是否过度收集你的数据"这种灰色问题。

## 7.7 添加 MCP Server

MCP 的添加方式，通常是在你的 Agent 配置文件里，写上一段说明："我要用哪个 MCP Server，它怎么启动，它的钥匙放哪"。改完配置，重启 Agent，它就插上了这个"万能插座"。

以 2026 年 9 月各平台现状为准，不同平台的配置文件位置和格式不同，**不要照抄网上三年前的教程**，以你所用平台官方文档里的"添加 MCP"一节为准。

添加 MCP 时同样要过 12 问：这个 Server 是谁写的？它要访问什么？它需要什么密钥？会不会把你的数据转给第三方？一个标着"MCP"的开源 Server，本质和一个 Skill 一样，是会跑的代码。

## 7.8 添加 Connector

Connector 是最贴近普通用户的扩展方式：界面上一个"连接邮箱""连接日历""连接云盘"的按钮，点一下，跳到你那个账号的登录页，授权，回来就连上了。

它和手动配 MCP 的区别是：Connector 把技术细节包起来了，你不用碰配置文件。但授权那一步，你仍然要看清楚——这就引出下一节。

## 7.9 OAuth 与账号授权

当你点"连接邮箱"时，跳出来的那个登录页问你："是否允许 XX 应用访问你的邮箱？"——这背后走的就是 **OAuth**（一种业界通用的"第三方授权"机制，你可以先理解成"你不把账号密码告诉这个应用，而是通过官方登录页给它发一张有时效的通行证"）。

关键不是这个机制本身，而是你在授权页上要做的事：

**授权页会列出这个应用要哪些权限。你要逐条看，不要直接滑到底点"同意"。** 典型的权限粒度包括：

- 只读你的邮件 / 日历 / 文档，还是能替你发邮件、改日历、删文档？
- 能访问哪些数据？全部，还是只某个文件夹？
- 有效期多久？能不能随时撤销？

用一个类比：OAuth 授权就像你给朋友一把家里的钥匙。你要知道这把钥匙能开哪扇门——能开大门可以理解，能开保险箱就过分了。授权页列出的就是"这把钥匙能开哪些门"。

事后想反悔怎么办？去你那个账号（邮箱、云盘、GitHub）的"第三方授权 / 应用授权"设置页，找到这个 Agent，点"撤销授权"。这一步任何时候都可以做，别等出了事才找。

## 7.10 API Key

很多服务不给你登录授权页，而是让你填一串"密钥"。这串字符就是 **API Key**——你调它服务时的"门钥匙"。

先讲清楚三件最重要的事：

**第一，它是什么。** API Key 长得像一串随机字符（例如 `sk-xxxxxxxx...`）。拿着它，任何人都能以你的身份调用那个服务、用你的额度、甚至产生你的账单。

**第二，它不是密码，但比密码还不能外传。** 密码你还能登录后改，API Key 一旦泄露，要么去服务商那里重新生成一个、把旧的作废。它泄露的代价是真金白银和数据。

**第三，三条铁规矩：**

- **不要把 API Key 写进普通的对话 Prompt 里。** 你在对话框里贴一次，它就可能被记进聊天历史、被模型的日志带走。
- **不要把 API Key 提交到 GitHub 等公开仓库。** 哪怕你觉得"这个仓库只有我自己看"——仓库可能变公开、可能被 fork、可能被 AI 扫描器盯上。业界每年都有成百上千个 Key 因为误传 GitHub 被扫走、被盗刷。
- **Key 要能随时作废、随时重发。** 每个服务商后台都有"重新生成 / 作废旧 Key"的功能，怀疑泄露就立刻换。

那 Key 到底放哪？看下一节。

## 7.11 环境变量

直接在对话框里念 Key，是最危险的做法。正确做法是把 Key 放进一个专门的地方，让 Agent 要用时自己去取，而不是每次都从对话里读到。

这个专门的地方，就是**环境变量（Environment Variable）**。你可以先把它理解成"一个上锁的抽屉"：你把 Key 放进去，关上门；Agent 需要用的时候，按约定的名字去抽屉里拿，但它看不到别的东西，也不会把这串字打印到对话里、写进提交记录。

各平台设置环境变量的入口不同（有的在设置页，有的在配置文件里，有的在你电脑的系统环境变量里），以你所用平台文档为准。你只需要建立这个习惯：

> 凡是钥匙类的东西（API Key、Token、密码），一律进环境变量或平台的密钥管理处，永远不进 Prompt、不进文档、不进 Git。

## 7.12 最小权限原则：L1–L4 风险分级表

装上了能力，就要管住它能干什么。核心原则一句话：**只给完成这件事所需的最小权限，多一分都不给。**

把 Agent 的所有可能动作，按"做错了能不能收回来"分成四级：

| 风险级别 | 典型动作 | 默认策略 |
|---|---|---|
| **L1 低风险** | 读文件、搜索网页、分析数据副本、读你给的材料 | 可以自动执行，不用每次问你 |
| **L2 可逆修改** | 新建文件、改工作副本、在 Git 上建分支、改草稿 | 可以执行，但要留记录（改了什么、改前是什么） |
| **L3 高影响** | 覆盖你原来的文件、Git push 到远程、改云端共享文档、替你发消息或邮件 | 建议每一步都停下来让你确认 |
| **L4 不可逆 / 高风险** | 删除数据、支付、公开发布、改生产数据库、改权限、对外发正式公告 | 必须你明确说"确认执行"才做，且最好先备份 |

这张表你可以直接抄下来，贴在你和 Agent 协作时的旁边。每次派任务时，心里过一遍："我现在授权它做的事，落在哪一级？"

- 做文献整理、读 PPT、分析 Excel 副本——L1，放手让它跑。
- 让它在工作文件夹里新建分析结果——L2，跑之前让它先说清楚要建哪几个文件。
- 让它改你那份要交的论文原稿——L3，先让它改一个副本，你看满意了再替换。
- 让它"把这封邮件发出去""把这个推到 GitHub 主分支""付这笔钱"——L4，停下来，你自己点最后一下。

一个朴素的判断：**凡是错了找不回来的事，最后那一下永远你自己按。**

## 7.13 如何卸载 / 禁用能力

装上去的东西，要能撤下来。三种动作要分清：

- **临时禁用**：Agent 里往往有开关，把某个 Skill / Plugin / MCP 关掉，它暂时不生效，但文件还在。适合"我现在不想用它，但以后可能还开"。
- **卸载**：把这个插件从 Agent 里移除。适合"我确定不用了"。
- **撤销账号授权**：如果它连了你的邮箱 / GitHub / 云盘，记得去对应账号的第三方授权页把它踢掉——光在 Agent 里卸载，有时你那个账号上的授权还挂着。

一个好习惯：每季度花十分钟，去你常用的账号（邮箱、GitHub、云盘、社交平台）的"第三方应用授权"列表里扫一眼，把不认识、不再用的授权全部撤销。

## 7.14 如何更新 Skill / Plugin / MCP

这些社区件会更新：修 bug、加功能、改权限。但**不要开启全自动更新**。理由很简单：一个昨天还干净的 Skill，今天的版本可能加了联网、加了付费调用。

正确姿势：

1. 更新前先看它的更新说明（changelog / release notes）——这版改了什么？
2. 尤其注意"新增了什么权限、新增了什么网络请求、新增了什么依赖"。
3. 更新后跑一次你常用的 Mission，确认它没跑偏。
4. 出问题就回到上一个版本。

平台官方商店的 Plugin 更新相对省心，但也别假设"官方更新 = 对你更好"。

## 7.15 如何发现新的 Agent 能力：资源地图概念

最后一个问题：我怎么知道"有什么新东西可装"？

不要靠刷社交平台碰运气。你需要在心里建立一张**资源地图**，按三层去找，越靠上越可信：

**第一层：官方来源。** 你所用 Agent 平台的官方文档、官方 Skill 商店、官方 GitHub 组织、官方 MCP 注册中心。先查这里，因为信息最准、维护最勤。

**第二层：聚合发现平台。** 一些社区目录会聚合公开的 Skill、MCP、Plugin，方便你搜索。它们的价值是"让你发现"，**不是让你直接装**。看到感兴趣的，记下来，回到第三层。

**第三层：源仓库。** 打开这个 Skill / MCP 的 GitHub 或官方源码页，看：谁做的、最近提交时间、Star 和 Issue 活跃度、README、License、有没有脚本、要什么权限。过一遍 7.4 的 12 问，再决定装不装。

> 再次强调：聚合平台上的排名、评分、"热门""推荐"，只代表它被很多人发现，不代表它安全、不代表它适合你、不代表它还在维护。**发现靠聚合站，决定靠源仓库。**

具体的官方注册中心、Skill 目录、MCP 目录、社区 Awesome 列表，本教程配套的资源文件里会单独整理，并标注核验日期。本节只教你这套"三层找法"。
